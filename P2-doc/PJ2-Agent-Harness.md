## 1. 용어와 범위
### 1.1 런타임 하네스와 개발 하네스

| 구분 | 무엇을 감싸나 | 예 | 원본 |
|---|---|---|---|
| **런타임 하네스**(이 문서) | 제품 안에서 사용자 질문을 처리하는 LLM 에이전트(`gpt-6-luna`, ReAct) | `guardrail_in`, 도구 출력 계약, 도구 실행 전후 검사, 호출 상한, `validator`, `finalize` | RFP-29 §4.1, 이 문서 |
| 개발 하네스 | 저장소에서 일하는 사람과 코딩 에이전트(Claude Code) | pytest, ruff, pre-commit, Claude Code 훅(`.claude/settings.json`), `check_schedule.py` | RFP-29 §4.3, RFP-29-01 A, BE-15 |
| 평가 하네스 | 측정 결과 | 코드 채점기, judge(J1~J5), 경로·신뢰성 평가 | RFP-29 §4.2, RFP-26 |

이 문서가 말하는 "하네스"는 모두 **런타임 하네스**다. 개발 하네스의 pytest는 이 문서의 장치를 **테스트하는 도구**로만 나온다(이 문서 6장).

### 1.2 PreToolUse·PostToolUse라는 이름
- Claude Code에는 같은 이름의 훅(도구 실행 직전·직후에 도는 스크립트)이 있다. 이 문서는 **그 훅을 쓰지 않는다.** 이름과 개념만 빌려 온다. 개념은 도구 호출 한 건을 실행 전에 막고, 실행 후 결과를 검사하는 것이다. 구현은 LangGraph 그래프 안의 파이썬 코드다.
- 이 프로젝트에서의 뜻:
  - **PreToolUse**: 모델이 낸 `tool_call` 한 건을 **실행하기 직전**에 검사한다. 결과는 **통과 / 차단(도구를 실행하지 않고 이유를 돌려줌) / 경고(기록하고 통과)** 셋뿐이다. 인자를 몰래 고쳐서 통과시키지 않는다. 그러면 trace의 호출과 모델이 낸 호출이 달라져 경로 평가(PJ2-RFP.md 9.4절)가 어긋난다. 이름 정규화(공백·염 이름 → 표준명)는 도구 안의 사전(BE-10)이 한다.
  - **PostToolUse**: 도구가 **돌아온 직후** 결과를 검사한다. 항목별 상태, 근거 ID, 제품 단위 정보 없음 표시, 파일/API 병기 표시, 데이터 블록 구분이 대상이다.
  - **기준선에서는 둘 다 도구 함수 안에서 구현한다.** Pre는 인자 스키마 검증이고, Post는 도구가 지켜야 할 **출력 계약**이다(3.2). 그래프 상태(요청 범위)를 읽어야 하는 검사는 실패를 관찰한 뒤 개선 단계에서 래퍼로 더한다.
- 입구(`guardrail_in`, LLM 호출 전)와 출구(`validator`·`finalize`, 최종 답 뒤)는 도구 단위가 아니라 질문 단위다. 그래서 따로 부른다(3.1).

| 지점 | 언제 | 단위 | 노드·함수(제안) | 주된 규칙 |

### 3.2 그래프 배치
```
START → guardrail_in ─(거절·범위 외·미확인 사진 입력)→ finalize → END
             ▼
           router
             ▼
           model ──tool_calls 있음──▶ tools ┐   기준선: 단일 ToolNode(RFP-23 §4.2)
             ▲                              │   도구 함수 안: 인자 스키마 → 본문 → 출력 계약(items[])
             └──────────────────────────────┘
             │ tool_calls 없음        (steps ≥ 8이면 finalize로 안내 전환, RFP-23 §4.5)
             ▼
          validator ─(실패)→ finalize(안내 전환)      (개선) 실패 시 model로 되돌림 ≤2, RFP-23 §4.5
             ▼
          finalize → END
```
- **기준선**: `tools`는 RFP-23 §4.2의 단일 `ToolNode`다. Pre(인자 스키마)와 Post(출력 계약)는 **도구 함수 안**에 있다. 도구는 모두 같은 형식(`items[]`, 항목마다 ID·상태·꼬리표)으로 돌려준다(3.4). 그래서 C1·C1+처럼 코드가 도구를 부르는 조건에서도 같은 계약이 적용된다(7.2). 출력 계약의 항목이 `evidence`(누적 reducer, RFP-23 §4.4)로 들어가는 방식은 RFP-23 §4.4 표가 이미 가정한 것이다. 다만 `ToolNode`가 도구 결과로 `messages` 밖의 상태 키를 쓰는 방법은 확인하지 못했다(10장). 안 되면 `finalize`가 `ToolMessage` 본문의 `items[]`를 읽는다.
- **개선 단계**(실패를 관찰한 뒤, AG-13): 요청 범위 그래프 상태(`known_ids`, `input_units`)를 읽어야 하는 검사를 더할 때만 `tools` 자리를 얇은 함수 노드 `harnessed_tools`로 바꾼다. 노드 수는 6개 그대로다.
  ```
  harnessed_tools(state):                  # 개선 단계에서만
      local = Accum.from_state(state)       # known_ids·input_units를 이 묶음 안에서 누적할 로컬 사본
      msgs, events = [], []
      for call in last_ai_message(state).tool_calls:   # 순서대로 처리(묶음 안 앞 결과가 뒤 Pre에 반영됨)
          pre = pre_tool_use(call, local)
          events += pre.events
          if pre.blocked:
              msgs.append(pre.tool_message(call.id)) ; continue   # 차단한 호출에도 ToolMessage 1개
          result = TOOLS[call.name](pre.args)
          msg, upd = post_tool_use(call, result, local)
          local.merge(upd) ; events += upd["events"] ; msgs.append(msg)
      return {"messages": msgs, "evidence": local.new_evidence,
              "known_ids": local.new_ids, "input_units": local.new_units, "harness_events": events}
  ```
  - 노드는 상태를 **한 번만** 반환하고, 각 키는 3.5의 reducer로 합쳐진다(호출마다 나온 `upd`를 버리지 않는다).
  - 모든 `tool_call_id`에 `ToolMessage`가 하나씩 있어야 하는지(OpenAI API 요건)는 **확인하지 못했다**(10장). 그래서 차단한 호출에도 `ToolMessage`를 하나씩 만드는 쪽으로 정한다.
  - 기준선과 개선 모두 `ToolNode` 내장 훅(도구 호출 래퍼 인자)이 있는지는 확인하지 못했다(10장). 있으면 그것으로 바꿔도 동작은 같다.
- 상한: `steps`(모델 호출 수)가 8에 닿으면 `finalize`가 안내 전환 응답을 만든다(RFP-23 §4.5). "같은 차단이 2번 반복되면 종료" 같은 **새 상한 숫자는 두지 않는다**(RFP-22-05, H12). 상한에 닿으면 이미 얻은 판정 항목을 코드 문구로 보이고 판정하지 못한 항목은 "확인하지 못함"으로 둔다(RFP-33-06 A).

### 3.3 PreToolUse 의사코드
```python
# mediagent/harness/pre_tool.py (제안)
# [기준선] 1번만. 도구 함수 안의 Pydantic 검증이다(H8의 기존 Sensor "도구 입력 스키마 검증").
# [개선] 2~4번은 해당 실패를 관찰한 뒤 한 번에 하나씩 더한다(RFP-33-04, AG-13).
# ctx = 노드에 들어올 때의 state + 이 묶음에서 앞 호출이 더한 local 값(3.2)
def pre_tool_use(call, ctx) -> PreResult:
    spec = TOOL_SPECS[call.name]                    # Pydantic 인자 모델 + 규칙 메타
    # 1. [기준선] 인자 스키마 (H8, H21): 성분코드 형식(D######·KIDS 형식), 품목기준코드 9자리 등
    args, err = spec.validate(call.args)
    if err: return block("H21", "ARG_SCHEMA", detail=err)
    # 2. [개선] ID 존재 (H21): 이 요청에서 앞선 도구 결과에 나온 ID만
    for id_ in spec.ids(args):
        if id_ not in ctx.known_ids:
            return block("H21", "UNKNOWN_ID", detail=id_)
    # 3. [개선] 단위 보조 차단 (H17): 출력 계약이 있는데도 제품 정보가 새는 것을 관찰했을 때만
    if spec.returns_product_label and ctx.input_units.get(spec.drug_id(args)) == "ingredient":
        return block("H17", "NO_PRODUCT", detail=spec.drug_id(args))
    # 4. [개선] 같은 호출 반복 (H12 보조): 경고만 기록하고 실행한다(RFP-33-02 A). 종료는 상한 8에 맡긴다
    if ctx.same_call_count(call) >= 1:
        return allow(args, events=[event("H12", "warn", "REPEAT", call.name)])
    return allow(args)
```
- `block(rule, code, detail)`은 도구를 실행하지 않고 3.6 형식의 `ToolMessage`를 만든다. 모델은 이것을 Observation으로 받아 다음 행동을 다시 고른다. ReAct 루프 안의 재시도이며 Reflexion이 아니다(RFP-22-10).
- 사진 확인 선행(H19)은 도구 단위가 아니라 **입구**에서 한 번 검사한다(4.1 (c)). 그래서 Pre에 두지 않는다.
- 차단 강도(하드 차단 vs 경고)는 RFP-33-02다. 기준선에서 해당하는 것은 1번(스키마)과 입구의 확인 선행뿐이다.
- 인자 정규화는 하지 않는다(1.2). 정규화는 도구 안의 사전(BE-10)이 맡는다.

### 3.4 PostToolUse 의사코드
기준선에서 아래 1~6번은 **도구 함수가 만드는 출력 계약**이고 pytest로 검사한다. 개선 단계에서 `harnessed_tools`를 두면 같은 검사를 실행 중에도 한다(계약 위반 항목은 `NO_EVIDENCE`로 바꾸고 이벤트를 남긴다. 판정 값은 바꾸지 않는다).
```python
# mediagent/harness/post_tool.py (제안)
STATUS_BY_TOOL = {
    "identify_drug":           {"FOUND", "UNIDENTIFIED"},
    "check_contraindications": {"FOUND", "NOT_LISTED", "UNIDENTIFIED"},
    "search_notice": {"FOUND", "NO_EVIDENCE"}, "search_reason": {"FOUND", "NO_EVIDENCE"},
    "search_label":  {"FOUND", "NO_EVIDENCE", "NO_PRODUCT"}, "get_label_section": {"FOUND", "NO_EVIDENCE"},
}
POST_WRITABLE_KEYS = {"evidence", "known_ids", "input_units", "events"}   # emergency·route·profile·confirmed_mentions는 못 쓴다

def post_tool_use(call, result, ctx) -> tuple[ToolMessage, dict]:
    upd = {"evidence": [], "known_ids": set(), "input_units": {}, "events": []}
    for item in result.items:      # 모든 도구가 같은 형식. 항목 = 약 1개 / 쌍 1개 × 금기 종류 / 청크 1개
        # 1. 항목별 상태 (H2, FR-08). 도구 호출 1건에 상태 하나를 두지 않는다
        check(item.status in STATUS_BY_TOOL[call.name])
        # 2. 근거 ID (H1): ID·출처·기준일 또는 조회 시각
        check(item.evidence_id and item.source and item.as_of)
        # 3. 단위 (H17): 성분명으로 일치한 항목은 제품 필드(제품 연령 문장·허가 라벨·제형)가 비어 있어야 한다
        if item.matched_by == "ingredient_name":
            check(item.product_fields_empty() and "NO_PRODUCT_INFO" in item.flags)
            upd["input_units"][item.drug_id] = "ingredient"
        elif item.matched_by == "product_name":
            upd["input_units"][item.drug_id] = "product"
        # 4. 라벨 출처 (H18): 전문의약품이라 e약은요가 없으면 허가 상세 원문만 쓰고 EASY_TEXT_MISSING
        if item.is_label and item.easy_text is None:
            check(item.label_source == "허가정보 상세" and "EASY_TEXT_MISSING" in item.flags)
        # 5. API 병기 (H9·H20): 파일 판정은 그대로 두고, API 쪽 꼬리표만 본다
        if call.name == "check_contraindications" and item.api_checked:
            check(item.api_flag in {"API_SAME", "FILE_ONLY", "API_ONLY", "API_FAIL", "API_PAIR_INCOMPLETE"})
        upd["evidence"].append(item)
        upd["known_ids"] |= item.ids()            # identify_drug 후보의 품목기준코드·성분코드(두 체계)도 포함
    # 6. 데이터 블록과 키 제한 (H8, NFR-09)
    check(set(upd) <= POST_WRITABLE_KEYS)
    return ToolMessage(render_data_block(result.items), tool_call_id=call.id), upd
```
- **상태 4종**: `FOUND`(해당 있음, 또는 찾음), `NOT_LISTED`(조회는 성공했고 금기 목록에 없음), `UNIDENTIFIED`(약을 식별하지 못해 판정하지 못함), `NO_EVIDENCE`(검색 도구가 맞는 근거를 찾지 못함)다. 도구별로 쓸 수 있는 상태는 위 `STATUS_BY_TOOL`과 같다. 검색 도구의 `NO_EVIDENCE`는 RFP-22-02 A의 코드 검사(청크의 약·성분 ID 일치)로 정한다. 의미 검색은 0건이 잘 나오지 않으므로 건수로 정하지 않는다. `search_label`의 `NO_PRODUCT`는 성분코드로 불렀을 때의 결과이며, 상태가 아니라 거부 응답이다(4.1 (a)).
- **API 쪽 사정은 상태가 아니라 꼬리표다.** API 실패나 양방향 누락은 파일 판정을 바꾸지 않는다(PJ2-RFP.md 5.1절 (7)). 그래서 초안의 `INCOMPLETE` 상태는 없앴다. 평가에서는 API를 끄므로 이 꼬리표가 나오지 않는다.
- **입력 코드 형식 꼬리표 2개(2026-11-10 사용자 승인, 어휘 표 등록)**: `INVALID_CODE`는 `identify`가 형식이 맞지 않는 코드를 받아 `UNIDENTIFIED`로 돌려줄 때 항목에 붙고(`backend/app/tools/lookup.py` 224·243행), `PAIR_NOT_CHECKED`는 코드 쌍 중 하나가 `INVALID_CODE`여서 그 쌍을 조회하지 못했을 때 붙는다(같은 파일 253행). 둘 다 상태는 `UNIDENTIFIED`이고 `NOT_LISTED`가 아니다(H2). 회귀 시험은 `backend/tests/test_be09_lookup.py`다. 문구는 아래 표에 있다.
- PostToolUse는 **판정을 바꾸지 않는다.** 판정은 도구 안의 코드가 이미 했고(H9), Post는 결과가 계약을 지켰는지 본다. 모델·`validator`·`finalize`가 같은 사실을 보게 하는 것이 목적이다.
- `finalize`는 항목별 상태와 꼬리표를 읽어 **항목마다** 고정 문구를 코드로 붙인다. 순서는 `FOUND`(금기 발견) 항목이 먼저다. 그래야 한 결과 안에서 발견한 금기가 다른 항목의 "확인하지 못함"에 묻히지 않는다(PRD 화면의 "제품별 줄", PJ2-PRD.md 15장).

| 상태·꼬리표 | `finalize` 문구(코드 상수) |
|---|---|
| `FOUND` | 금기 종류·등급 원문·고시번호(등급은 상세정보 문구 그대로) |
| `NOT_LISTED` | "금기 목록에 없음(안전하다는 뜻이 아님)" |
| `UNIDENTIFIED` | "약을 찾지 못해 확인하지 못함" + 다시 쓸 이름 안내. 항목에 `input_name`(입력 이름 그대로)·`searched[{dataset, count}]`·`retried`를 달고 화면 문구는 기관 표기 `식약처·한국의약품안전관리원 자료에서 찾지 못했어요`(내부 단계명·`약 이름 사전` 없음). 다중 약 질문의 식별된 약은 요약 한 줄 항목으로 함께 나간다(PRD-14-01·02·04) |
| `INVALID_CODE` | (초안, AG-06 구현 때 확정) "입력한 약을 식약처·한국의약품안전관리원 자료에서 찾지 못했어요. 약 이름을 다시 알려 주세요." 형식이 맞지 않는 코드(None·빈 문자열·KIDS 성분코드 형식 아님)가 `UNIDENTIFIED`로 돌아온 항목에 붙는다. 판정한 출처가 아니므로 `source=None`·`as_of=None`·`dataset_key=None`이다(BE-09 §2, 2026-11-10). 코드명은 화면에 노출하지 않는다 |
| `PAIR_NOT_CHECKED` | (초안, AG-06 구현 때 확정) "이 약과 함께 먹어도 되는지는 식약처·한국의약품안전관리원 자료에서 확인하지 못했어요. 안전하다는 뜻이 아니에요." 코드 쌍 중 하나가 `INVALID_CODE`여서 그 쌍을 조회하지 못한 항목에 붙는다. `NOT_LISTED`가 아니라 `UNIDENTIFIED`이며 "확인하지 못함"으로 렌더한다. 판정한 출처가 아니므로 `INVALID_CODE`와 같이 `source=None`·`as_of=None`·`dataset_key=None`이다(2026-11-10 사용자 결정). 코드명은 화면에 노출하지 않는다 |
| `NO_EVIDENCE` | "근거 문장을 찾지 못함" |
| `NO_PRODUCT_INFO` | "제품 단위 정보(제품 연령 문장·허가 라벨·제형) 없음. 봉투의 제품명을 알려 주시면 더 확인할 수 있어요" |
| `EASY_TEXT_MISSING` | "{약 이름}은 전문의약품이라 쉬운 설명(e약은요)이 없어서 허가사항 원문을 그대로 보여 드려요"(PRD-10-04, `EASY_TEXT_MISSING_NOTE`). 허가 상세 원문이 있을 때의 안내 한 줄이다 |
| 미확보 `OUT_OF_SCOPE` | `MISSING_OUT_OF_SCOPE`: "{약 이름}은 전문의약품이라 공공 자료로는 설명을 확인할 수 없어요" + 약사 확인 권고 |
| 미확보 `ABSENT` | `MISSING_ABSENT`: "{약 이름} 허가사항에는 이 항목이 따로 적혀 있지 않아요" + 약사 확인 권고 |
| 미확보 `FETCH_FAIL` | `MISSING_FETCH_FAIL`: "지금은 허가사항을 불러오지 못했어요. 잠시 뒤 다시 시도해 보세요" + 약사 확인 권고 |
| 미확보 `SEARCH_MISS`(`NO_EVIDENCE`) | `MISSING_SEARCH_MISS`: "허가사항에서 관련 문장을 찾지 못했어요" + 약사 확인 권고 |
| 등급 정의 블록 미확보 `GRADE_DEF_MISSING`(후보) + `FETCH_FAIL`·`OUT_OF_SCOPE` | `FETCH_FAIL`: "지금은 임부금기 {N}등급의 뜻(고시 원문)을 불러오지 못했어요. 잠시 뒤 다시 시도해 보세요." / `OUT_OF_SCOPE`: "임부금기 {N}등급의 뜻(고시 원문)을 아직 준비하지 못했어요." + 약사 확인 권고(후보). `SEARCH_MISS` 없음(등급 정의는 청크 ID 조회). 원문 없는 블록은 조항 출처 줄 없음(PRD-15-03) |
| `source_kind` 표지 | `API_DIRECT` "공식 자료에서 직접 가져왔어요", `FILE` "공식 파일 기준이에요", `CORPUS_QUOTE` "공식 문서에서 찾은 문장이에요"(쉬운 말, 내부 용어 없음, 후보). 표지는 `{종류 문구} · {dataset}` 형식으로 자료 약칭(출처 표 자료 열과 같은 문자열, 예: `공식 문서 · e약은요 쉬운 설명`)을 포함한다(PRD-12-03) |
| `FILE_ONLY`·`API_ONLY`·`API_SAME` | PJ2-RFP.md 5.1절 (7)의 문구 |
| `API_FAIL`·`API_PAIR_INCOMPLETE` | "실시간 확인을 하지 못함"(파일 기준 답은 그대로) |

- **미확보 사유 코드와 권고 필수 규칙(PRD-11, 2026-11-09, H26·H27)**: 허가사항 원문 미확보는 `missing_reason` 4종(`ABSENT`·`FETCH_FAIL`·`SEARCH_MISS`·`OUT_OF_SCOPE`)으로 구분해 도구가 돌려주고(`SEARCH_MISS`는 `NO_EVIDENCE`와 함께), `finalize`가 위 표의 상수를 렌더한다. **화면·mock·프로토타입의 문구도 이 상수에서만 나온다**(상수에 없는 일반 실패 문구 "원문을 가져오지 못했어요"는 폐기, 사용자 지적). 미확보 항목마다 **약국·약사 확인 권고를 코드가 필수로 붙이고**(접히지 않음, 강조 색 박스) 어느 경우에도 "상호작용 없음·안전"을 암시하지 않는다. 권고 문구 존재와 암시 부재는 `validator`가 코드로 검사한다. 화면 대응표는 `tickets/doc/PRD-11.md` §6.6·§6.7이다.

### 3.5 상태 필드 추가안
RFP-23 §4.4 상태 필드에 더하는 안이다(기존 필드는 그대로). LangGraph에서 reducer가 없는 키는 마지막 값으로 덮어쓴다고 알고 있지만 문서로 확인하지 못했다(10장). 그래서 새 키는 모두 갱신 방식을 적는다. 하네스 상태는 **요청 범위**다(PRD-07-01 A, RFP-35 점검 2026-11-07): 서버는 요청마다 상태를 새로 만들고 요청이 끝나면 버린다. 대화 상태는 브라우저 메모리에만 있고, 되묻기 카드 다음 턴에는 브라우저가 필요한 값(되묻기 선택값, 이미 말한 나이·임신 여부)을 요청 입력 묶음에 실어 보낸다. 앞 턴의 `known_ids`·`harness_events`는 다음 요청으로 넘어가지 않는다. LangGraph의 `thread_id`·메모리 checkpointer를 쓴다면 한 요청 안의 그래프 실행에만 쓴다(RFP-22 §8, 대화 비저장).

| 필드 | 내용 | 갱신 방식 | 쓰는 곳 → 읽는 곳 | 단계 |
|---|---|---|---|---|
| `evidence`(기존) | 항목에 `status`·`flags`·`matched_by`를 더한다(3.4) | 누적(기존 reducer) | 도구 출력 계약 → `validator`, `finalize` | 기준선 |
| `inputs_confirmed` | 사진 추출 결과를 사용자가 확인했는가. **기본값 거짓**, 텍스트 입력 경로만 참으로 둔다(값을 빠뜨리면 닫힘, fail-closed). 음성은 인식 글자를 사용자가 입력창에서 고쳐 전송한 텍스트라 텍스트 경로다(전송이 곧 확인, RFP-35-03) | 입력 변환이 1회 씀 | 입력 변환(PRD-08) → `guardrail_in` | 사진·음성 구현 때 |
| `confirmed_mentions` | 확인 카드에서 사용자가 고친 약 이름 목록 | 입력 변환이 1회 씀. `router`는 쓰지 않는다 | 입력 변환 → `router`(이 값이 있으면 질문 문장에서 약 이름을 다시 뽑지 않음) | 사진·음성 구현 때 |
| `known_ids` | 앞선 도구 결과에 나온 품목기준코드·성분코드(API `D######`과 KIDS 형식 두 체계)·청크 ID | 합집합 reducer | `harnessed_tools` → Pre(H21), `validator`(인용 ID) | 개선 |
| `input_units` | 약 ID별 식별 단위(`product` / `ingredient`) | 사전 병합 reducer | `harnessed_tools` → Pre(H17 보조) | 개선 |
| `harness_events` | 차단·경고·꼬리표 기록(규칙 ID, 동작, 도구, 코드) | 이어 붙임 reducer | Pre/Post → trace span `harness_event`(PJ2-Agent-로깅-전략.md) | 개선 |

- 기록 범위: eval·dev 모드는 전체를 남기고, service 모드는 규칙별 건수만 남긴다(RFP-34-01 A). 질문·약 이름은 남기지 않는다(H13).
- 초안의 전역 `flags`는 항목별 `flags`(3.4)로 옮겼다. `allowed_next`는 만들지 않는다(7.1, 7.2).

### 3.6 에이전트에게 돌려주는 메시지
차단·경고는 모델이 읽고 다음 행동을 고를 수 있게 **짧은 고정 형식**으로 돌려준다(교안 48쪽 "오류 메시지에 다음 행동을 적는다", RFP-22 §4 3번). 차단한 호출도 모델 호출 1회를 쓰므로 남은 호출 수(`left`)를 함께 준다.
```
[HARNESS] rule=H21 code=UNKNOWN_ID action=block tool=check_contraindications left=5
reason=성분코드 D009999 는 앞선 도구 결과에 없습니다
next=identify_drug 로 약을 먼저 찾으세요
```
- 문구는 코드 상수이며 이 표가 원본이다(프롬프트가 아니다). 사용자 화면에는 나가지 않는다.
- 동작 어휘는 `block`·`warn`·`flag`다. 로깅 전략의 어휘(block/rewrite/rollback/append, PJ2-Agent-로깅-전략.md)에는 `warn`·`flag`가 없다. 그래서 RFP-34에서 이 둘을 더하는 안을 낸다(이 문서 9장).

| 코드 | 규칙 | 동작 | 언제 | `next` 문구 | 단계 |
|---|---|---|---|---|---|
| `ARG_SCHEMA` | H21·H8 | block | 인자 형식 오류 | "인자 형식을 고쳐 다시 부르세요(형식: {spec})" | 기준선(도구 함수가 돌려줌) |
| `NO_PRODUCT` | H17 | block | 성분코드로 `search_label`을 부름(출력 계약), 또는 성분 단위 약으로 라벨 도구를 부름(개선 Pre) | "제품명을 모르면 라벨을 찾지 말고 성분 단위로 답하세요" | 기준선(도구 결과) / 개선(Pre) |
| `UNKNOWN_ID` | H21 | block | 앞선 결과에 없는 ID | "identify_drug 로 약을 먼저 찾으세요" | 개선 |
| `REPEAT` | H12 보조 | warn | 같은 도구·같은 인자 재호출 | "같은 호출입니다. 검색어를 바꾸거나 답을 마치세요" | 개선 |

### 4.2 (a) 성분명만 있는 입력의 흐름
근거: [PJ2-약국-약봉투-조사.md](PJ2-약국-약봉투-조사.md) 5장, PRD-08 §3.1, `PJ2-API-응답확인.md` 3장 (3).

| 단계 | 하는 일 | 지점 |
|---|---|---|
| 1 | "이부프로펜"을 `router`가 약 이름으로 뽑는다 | `router` |
| 2 | 모델이 `identify_drug("이부프로펜")`을 부른다. 사전(BE-10)에 상품명 일치가 없어 **성분명 일치**로 성분코드를 돌려준다. 제품 필드는 비우고 `NO_PRODUCT_INFO`를 붙인다 | 도구(출력 계약) |
| 3 | 모델이 `check_contraindications(성분코드, 프로필)`을 부른다. 성분 단위 병용·임부·연령금기를 판정한다(판정은 성분코드 기준). 결과는 항목별 상태다 | 도구 |
| 4 | 모델이 `search_label(성분코드, 주제)`를 부르면 도구가 라벨 대신 `NO_PRODUCT`를 돌려준다. 성분코드에는 품목기준코드가 없어 `get_label_section`은 인자 스키마에서 막힌다 | 도구(출력 계약)·Pre(스키마) |
| 5 | `finalize`가 항목별 문구(`FOUND` 먼저)와 "제품 단위 정보 없음 + 봉투의 제품명을 알려 주시면 더 확인할 수 있어요"를 붙인다. `validator`(최소형)는 안전 단정을 막는다 | 출구 |
- RFP-33-01 B를 고르면 2단계 뒤에 되묻기 카드로 끝내고 3단계를 하지 않는다. C를 고르면 거절 응답이다.
- C1·C1+는 약마다 `search_label`을 고정 순서로 부른다(RFP-23 §5.2). 성분명 입력이면 같은 출력 계약 때문에 `NO_PRODUCT`가 돌아온다. 그래서 C1·C1+에서도 제품 라벨이 새지 않는다.
- 섞인 입력("타이레놀이랑 이부프로펜")은 항목마다 단위가 다르다. 타이레놀은 `product`, 이부프로펜은 `ingredient`다. 제품 일치를 우선하는 규칙은 BE-10에 적는다(이 문서 9장).
- 성분명이 여러 성분(염·복합)으로 풀려 모호하면 기존 되묻기(FR-10, H11)를 따른다. 되묻기 다음 턴은 새 요청이며, 브라우저가 되묻기 선택값을 실어 보낸다(요청 범위 상태, 3.5).

## 7. 자율성과 비교 공정성
### 7.1 장치별 자율성 감소
RFP-25 §4.3은 ReAct에서 LLM이 고르는 것을 "도구를 부를지·어느 도구를·몇 번 부를지·언제 멈출지"로 적었다. 이 문서는 여기에 "어떤 인자로"를 더해 본다. 장치가 이 선택지를 얼마나 줄이는지를 적는다.

| 장치 | 단계 | 줄이는 선택 | 정도 | 이유 |
|---|---|---|---|---|
| 인자 스키마(H8·H21) | 기준선 | 잘못된 인자 | 없음 | 어차피 실패할 호출만 막는다 |
| 출력 계약(H1·H2·H17·H18·H20) | 기준선 | 없음(정보를 정확하게 준다) | 없음 | Observation이 정확해질 뿐 선택은 그대로다. `search_label`의 `NO_PRODUCT`도 도구가 돌려주는 결과다 |
| 데이터 블록·키 제한(H8) | 기준선 | 도구 결과 속 지시를 따를 여지 | 낮음 | 의도한 감소(안전) |
| 확인 선행(H19) | 사진·음성 구현 때 | 확인 전 판정 | 낮음 | 그래프 밖 입력 단계라 평가 세트와 무관하다 |
| ID 존재(H21 `known_ids`) | 개선 | 없는 ID | 낮음 | 환각 ID만 막지만, 오차단하면 정상 흐름이 막힌다(6장 회귀 테스트로 확인) |
| 단위 보조 차단(H17 Pre) | 개선 | 성분 단위에서 라벨 도구 | 중간 | 특정 상태에서 도구 하나를 금지한다 |
| 반복 경고(H12 보조) | 개선 | 없음(경고만 기록) | 낮음 | 실행은 막지 않는다. 막는 쪽은 RFP-33-02 B·C를 고를 때만 |
| 다음 행동 제한(`allowed_next`) | **만들지 않음** | 다음 도구 선택 전체 | 높음 | 사실상 코드가 순서를 정하는 쪽(C1)으로 다가간다. C3 = L2 "확장된 자유도"(RFP-25 §7.4, PJ2-RFP.md 9.5절)와도 충돌한다 |

### 7.2 C1·C1+·C2 비교에 주는 영향
- RFP-23 §5.2는 "도구 함수와 데이터(파일 기준, API 끔), Guardrail·Validator·고정 문구는 같게"라고 정했다. 기준선 장치는 모두 **도구 함수(스키마·출력 계약)와 입구·출구** 안에 있다. 그래서 C1·C1+·C2에 똑같이 적용된다(RFP-33-03 A). 안전 장치인 H17도 출력 계약에 있으므로, 코드 순서로 `search_label`을 부르는 C1·C1+에서도 성분명 입력의 제품 라벨이 새지 않는다. 그래서 하네스가 한 조건에만 유리한 교란은 생기지 않는다.
- PJ2-RFP.md 9.5절의 "같은 도구·같은 모델·같은 Validator로 비교" 문구를 확인했다. 위 구성에서는 바꿀 필요가 없다. API 병기 장치(H9·H20)는 평가에서 API를 끄므로 모든 조건에서 동작하지 않는다.
- **개선 단계 장치**(ID 존재, 단위 보조 차단, 반복 경고)는 AG-13에서 기준선 실패를 본 뒤 C3에 **한 번에 하나씩**(ablation, PJ2-RFP.md 9.5절) 더하고, 개발셋만 본다(RFP-26-04). 이 장치는 선택을 줄이는 쪽이다. 그래서 C2→C3 차이 가운데 L2 확장 몫과 장치 몫을 ablation 기록으로 나눠 보고한다. 차이가 줄어도 실패가 아니라 결과로 그대로 보고한다(RFP-23-03 A).
- 하네스 차단은 차단당한 조건의 호출 수·비용(PJ2-RFP.md 9.4절)만 늘린다. 이 비대칭은 6장의 조건별 차단 건수로 보고한다.
- **규칙은 측정 전에 고정한다**(RFP-23 §5.1, PJ2-RFP.md 9.1절 6번). 기준선에 들어가는 장치 목록(RFP-33-04)과 조건별 적용표를 BE-08 결과 파일에 버전(`harness@v1`)으로 기록한다. 측정 중에 바꾸면 이전 결과와 섞지 않는다.

## 10. 확인하지 못한 것
- LangGraph: `ToolNode`에 도구 호출 전후 래퍼를 넣는 내장 인자가 있는지(Context7로 조회했으나 확인하지 못함, 2026-11-06). `ToolNode`가 도구 결과로 `messages` 밖의 상태 키(`evidence`)를 쓰는 방법. reducer가 없는 키를 마지막 값으로 덮어쓰는지. `ToolNode`가 여러 도구 호출을 병렬로 실행하는지.
- OpenAI API: 모델이 낸 모든 `tool_call_id`에 대응하는 `ToolMessage`가 있어야 하는지(3.2는 하나씩 만드는 쪽으로 정함). `gpt-6-luna`가 병렬 도구 호출을 내는지.
- 데이터: KIDS 병용금기 파일 판정에도 방향성(A쪽 기준)이 있는지. 성분정보 API의 방향성 자체도 관찰일 뿐 명세서로 확인하지 못했다(RFP-32 §9.3 4번). "아스피린"처럼 제품명이자 성분명인 이름이 사전에 있는지. KIDS 성분코드가 염마다 따로 있는지.
- 측정 전: 차단 메시지(3.6)를 받은 모델이 실제로 다음 행동을 고치는지와 차단 빈도. 허가 라벨 문장에서 지시형 패턴이 오탐을 내는 비율. 파일과 API의 연령 문장이 다른 빈도(RFP-32 §9.3 3번은 파일 대 품목 API의 사례 1건이며 내용은 같은 취지다).
- 약사법 시행규칙 제18조·약사법 제28조 제2항 원문은 확인했다([PJ2-약국-약봉투-조사.md](PJ2-약국-약봉투-조사.md) 4장, 2026-11-06). 약 이름이 법정 필수가 아니어서 사진 경로는 약 이름 없음을 정상 경로로 둔다(4장 (c)의 확인 선행 차단은 그대로). 약사법 제24조·제26조·제27조·제27조의2 원문은 읽지 못했다.
