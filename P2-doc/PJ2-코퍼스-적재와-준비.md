## 1. 용어 정의

### 1.1 세 가지를 구분한다

| 용어 | 가리키는 것 | 어디에 있나 | 근거 |
|---|---|---|---|
| **코퍼스(corpus)** | 답변 근거를 찾는 검색 대상인 **문서 청크 모음**. 설명용 문장과 연결 메타(출처·기준일·성분코드)만 담고 **판정 결과는 넣지 않는다** | DB 테이블 `corpus_chunks`(원본), 서버 메모리 `CorpusIndex.chunks`(사본) | `backend/app/db/schema_corpus.sql:1-8`, `:11` |
| **사전(dictionary)** | 약 이름(제품명·성분명) → 품목기준코드·성분코드를 찾는 **식별용 표**. 근거 검색 대상이 아니다 | DB `drug_dict_meta`·`drug_dict_entry`(판 단위), 서버 메모리 `DrugDict` | `backend/app/db/schema_dict.sql:1-12`, `drug_dict_store.py:3` |
| **인덱스(index)** | 코퍼스 청크를 빨리 찾으려고 **서버 프로세스가 메모리에 만드는 구조**(BM25 글자 2-gram 점수표, 층·종류·성분코드·품목기준코드별 번호 집합). 저장되지 않고 매번 만든다 | `CorpusIndex.__post_init__`이 구성 | `backend/app/agent/tools/corpus.py:122-157` |

판정 테이블(`contra_pair`·`pregnancy_contra`·`age_contra`·`caution`)은 코퍼스가 아니다. 금기 여부는 코드가 판정 테이블에서 정확 일치로 정하고, 코퍼스는 그 판정의 **설명·정의·사유 문장**을 찾는 데만 쓴다(`PJ2-DUR-RAG-근거설계.md` 1장 "RAG는 판정하지 않는다").

### 1.2 코퍼스의 구성 (로컬 빌드 산출물 기준)

층(layer)은 근거의 성격이다. 개수는 로컬 `data/mock/corpus/*.jsonl` 줄 수를 직접 센 값이며 합이 원격 적재 수와 같다.

| 층 | 청크 종류 | 출처 | 개수 | 근거 |
|---|---|---|---:|---|
| L1 | 고시 조문·별표 1·3·별표 2(`l1_notice`, `l1_bupyo2_*`) | 고시 「의약품 병용금기 성분 등의 지정에 관한 규정」 | 2,904(`l1_notice.jsonl` 줄 수) | `backend/scripts/build_corpus_l3.py:1-8` |
| L2 | 병용 조합·임부·연령·노인주의 사유(`l2_combo`·`l2_preg`·`l2_age`·`l2_elderly`) | 한국의약품안전관리원 파일 데이터 | 28,390(`l2_chunks.jsonl` 줄 수) | `backend/scripts/build_corpus_l2.py:1-12` |

- 임베딩은 `text-embedding-3-small` 1536차원으로 `corpus_chunks.embedding`(pgvector)에 둔다(`corpus_remote.py:29-30`, RFP-15-05). **서비스 런타임은 지금 벡터 검색을 붙이지 않는다**(BM25 단독, `service.py:64`, `vector_search_fn=None`). 그러므로 서버가 읽는 열에서 `embedding`은 빠진다(`corpus_remote.py:41-46`).
- 용량: 원격 `corpus_chunks` 973.29MB(힙 59.78 + TOAST 542.18 + 인덱스 371.29, 그중 HNSW 364.91MB; 2026-11-11 실측, 재적재 전 값), 재적재 뒤 DB 전체 1,203.4MB(BE-05 §5 2026-11-13). 서버가 읽어 오는 양은 임베딩을 뺀 약 62.5MB(chat-rca §2.2).
- **사용자 답변 코퍼스에 넣지 않는 것**: L5 논문 4편(Cho 2016·제남경 2015·Yang 2015·2019 체계적 문헌고찰). 이유는 일반인에게 임상 판단을 하게 만들고, 고시와 결론이 다를 때 판단할 수 없고, 논문 본문의 이용 조건을 확인하지 않았고, 2015~2016년 규모가 현재 고시와 다르기 때문이다. 설계 결정의 근거(README·평가 리포트·발표)로만 쓴다(`PJ2-DUR-RAG-근거설계.md:30`, `:238-243`). 심평원 「기능과 역할」(L4 제도 해설서)도 "왜 금기인가"의 근거가 아니라 용어·절차 인용에만 쓴다(같은 문서 `:31`).
- 개인 정보: 질문·대화는 코퍼스에 더하지 않는다. "Tool 결과를 코퍼스에 더하기(선택)"도 약품 데이터만 저장하고 사용자·질문과 연결하지 않는 조건이다(`PJ2-DUR-RAG-근거설계.md:183`).

## 2. 생명주기 3단계

| 단계 | 언제·누가 | 하는 일 | 소요 시간 | 근거 |
|---|---|---|---|---|
| ① 오프라인 생성 | 개발 중 필요할 때, 사람이 스크립트 실행(서비스 시작과 무관) | 수집(`collect_*.py`) → 정규화·청크(`build_corpus_l2.py`·`build_corpus_l3.py`) → 임베딩(`embed_corpus.py`) → DB 적재(`load_corpus.py`). 사전은 `build_drug_dict.py` → `be06_dict_load.py` | 원격 적재 6분 40초(68,572행, 2026-11-11), HNSW 생성 367초 | BE-05 완료 조건 `:37`, `:56`(BE-05 §5) |
| ② 저장 | 적재 뒤 상시 | Supabase Postgres. 코퍼스는 `chunk_id`(결정적 해시: 종류 접두 + sha1(키+본문)[:16])가 기본키, 사전은 **판(version) 단위**(내용 해시 `be10-dict-s1-…`, meta 1행 + entry N행) | — | `schema_corpus.sql:13`, `schema_dict.sql:3-6` |
| ③ 런타임 준비 | **서버 프로세스가 첫 `/chat` 요청을 받았을 때** 한 번 | DB를 읽기 전용으로 SELECT → 메모리에 `DrugDict`·`CorpusIndex` 구성 → 모델 객체 생성 | 아래 표(합계 약 29.2초) | `service.py:187-192`, `:83-88`, BE-06-27 A |

### 2.1 ① 오프라인 생성과 원격 쓰기 승인 절차

- 코퍼스 적재(`load_corpus.py`): 기본은 dry-run, 원격은 `--dsn-env … --yes`가 있어야 돈다. 같은 `chunk_id`는 `ON CONFLICT DO NOTHING`이라 재실행해도 중복 0(`load_corpus.py:1-11`, `schema_corpus.sql:3`).
- 사전 적재(`be06_dict_load.py apply --yes`): `--yes`와 승인 파일 `data/mock/review/be06_dict_approved.flag`가 **둘 다** 있어야 쓴다. 한 트랜잭션에서 스키마 → RLS·권한 회수 → entry 삽입 → 행 수 확인 → meta 삽입 → 커밋하고, 같은 판이 이미 완전하면 0행(`be06_dict_load.py:1-18`).
- 승인 파일은 사용자 승인 뒤 **메인이 실행 직전에 만들고 직후에 지운다**(CLAUDE.md 7장 `backend/scripts`, BE-05 §5 2026-11-12 사고 기록 "승인 파일을 미리 두지 않는다").
- 재적재는 서버 재시작이 필요하다: 앱이 시작 때 DB에서 청크를 읽어 메모리 색인을 만들기 때문이다(BE-05 §5 3차 A6 사전 조건 P9). 즉 **DB를 갱신해도 이미 떠 있는 프로세스의 메모리는 옛것이다**.

### 2.2 ③ 런타임 준비의 단계별 시간

측정: 로컬 → 원격 Supabase, 읽기 전용, 2026-11-19, **1회**(chat-rca §2.1). 네트워크에 따라 ±수 초 흔들릴 수 있다.

| import(psycopg·config·app 그래프) | 0.19 + 0.40 | `service.py:68-74` |
| 첫 DB 연결 | 0.99 (이후 0.06) | `service.py:78-81` |

## 3. 준비 단위: 누가 언제 다시 만드는가

### 3.1 질문 답

사용자 질문(2026-11-19): "서버 빌드시에 코퍼스가 생성되는 것이 아니라 첫 요청시에 생성된다는 거니? … 버전을 업할 때마다 즉시 실행하면 그 다음 대응은 빨라지는 건지."

1. **그렇다.** 코퍼스(DB의 `corpus_chunks`) 자체는 ①에서 미리 만들어 DB에 있다. 하지만 서버가 쓰는 **메모리 사본과 인덱스는 빌드 때가 아니라 첫 요청 때 만들어진다.** 앱 시작(lifespan)은 `make_service_runner`로 지연 실행기만 붙이고 접속하지 않으며, 자원 생성은 `LazyGraphRunner._resources()`가 첫 `updates()` 호출에서 한다(`main.py:36`·`:9-10`, `service.py:178-197`, `:206`, BE-06-22 A·BE-06-27 A).
2. **준비의 단위는 "서버 프로세스"다.** 메모리 자원은 `LazyGraphRunner` 객체의 `_base`에 저장되고 그 객체는 프로세스 안에 하나다(`service.py:184-192`). 같은 프로세스 안에서는 한 번 만들면 이후 요청이 빠르다(되묻기 0.016~0.02초, 정상 질문은 모델 호출 시간만큼).
3. **"버전을 올린 직후 한 번 실행(warm-up)하면 그 프로세스의 다음 요청부터 빨라진다"는 맞다.** 조건은 다음과 같다.

| 상황 | 다시 만드나 | 근거 |
|---|---|---|
| 같은 프로세스의 다음 요청 | 아니오(재사용) | `service.py:187-192` 이중 확인 잠금 |
| 만들다 예외가 나면 | 저장되지 않아 **다음 요청이 처음부터 다시** | `service.py:190` 주석 |
| 서버 재시작·배포(버전 업)·`uvicorn --reload` | 예, 프로세스가 새로 생기므로 | `_base`가 프로세스 메모리 |
| 워커 여러 개(`--workers N`) | **워커마다** 각자 만든다(프로세스 간 공유 없음). 지금 Dockerfile은 `--workers 1` | `backend/Dockerfile:35` |
| 인스턴스를 늘림 | 인스턴스마다 | (구조상 필연, 코드에서 확인한 것은 프로세스 단위까지) |
| 쉬다 깨는 서버리스 | 깨어날 때마다(추정) | BE-13이 서버리스를 쓰지 않고 EC2 1대로 정했으므로(`BE-13.md:27`, `:56`) 지금 구성에는 해당 없음 |
| DB에서 코퍼스·사전을 갱신(재적재) | **떠 있는 프로세스는 옛 메모리 그대로**, 재시작해야 반영 | BE-05 §5 P9 |

4. 따라서 "배포 직후 한 번 먼저 요청하는 warm-up"은 그 프로세스(워커 1개) 한 곳에서만 효과가 있다. 워커 수를 늘리면 워커마다 첫 요청이 느려질 수 있다. 확인하지 못한 것: 워커 수·배포 방식의 최종 값(AWS 인스턴스는 아직 미준비, BE-13 `[ ] AWS 인스턴스 준비`, `:41`).
5. warm-up을 **누가 어떻게** 하느냐는 두 가지다. (a) 배포 스크립트가 한 번 `/chat`을 호출 — 코드 변경 없이 가능하지만 LLM·공공 API 호출이 없는 되묻기 질문이 필요하고, 사람이 매번 해야 한다. (b) 서버가 시작 직후 스스로 준비 — C1(§5.2)이며 코드 변경이 필요하다.

### 3.2 같은 프로세스 안의 "이중 요청" 주의

첫 요청이 준비하는 동안 들어온 다른 요청은 같은 잠금에서 기다렸다가 같은 자원을 쓴다(`service.py:189`). 사용자 로그에서 합계가 약 55초가 아니라 27.8초였으므로 둘이 동시에 준비하지 않은 것으로 본다(chat-rca §2.3).

### 5.3 사용자 제안: "스플래시 때 준비 신호"

- 아이디어: 프런트가 스플래시(약 1.3~2초) 중에 백엔드에 "준비 시작" 신호를 보낸다. 지금 구현에서 스플래시 컴포넌트 기본값은 `durationMs = 1300`(`frontend/src/features/chat/Splash.tsx:9`)이고, 지시서의 "2초"와 다르다. 실제 앱의 호출 값은 코드에서 확인하지 못했다(검색에서 개발 미리보기 `ChatPreview.tsx:16`과 시험만 확인).
- 효과(모두 **추정**): 스플래시 시간 + 사용자가 첫 질문을 입력하는 10~20초만큼 준비를 앞당겨, 28초가 약 6~16초로 줄 수 있다. 준비 전체가 약 29초이므로 첫 입력이 일찍 와도 일부는 기다려야 한다. **서버 시작 준비(C1)와 함께일 때** 서버가 쉬다 깨는 배포(서버리스 등)에서 효과가 크고, EC2 1대 상시 구동이라면 C1만으로 충분하고 이 신호의 추가 효과는 작다.
- 설계 조건(제안): `/health`는 지금처럼 즉시 응답을 유지한다(`main.py:49-52`, `be13_health_check.py`가 의존). `/warmup`은 상태를 바꾸지 않고(멱등), 이미 준비 중·완료면 새로 시작하지 않으며, 응답은 준비 상태(`idle`/`warming`/`ready`) 정도만 돌려준다. 로그에는 시작·완료·실패 종류와 소요 초만 남기고 질문·사용자 정보는 보내지 않는다.
- 위험(추정): 게스트가 열 때마다 서버가 DB를 약 90MB 읽는 egress 부담은 프로세스당 1회라 작지만, 프로세스가 이미 준비돼 있으면 0이다. 악의적 반복 호출은 중복 시작 안 함 조건으로 막는다. 브라우저 스플래시 시점에 백엔드가 아직 안 떠 있을 수 있다(콜드 스타트). 새 API 계약이라 `GET /openapi.json`·타입 재생성이 필요하다.

## 7. 평가 영향

- 평가 러너는 서비스 경로(`stream.py`·`LazyGraphRunner`)를 쓰지 않는다. 자기 자원으로 돈다(`evaluation/eval_runner.py:1237-1267`, 사전은 파일 `DrugDict.load()`, `:1258`).
- 그러나 **코퍼스 로더는 공유한다**: 서비스 `service.py:84`와 평가 `eval_runner.py:1259`가 모두 `CorpusIndex.from_db(conn_factory)`를 부른다. 로더가 읽는 열·순서(`ORDER BY chunk_id`)·변환(`row_to_chunk`)이 바뀌면 BM25 결과가 달라질 수 있어, 측정 시작 뒤 고정(RFP 9장, RFP-23 §5.1 사전 고정 원칙)과 충돌할 수 있다.
- 그러므로 C1·C2·C3·C4(배선만)·C7은 평가 영향이 없고, C6(코퍼스 로더 변경)은 청크 dict 동일성 시험이 생기기 전에는 측정 기간에 손대지 않는다. C5(사전 압축)는 평가가 파일 사전을 쓰므로 영향이 없다.
- 서비스는 사전을 DB에서, 평가는 파일에서 읽는다. 두 경로가 같은 판인지는 `be06_dict_load.py verify`(`same_source`)가 확인한다(`BE-06.md:62`).
