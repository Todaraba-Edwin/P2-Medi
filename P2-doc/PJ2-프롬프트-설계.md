## 1. 개요와 읽는 법

### (1) 원칙: 프롬프트는 Guide, 안전은 코드
- 프롬프트·도구 설명은 **Guide(Feedforward)**이고 확률적이라 모델이 무시할 수 있다. 코드 검사·judge는 **Sensor(Feedback)**다(`tickets/doc/RFP-29.md:53-54`).
- 프로젝트 원칙: **반드시 지킬 것은 결정적 Sensor로, 알면 좋은 것은 Guide로 두고, Guide 내용은 Sensor로도 둔다**(`tickets/doc/RFP-29.md:56`). 매트릭스는 "Guide만 있는 행이 없어야 한다"를 목표로 한다(`tickets/doc/RFP-29.md:117`).
- 고정 문구(약사 안내·안전 단정 금지·119)는 **프롬프트가 아니라 코드**가 붙인다(`tickets/agent/AG-08.md:23,27`). 판정·인용·출처 표·배지는 코드 렌더러가 만들고 LLM은 `summary` 문장과 문장별 근거 ID·인용 지정만 낸다(AG-06-01 A, `tickets/agent/AG-06.md:42`).
- 따라서 이 문서의 프롬프트는 **"코드가 지키는 선 안에서 품질(쉬운 말·근거 사용·도구 선택)을 올리는 장치"**다. 프롬프트가 실패해도 안전 문구가 빠지지 않게 설계되어 있는지가 4장의 확인 대상이다. 단, 모든 안전 규칙이 코드로 잡히는 것은 아니다(4장 (2) 위험 목록).

### (2) 이 문서의 목적
1. 개발자가 **어떤 규제가 어느 프롬프트에 들어가고, 어떤 하네스(Sensor)가 그 프롬프트를 받쳐 주는지** 한눈에 알게 한다(2·3·4장).
2. 프롬프트를 바꿀 때 **무엇으로 평가하고 언제 채택하는지**를 미리 정한다(5장, 평가 기준 원본 `P2-doc/PJ2-RFP.md` 9장을 바꾸지 않는 범위).
3. 작성된 프롬프트를 **사용자와 함께 논의하는 형식**(프롬프트 검토 카드)을 정한다(7장).

### (3) LangGraph·LangChain에서 프롬프트의 자리
- 그래프는 LangGraph이고 LangChain 패키지는 노드 안의 모델·도구 부품으로만 쓴다(CLAUDE.md 1장). 기준선 노드 안은 `guardrail_in`·`router`·`model`·`tools`·`validator`·`finalize` 6노드다(`tickets/agent/AG-01.md:23`).
- LLM을 부르는 노드만 프롬프트를 가진다: `router`(엔티티·유형 분류 일부), `model`(ReAct 도구 선택과 최종 답), `validator`(의미 일치 LLM 판정 일부), 개선 단계의 `grade`. `guardrail_in`·`tools`·`finalize`는 코드다.
- 도구 이름·인자·docstring은 모델에 함께 들어가는 **Guide**다(`tickets/doc/RFP-29.md:72`). 도구 설명도 이 문서의 인벤토리에 넣는다.
- 제안: 프롬프트는 LangChain Hub 같은 외부 저장소를 쓰지 않고 `backend/prompts/` 파일에서 읽는다(이미 정한 위치, `backend/prompts/README.md:3`).

## 5. 골든 평가 설계(프롬프트용)

### (1) "골든"의 정의와 지금 상태
| 용어 | 뜻 | 근거 |
|---|---|---|
| 골든 문항 | **사람이 정답을 직접 검증한 문항**. RFP-21 §4.8의 5문항 + 가설검증 TC에서 선별 | `P2-doc/PJ2-RFP.md:496`, `tickets/doc/RFP-21.md:199-206` |
| 위치 | `golden: true`는 시험셋에 있고(TC-15·16·17·21·22·23 포함), 개발셋에는 `dev_golden` 표시가 생겼다(2026-11-17, AG-12-02) | `evaluation/eval_set/README.md:51` |
| 검증 상태 | `golden_verified`가 **모두 `false`**(사람 확인 전) | `evaluation/eval_set/README.md:51` |
| judge 보정 | 개발셋 답변에서 뽑은 사람 라벨 40문항, 일치율 85%·κ 0.6(잠정) | `tickets/doc/RFP-26.md:254-255` |
| 안전 핵심 40 | 시험셋의 응급 10·목록에 없는 약 10·오정보 20(`reliability_core`). 개발셋에는 같은 구성의 `dev_reliability_core` 표시가 생겼다(2026-11-17) | `evaluation/eval_set/README.md:50` |

### (2) 문제: 골든·안전 핵심이 시험셋에만 있다
- 개선 중에는 시험셋을 열람·분석하지 않는다(RFP-26-04, `P2-doc/PJ2-RFP.md:475`, `evaluation/eval_set/README.md:3`).
- 그래서 **지금 정의된 골든 문항과 안전 핵심 40은 프롬프트를 고치는 동안 쓸 수 없다.** 프롬프트를 고치며 돌려 볼 "골든"이 따로 필요하다.
- 개발셋은 시험셋과 같은 구성이므로(`evaluation/eval_set/README.md:34`) 개발셋에도 응급 10·목록에 없는 약 10·오정보 20이 있다. 표시가 없었으나 2026-11-17에 `dev_golden`·`dev_reliability_core`가 생겼다(`mark_dev_subsets.py`, 커밋 `7f10f2d`, 시험셋 미적용).
- 제안(8장 결정 후보 2): 개발셋 안에 **개발 골든**(`dev_golden`, 사람이 정답·기대 응답을 확인한 약 20문항, 분기 유형별로 고르게)과 **개발 안전 핵심**(`dev_reliability_core`, 응급·목록에 없는 약·오정보 40)을 표시한다. 시험셋 골든은 그대로 둔다. 9장 지표·세트 구성은 바꾸지 않고 **개발셋 메타데이터만** 늘린다.

### (3) 프롬프트 변경 평가 단계(제안)
| 단계 | 무엇 | LLM 비용(제 추정) | 언제 |
|---|---|---|---|
| L0 정적 검사 | 프롬프트 파일 프런트매터 필수 칸, 비밀값·실제 사용자 질문 없음(`backend/prompts/README.md:7`), 프롬프트 안 예시에 용량 숫자·고정 문구 사본 없음 | 0 | 모든 변경, pytest |
| L1 하네스 회귀 | 가짜 모델(스크립트 응답)로 하네스 차단 0건·판정 도달(`P2-doc/PJ2-Agent-Harness.md:328,333`). **프롬프트 품질은 보지 않음**, 코드가 프롬프트 변경에 영향받지 않음을 확인 | 0 | 모든 변경 |
| L2 개발 골든 스모크 | 개발 골든 약 20문항 × C2 1회 + judge | 에이전트 약 $0.06 + judge 약 $0.1~0.15 | 모든 프롬프트 변경 |
| L3 개발셋 전체 | 개발셋 150 × C2(또는 C3) + judge, 개발 안전 핵심 40은 3회 | 에이전트 약 $0.5 + 반복 약 $0.25 + judge 약 $1~2 | `P-AG01-model`·`P-AG06-summary` 채택 전 |
| L4 시험셋 | AG-11 기준선(점수만)과 AG-14 최종 재측정에서만 | 9.7절 예산 | 개선 중에는 **하지 않음** |

- 운영 메모(2026-11-17): 지금까지 실제로 돌린 L3는 **judge 없이 코드 채점만**이다(Recap 23). judge 포함 L3는 judge 보정(RFP-26-02·03) 뒤에 한다.
- 비용 추정식: 에이전트 1회 약 $0.0031(9.7절 $4.3 ÷ 1,370회, `P2-doc/PJ2-RFP.md:565`), judge 1회 $0.0046~0.0074(`P2-doc/PJ2-RFP.md:566`). 측정 전 추정이다.

### (4) 무엇을 재나: 지표·하네스 카운트
| 묶음 | 항목 | 정의 원본 |
|---|---|---|
| 최종 답 5지표 | 검색 정확도, 답변 충실도, 오탈자 견고성, 안전 응답률, 금기 판정 정답률 | `P2-doc/PJ2-RFP.md:501-508` |
| 경로 | 필수 도구 호출률, 금지 도구, 순서 위반, 판정 도구 생략, 인용 ID 검증 | `tickets/doc/RFP-26.md:353-362` |
| 신뢰성 | `pass^3`·`pass@3`·불안정 문항·안전 문구 일관성 | `tickets/doc/RFP-26.md:372-380` |
| 하네스 카운트(보조 기록, 새 지표 아님) | 근거 ID 없어 걸러진 문장 수, 글자 불일치 인용 수, 스키마 불일치 수, 고정 문구 누락 수(**0이어야 하며 0이 아니면 코드 버그**), 하네스 차단·경고 건수 | `tickets/agent/AG-06.md:43`, `P2-doc/PJ2-Agent-Harness.md:334`, `tickets/doc/RFP-26.md:379` |
| 프롬프트 전용 관찰(제안, 보조) | `claim_type` 정확도(R-2), `summary` 용량 숫자·`D######` 검출 수 | 이 문서 4장 (2) |

- 보고는 k/n과 Wilson 95% 구간, **칸당 n이 8 이하면 유의성을 주장하지 않는다**(`P2-doc/PJ2-RFP.md:472`). 개발 골든 20문항을 유형별로 나누면 칸당 n이 8 이하가 되므로 L2 결과는 "회귀 경보"로만 읽고 개선 주장에 쓰지 않는다(제안).

### (5) 비교 조건과 동결
- 비교 조건 C0·C1·C1+·C2·C3는 9.5절 그대로다(`P2-doc/PJ2-RFP.md:528-536`). 프롬프트 개선의 비교는 **같은 세트·같은 judge·같은 도구에서 프롬프트 하나만** 바꾼다("한 번에 하나", `P2-doc/PJ2-Agent-로깅-전략.md:260`).
- 측정 기간(AG-11~AG-14)에는 세트 해시·judge 모델·루브릭·C1 규칙·지표·모델 ID·호출 상한을 동결하고, 에이전트 쪽 프롬프트 수정은 `prompt_version`을 기록하고 개발셋으로만 확인한다(`P2-doc/PJ2-RFP.md:548`).
- **judge 프롬프트·모델 ID는 평가 기간 중 고정**(RFP-26-01, `tickets/doc/RFP-26.md:239`). 사람 보정에서 루브릭을 고치면 다른 문항으로 재측정한다(`:256`).
- 제안: C1의 요약 프롬프트(`P-AG16-c1summary`)는 "C1 규칙" 동결에 포함해 **기준선 버전에 고정**한다. C3 개선에서 `P-AG06-summary`를 바꿔도 C1 쪽은 바꾸지 않아야 C2↔C3 비교가 "프롬프트만 바뀜"이 된다. C0 프롬프트도 같은 이유로 고정한다.

### (6) 채택 기준(제안)
9장 지표·목표를 바꾸지 않는 **운영 규칙 제안**이다. 결정이 필요하면 8장 후보로 올린다.

| # | 기준 | 판정 |
|---|---|---|
| 1 | L0·L1 통과, 고정 문구 누락 0 | 필수 |
| 2 | 개발 안전 핵심 40의 `pass^3`가 이전 채택 버전보다 **내려가면 채택하지 않는다**(시험셋 안전 핵심 40 대신 개발셋 대응 문항, 5장 (2)) | 필수(L3 대상 프롬프트) |
| 3 | 금기 판정 정답률(개발셋) 하락 없음 | 필수 |
| 4 | 걸러진 문장 수·글자 불일치 인용 수가 늘면 이유를 카드에 적는다 | 기록 |
| 5 | 개선 주장은 L3 결과로만, k/n·Wilson 구간으로 쓰고 칸당 n 8 이하면 유의성 주장 없음 | 보고 규칙 |
| 6 | 사용자가 검토 카드를 승인(7장) | 8장 결정 후보 3 |

## 7. 논의 절차
1. **초안 작성**: 담당 티켓 작업 중 프롬프트 초안을 `status: draft`로 쓴다(기준선에 연결하지 않음).
2. **프롬프트 검토 카드** 작성: 아래 다섯 칸을 한 장으로 사용자에게 보인다.

| 칸 | 내용 |
|---|---|
| 초안 전문 | 프롬프트 본문 그대로 |
| 적용 규제·H 연결 | 3장 카드의 H 표(Guide 문장이 본문 몇째 줄인지 표시) |
| 예상 실패 5개 | 4장 (2) 위험 목록에서 이 프롬프트에 해당하는 것 + 새로 예상한 것 |
| 골든 결과 | L0·L1 결과, L2(개발 골든) k/n, 해당 시 L3 |
| 묻는 것 | 결정 번호(아래 3) |

3. **결정 번호**: 논의할 선택은 **해당 티켓 결정 현황**에 `AG-06-nn`·`AG-01-nn`처럼 올린다(CLAUDE.md 5장, 이 문서는 번호를 만들지 않는다).
4. **승인 전에는 기준선에 넣지 않는다.** 승인되면 `status: adopted`, `prompt_set` 버전을 올리고 카드에 결과를 적는다.
5. 측정 기간에 바꾸는 프롬프트는 5장 (5) 동결 규칙을 따른다.
