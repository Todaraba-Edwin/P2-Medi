## 1. 결론

"근거 있는 RAG"는 자료를 많이 넣는 것이 아니라, **청크마다 근거의 성격(계층)을 붙이고, 답변 문장의 종류마다 쓸 수 있는 계층을 정해 Validator가 검사하는 것**이다.

- 금기 **여부**는 지금처럼 정확 일치(L0)로만 말한다. RAG는 판정하지 않는다.
- 그래도 retrieval은 판정 경로 안에서 빠질 수 없는 일을 한다. **판정의 입력(약 이름 → 성분코드)을 찾고, 성분을 특정하지 않은 열린 질문에서 후보를 찾아 규칙으로 검증하게 한다**(7장). retrieval을 끄면 판정 자체가 실행되지 않는 질문이 생기고, 이것을 수치로 보인다.
- RAG는 **정의(L1)·사유(L2)·품목 주의(L3)·절차 용어(L4)**를 찾아 문장마다 출처를 붙인다.
- 논문(L5)은 사용자 답변 코퍼스에 넣지 않는다. 대신 "금기 목록에 없음 ≠ 안전" 같은 **설계 결정의 근거**로 README·평가 리포트·발표에 쓴다.
- 심평원 「기능과 역할」은 판단하신 대로 성격이 다르다. 제도·운영 해설서(L4)라 "왜 금기인가"의 근거가 아니며, 용어·절차 설명에만 쪽을 밝혀 인용한다(RFP-17 결정 13·14 유지).

## 2. 지금 가진 자료의 성격

| 자료 | 위치 | 성격 | 답하는 질문 |
|---|---|---|---|
| 병용금기 JSON (KIDS, 파일 기준일 2026-07-31) | `data/` | 판정 데이터 + 사유 문장 | 이 두 성분이 병용금기인가, 사유는 무엇인가 |
| 임부금기 CSV (KIDS, 기준일 2026-07-21) | `data/` | 판정 데이터 + 상세정보 | 이 성분이 임부금기인가, 몇 등급인가 |
| DUR 품목·성분정보 OpenAPI (식약처) | 키 보유 | 판정 데이터(연령금기 1차 소스) | 이 성분이 특정 연령에 금기인가 |
| 고시 「의약품 병용금기 성분 등의 지정에 관한 규정」 (제2026-52호) | `P2-doc/` | 규범(법적 근거) | 금기·등급의 공식 정의는 무엇인가 |
| e약은요 API (식약처) | 키 보유 | 품목 설명(일반인용 요약) | 이 제품은 몇 세부터, 무엇을 주의하는가 |
| 심평원 「기능과 역할」 2021~2026 | `data/` (git 제외) | 제도·운영 해설서 | DUR은 누가 어떻게 운영하는가, M등급·사유 코드는 무엇인가 |

2026년판 확인 결과(PDF 836쪽): 목차가 건강보험제도, 국민건강보험법령 해설, 심평원 업무 순이다. DUR은 제4부 3장 "의약품안전사용서비스(DUR)"(PDF 659~668쪽)뿐이고, 내용은 참여 현황, 기관별 역할(표4.3-3), 법적 근거, 점검 절차(표4.3-4), 등급별 사유 기재(표4.3-5), 사유 코드(표4.3-6)다. 금기 성분이 왜 지정되었는지는 다루지 않는다.

**비어 있는 층**: 제품 단위의 "왜·무엇을 주의하는가"를 담은 **허가사항(사용상의 주의사항) 원문**이 없다. e약은요는 일반의약품 중심의 요약이라 전문의약품(예: 메토트렉세이트, 알렌드로네이트)이 빠질 수 있다(가설검증 8.2).

## 3. 근거 계층

| 계층 | 이름 | 자료 | 법적·신뢰 지위 | RAG 역할 | 보유 |
|---|---|---|---|---|---|
| **L0** | 판정 데이터 | 병용금기 JSON, 임부금기 CSV, DUR API | 고시를 구조화한 공식 데이터 | **RAG 아님.** 성분코드 정확 일치 조회 | 보유 |
| **L1** | 규범 | 고시 조문·별표, (후보) 약사법 제23조의2·23조의3 | 법령·고시 | 정의·법적 근거 인용 | 고시 보유 |
| **L2** | 금기 사유 | JSON `금기사유`(고유 370), CSV `상세정보`(고유 1,073) | 공식 데이터의 문장 필드 | 사유·등급 조건 설명 | 보유 |
| **L3** | 품목 허가사항 | e약은요 문장 필드, 허가정보 API 허가 상세의 효능·용법·주의사항 본문(XML) | 식약처 허가사항 | 제품별 사용 연령·상호작용·주의 문장 인용 | e약은요 보유, 허가정보 API 승인 |
| **L4** | 제도·운영 해설 | 심평원 「기능과 역할」 DUR 장 | 기관 해설서 | 용어·절차 설명, 쪽 인용만 | 보유(인용만) |
| **L5** | 학술 근거 | 국내 DUR 연구 논문 | 학술 문헌 | **사용자 답변에 쓰지 않음.** 설계 근거·한계 서술 | 9장 |

계층은 위로 갈수록 "판정"에 가깝고 아래로 갈수록 "설명·배경"에 가깝다. 같은 내용을 두 계층이 말할 때는 위 계층이 이긴다. 다만 L0와 L1이 어긋나면 한쪽을 확정하지 않고 둘 다 보인다(RFP-17 결정 3).

## 4. 주장 유형별 허용 근거

답변의 문장을 아래 유형으로 나누고, 유형마다 인용할 수 있는 계층을 정한다. Validator(FR-05)는 문장의 인용 청크 계층이 허용 목록에 없으면 그 문장을 지우거나 "확인할 수 없음"으로 바꾼다.

| 주장 유형 | 예시 문장 | 허용 계층 | 금지 |
|---|---|---|---|
| 금기 여부 | "두 성분은 병용금기로 등록되어 있습니다" | L0만 | L1~L5에서 금기 여부를 추론 |
| 등급 정의 | "2등급은 원칙적으로 사용금지이나 예외가 있습니다" | L1 (고시 제3조 제3호) | 요약·의역 |
| 금기 사유 | "대사가 감소해 독성이 증가할 수 있습니다" | L2 우선, L3 보조 | 모델 지식으로 기전 설명 |
| 제품 주의 | "이 제품은 만 12세 이상이 복용합니다" | L3 | L5 |
| 용어·절차 | "M등급은 상병에 따라 1등급 또는 2등급입니다" | L4 (판·표·쪽 명시) | 사유 코드 M과 혼동 |
| 한계·고지 | "금기 목록에 없다는 것이 안전하다는 뜻은 아닙니다" | 코드 고정 문구 (FR-06) | 검색 결과로 생성 |
| 기준일 | "자료 기준일 2026-07-21"(임부금기 파일 예. 기준일은 파일별) | 메타데이터 | 추정 |

이 표가 포트폴리오에서 보여 줄 핵심이다. "RAG가 근거를 찾는다"를 넘어서, **어떤 문장이 어떤 근거로만 말해질 수 있는지를 코드로 강제**한다.

### (2) 계층별 청크 단위

| 계층 | 청크 단위 | 이유 |
|---|---|---|
| L1 고시 조문 | 조·호·목 하나 + 상위 조 제목을 앞에 붙임 | 정의는 목 단위로 인용된다 |
| L1 별표 | 표 한 행 + 열 이름 반복 (파서 시험 통과 뒤, 결정 12) | 행이 곧 하나의 규칙이다 |
| L2 병용 사유 | (성분A, 성분B, 금기사유, 고시번호) 고유 조합. 문장은 메타데이터로 다시 만든다 | 제품 쌍 512,464건은 반복이다(결정 6, BE-05 재결정) |
| L2 임부 상세 | (성분, 금기등급, 상세정보, 고시번호) 고유 조합 | M 처리 규칙상 원문 그대로 인용해야 한다 |
| L3 허가사항 | 항목(금기·신중투여·상호작용·임부·소아·고령자) → 문장. 문장을 찾고 항목 전체를 함께 넘김 | 긴 문서에서 관련 문장만 찾는다(H16) |
| L4 해설서 | 색인하지 않음. 용어 3개(M등급, 사유 코드, 점검 단계)를 판·표·쪽과 함께 고정 용어집으로 둠 | 이용 조건 미확인(결정 14) |

## 6. 검색 흐름

```
질문 → Router(엔티티·주장 유형) → L0 정확 일치(성분코드) ─┐
                                                          ├→ 메타데이터 사전 필터(ingr_codes, layer, notice_no)
                                                          │     → BM25 + 임베딩 하이브리드 → 재정렬
                                                          └→ 답변 생성(문장마다 인용) → Validator(4장 허용 검사, 원문 대조)
```

- **사전 필터가 먼저다.** L0에서 확정한 성분코드·성분명으로 검색 범위를 좁힌 뒤에만 의미 검색을 한다. 성분이 다른 청크가 섞이는 것을 막는다.
- **BM25를 함께 쓴다.** 성분명(영문·한글)과 고시 조항 번호는 정확한 문자열이라 키워드 검색이 강하다.
- **L0가 "목록에 없음"이면** 성분명 일치(같은 성분의 다른 코드·제형)와 L3 허가사항 문장으로 보완 근거를 찾는다(H13). 판정은 바꾸지 않고 "참고 정보"로만 보인다.

### (1) 청크 사이 연관성: 멀티홉 이슈 예고

top-K 검색은 질의와 가까운 청크를 각각 가져올 뿐, 청크 사이의 관계(같은 성분쌍, 같은 고시, 정의와 적용)를 모른다. 답이 여러 청크에 나뉘어 있으면 일부가 빠지거나 다른 성분의 청크가 섞인다. 이 프로젝트에서 그런 질문이 생기는 곳은 아래와 같다.

| # | 지점 | 나뉜 근거 | 예 |
|---|---|---|---|
| 1 | 등급 M 설명 | 상세정보(L2) → 등급 정의(L1 제3조) → M 설명(L4) | TC-21 |
| 2 | 같은 성분의 다른 제형 | L0 여러 행(정제·주사제 코드) + 고시 사유(L2) + 라벨 문장(L3) | TC-15 |
| 3 | 약 N개의 쌍별 사유 요약 | 쌍마다 L2 청크, 합쳐서 요약 | TC-13, 18, 22 |
| 4 | 열린 질문 | 후보 검색 → 후보별 판정(2홉) | TC-23, 역할 B |
| 5 | 조문 참조 | "별표 1에 따른", "제8조상 별도 공고"의 참조 대상 | 고시 L1 |
| 6 | 표가 청크 경계를 넘음 | 별표 행과 열 이름·비고 | 별표 1·2·3 |

**대응 원칙: LLM이 스스로 연쇄 검색하게 두지 않고, 연결을 코드와 메타데이터가 만든다.**

- **주장 유형별 분해**: Router가 질문에 필요한 주장 유형(4장 표)을 정하고, 유형마다 허용 계층 필터로 따로 검색한다. 한 번의 top-K에 모든 근거를 기대하지 않는다.
- **키 조인**: 청크에 `chunk_id`, `parent_id`(조→호→목, 표→행), `refs`(참조하는 조문·별표의 `chunk_id`), `pair_id`(성분쌍)를 둔다. 검색으로 찾은 청크의 `parent_id`·`refs`와 같은 `pair_id`·`ingr_codes`의 청크를 코드가 가져와 붙인다. 임베딩 유사도로 연관성을 추측하지 않는다.
- **증거 묶음**: 코드가 주장 유형별 결과를 묶음으로 만들고 LLM에는 묶음만 준다. 쌍별 사유 요약은 쌍마다 따로 요약한 뒤 합친다(map-reduce).
- **검증**: Validator가 문장마다 허용 계층의 청크를 인용했는지(기존)와, 질문에 필요한 주장 유형이 빠지지 않았는지(누락)를 본다.
- **한도**: 홉은 2회까지(역할 B의 후보 검색 → 판정). 그래프 RAG와 다단계 에이전트 루프는 3주 범위 밖이다.

**평가**: 평가 세트에 멀티홉 문항(위 1~4)을 따로 두고, "근거 묶음 Recall"(정답에 필요한 청크가 모두 묶음에 들어갔는지, 하나라도 빠지면 실패)을 보조 지표로 잰다. 단일 top-K와 주장 유형별 분해 검색을 비교한다(가설 H17). 구현 전에 샘플 질의 20개로 단일 top-K의 근거 누락률을 먼저 재서, 분해 검색이 필요한지 숫자로 보인다(AG-03).

## 7. Retrieval이 반드시 하는 일

판정을 규칙이 하더라도, 규칙은 **성분코드가 주어져야** 돌아간다. 사용자는 성분코드를 말하지 않는다. retrieval이 그 사이를 채운다. 아래 A·B는 retrieval이 없으면 판정이 실행되지 않고, C는 retrieval이 없으면 설명이 고정 문구로 줄어든다.

| 역할 | 질문 예 | retrieval이 하는 일 | 규칙이 하는 일 | retrieval을 끄면 |
|---|---|---|---|---|
| **A. 판정 입력 찾기** (entity linking) | "어린이 부루펜이랑 타이래놀" | 제품명·별칭·오탈자를 제품·성분 사전에서 검색해 성분코드 후보 top-k를 낸다 | 후보 중 확정된 성분코드로 L0 정확 일치 | 사전에 정확히 같은 이름이 없으면 판정 불가 |
| **B. 열린 질문의 후보 찾기** (retrieve-then-verify) | "임신 중에 피해야 하는 진통제 성분은?", "QT가 길어지는 약끼리 같이 먹으면 안 되는 조합은?" | L2 사유·상세정보와 L3 효능 문장을 의미 검색해 해당 성분 후보를 모은다 | 후보마다 L0로 금기 여부·등급을 확인하고, 확인된 것만 답에 남긴다 | 성분이 질문에 없으니 판정할 대상이 없다 |
| **C. 근거 설명** | "왜 같이 먹으면 안 돼?" | L1·L2·L3 청크를 찾아 문장마다 인용 | 4장 허용 매트릭스로 인용 계층 검사 | 고정 문구만 남는다 |
| **D. 검색 보정 루프** (agentic) | 검색 결과 점수가 낮거나 후보가 0개 | 에이전트가 질의를 다시 쓰거나(성분명 영문 변환, 효능군 일반화) 계층을 넓혀 다시 검색 | 재검색 횟수 상한 | 첫 검색 실패가 곧 "근거 없음"이 된다 |

### (1) A. 판정 입력 찾기

- **색인 대상**: 임부금기 CSV의 제품명·성분명(18,804행), 병용금기 JSON의 제품명·성분명(구분 A·B), e약은요 제품명. 제품 하나가 한 문서이고 메타데이터에 성분코드를 둔다.
- **검색 방식**: 문자 n-gram BM25(오탈자·띄어쓰기)와 임베딩(별칭·설명형 표현)을 섞는다. "타이래놀"처럼 한 글자가 틀린 경우는 n-gram이, "빨간 기침약 시럽"처럼 설명형은 임베딩이 맡는다.
- **확정 규칙**: top-1 점수가 기준 이상이고 2위와 차이가 충분하면 확정한다. 아니면 후보 2~3개를 보여 주고 질문 1개로 확인한다(FR-07, 가설검증 TC-05). 확정되지 않은 후보로는 판정하지 않는다.
- **지표**: 성분코드 Recall@1·Recall@5, 확인 질문 비율.

### (2) B. 열린 질문의 후보 찾기

- **흐름**: 질문 → L2·L3 의미 검색(효능군·사유 표현) → 후보 성분 집합 → **L0로 하나씩 검증** → 검증된 것만 답변.
- **안전 장치**: 검색으로 찾은 후보는 전체 목록이 아니다. 답변에 "찾은 항목이며 전체 목록이 아님"을 코드로 붙이고, 검증에 실패한 후보는 버린다. 검색이 금기를 만들지 못하고, 규칙이 확인한 것만 말한다.
- **정답 세트를 데이터에서 자동으로 만든다**: L0가 정답을 갖고 있다. 예를 들어 "임부금기 1등급 + 효능이 진통인 성분"의 정답 집합은 CSV와 e약은요 효능 필드로 만들 수 있다. 사람이 라벨링하지 않아도 Context Recall을 잴 수 있다.
- **지표**: 후보 Recall@k(정답 집합 대비), 검증 뒤 정밀도(규칙 통과 비율).

### (3) 이 설계가 포트폴리오에서 보여 주는 것

- **retrieval 없이는 판정이 시작되지 않는다**(A·B). retrieval이 근거 설명을 꾸미는 부가 기능이 아니라 판정 경로의 앞단이다.
- **retrieval의 오류가 금기 판정을 오염시키지 않는다.** retrieval은 후보만 내고 확정은 규칙이 한다. 의료 도메인에서 RAG를 쓰는 안전한 방식으로 설명할 수 있다.
- **같은 세트로 retrieval을 끄고 켜서** 판정 실행률·정답률이 어떻게 달라지는지 수치로 보인다(10장).

## 8. 수집할 자료와 API 이중 경로

### (1) 원칙: API는 Tool이면서 수집 경로다

같은 공공 API를 두 갈래로 쓴다.

| 경로 | 언제 | 하는 일 | Agent-RAG에서의 의미 |
|---|---|---|---|
| **수집 (오프라인 배치)** | 개발 중 1회, 필요하면 재수집 | API를 페이지 단위로 돌려 원본 JSON을 `data/` 스냅샷으로 저장 → 정규화 → 청크·사전 색인 | **retrieval 코퍼스**가 된다. API가 막혀도 RAG 실습·평가를 로컬에서 반복할 수 있다 |
| **Tool (런타임)** | 사용자 질문 때 | 사전에서 확정한 제품을 실시간 조회, 조회 시각 기록 | **Agent의 도구 선택**이 된다. 스냅샷 기준일 이후 변경을 확인한다 |

- **실습 부담을 줄이는 지점**: API를 다루는 코드는 "수집 스크립트 1개 + Tool 래퍼 1개"로 한정한다. RAG 개발·평가는 수집된 스냅샷으로만 한다.
- **두 결과가 다르면**: 스냅샷(기준일)과 Tool 결과(조회 시각)를 함께 보이고 한쪽을 확정하지 않는다(RFP-17 결정 3).
- **Tool 결과를 코퍼스에 더하기(선택)**: 런타임 Tool로 받은 공개 약품 데이터를 수집 형식으로 저장해 다음 검색에 쓴다. 약품 데이터만 저장하고 사용자·질문과 연결하지 않는다(RFP 7장 개인정보).

**사용자 답변 코퍼스에 넣지 않는 이유**
- 일반인에게 임상 판단을 하게 만든다(RFP 4장 제외 범위).
- 고시와 결론이 다를 때 일반인이 판단할 수 없다.
- 논문 본문의 이용 조건을 확인하지 않았다.
- 2015~2016년 연구라 2026년 고시 규모(성분코드 기준 약 23,619쌍)와 다르다. 현재 포괄률로 인용하면 안 되고, "규칙 목록은 상호작용 전부가 아니다"라는 구조적 한계의 근거로만 쓴다.

## 10. 평가 연결

| 지표 | 측정 | 새로 생기는 것 |
|---|---|---|
| Context Precision·Recall (Ragas) | 계층별로 따로 낸다 (L1, L2, L3) | 어느 계층의 검색이 약한지 보인다 |
| Faithfulness (Ragas) | 기존과 같음 | |
| **근거 계층 일치율** | 답변 문장 중 4장 허용 계층의 청크를 인용한 문장 비율 | 이 설계의 효과를 직접 재는 지표 (보조 지표로 제안) |
| 금기 판정 정답률 | L0만으로 측정 (RFP 9장) | 변화 없음 |
| **성분코드 Recall@1·@5** | 7장 A. 약 이름 질문에서 정답 성분코드가 후보에 드는 비율 | retrieval이 판정 입력을 찾는지 |
| **열린 질문 후보 Recall@k** | 7장 B. L0로 자동 생성한 정답 집합 대비 | 사람 라벨링 없이 retrieval을 측정 |
| **판정 실행률** | 질문 중 L0 판정까지 도달한 비율 | retrieval 끄기/켜기 비교의 핵심 수치 |

**retrieval 끄기/켜기**: 같은 세트에서 A·B를 끄면(정확한 이름 일치만 허용) 판정 실행률이 얼마나 떨어지는지를 먼저 보인다. 이것이 "retrieval이 실제로 일을 한다"의 가장 직접적인 증거다.

비교 실험(가설검증 6장)에 계층을 더해 **L0만 → L0+L1·L2 → L0+L1·L2·L3** 순서로 쌓으면, 각 계층이 실제로 하는 일을 수치로 보일 수 있다.
