# PJ2-RFP · MediAgent

> AI Agent(Agentic RAG) 부트캠프 3주 프로젝트 제품요구서 · fastcampus · 박영찬

## 1. 개요
| 항목 | 내용 |
|---|---|
| 프로젝트 | MediAgent: 공공 보건·의약품 데이터 기반 Agentic RAG 에이전트 |
| 기간 | 3주 (설계 → 구현 → 평가) |
| 형태 | 개인 프로젝트 (팀이면 역할 표 추가) |
| 한 줄 정의 | 사실은 공공 API·문서에서 가져오고, LLM은 설명과 종합만 맡는 근거 기반 질의응답 에이전트 |
| 프로젝트 성격 | 상용 서비스가 아니라 **취업 포트폴리오**다. Agent-RAG를 활용한 AX(AI 전환) 경험, 곧 에이전트를 직접 설계·구현·평가하고 수치로 개선을 보여 주는 것이 핵심 목표다. 의약품 도메인은 그 과정을 다루기 위한 소재다 |
| 아이디어 근거 | 원스글로벌 Dr.DI·ConnectDI 같은 의약품 정보 서비스가 이미 운영되고 의약정보 AI의 환각 검증이 쟁점이 된 것은, MediAgent 아이디어에 가능성이 있음을 확인해 주는 사례다(발표 자료 9~11쪽). 이 프로젝트는 Dr.DI를 재현하거나 같은 수준의 제품을 만들지 않는다. 같은 문제를 Agent-RAG의 대상 도메인으로 삼아, 3주·1인 개발이라는 조건에 맞춘 유사한 축소판을 만들고 취업 포트폴리오에 담는다. 성능 수치는 비교하지 않는다 |
| 주 사용자 | 일반인(비의료인) |
| 확장 사용자 | 의료인·약사도 쓸 수 있다. 같은 답변의 근거 상세(성분코드·고시 조항·등급·기준일)를 펼쳐 볼 수 있게 할 뿐, 전문가 전용 기능(처방 점검, 환자 기록)은 두지 않는다 |
| 온보딩·계정 (확장) | 처음 시작할 때 온보딩으로 프로필(연령대, 임신 여부, 복용 중인 약 등 선택 입력)을 저장 동의와 함께 받고, Apple·Naver·Kakao·Google 계정으로 로그인해 프로필을 저장한다. 응급 상황에서는 로그인·온보딩 없이 바로 질문할 수 있어야 한다(게스트 사용) |
| 사용 장면 | 임산부·영유아·아동·고령자(만성질환 약을 여러 개 복용)가 있는 집에서 응급 상황이나 평소에, 집에 있는 상비·응급 의약품과 보유 의약품을 먹기 전에 병용·연령·임부 금기와 중복·용량 주의를 스스로 확인한다. 전문가의 판단을 바로 받기 어려운 때 근거를 확인하는 용도다 |
| 목적 | 의약품을 잘못 조합하거나 임산부·영유아에게 맞지 않게 먹는 오남용을 막는다. 복용 여부와 용량은 정해 주지 않고, 금기·주의 정보와 출처를 이해하기 쉬운 말로 알려 준다. 책임을 지지 않는 대신 모든 답변에 근거를 달고, 자세한 확인은 근처 약국·약사에게 하도록 안내한다 |

## 2. 문제 정의
- **최신성**: 허가 사항·금기 기준이 바뀌어도 LLM 내부 지식은 반영되지 않음
- **추적성**: 의료·보건 답변은 출처(데이터·조항)를 댈 수 있어야 함
- **데이터 분산**: 약품 정보는 API, 금기 정보는 API·파일 데이터·고시(PDF)에 흩어져 있음
- **입력 불확실성**: 오탈자, 범위 밖 질문, 잘못된 전제 질문
- **오남용 위험**: 일반인은 임산부·아동에게 응급·상비 의약품을 먹이거나 보유 의약품을 함께 먹을 때 병용·연령·임부 금기를 확인하기 어려움

## 3. 목표
1. 질문 → 도구 선택 → 근거 조회 → 출처가 붙은 답변까지 끝단 동작
2. 정형(API·파일 데이터)·비정형(PDF) 하이브리드 검색
3. 환각 방지 장치(근거 고정·검증·안전 응답) 구현
4. 직접 측정한 평가 수치로 개선 전후 비교
5. Dr.DI 등 기존 서비스로 확인되는 아이디어의 가능성을, 3주·1인 개발 규모의 유사한 축소판으로 Agent-RAG에 적용해 보고 한계를 정리해 포트폴리오로 남김

## 4. 범위
| 포함 | 제외 |
|---|---|
| **핵심(필수)**: 약품 정보 조회, 병용·연령·임부 금기 확인 (복용 전 자가 확인) | 진단, 처방, 복용량 결정 (공식 기준값을 인용해 보여 주는 것은 포함) |
| **확장(권장)**: 성분 중복 확인(같은 성분을 가진 제품끼리 병용, 제품명→성분코드 매핑으로 비교)과 DUR의 효능군 중복·용량·투여기간 주의 정보 조회(용량주의약물 CSV 확보) | 진료·처방 이력 등 의료기록 처리. 사용자가 직접 입력한 프로필만 동의를 받아 저장하고, 질문·대화 내용은 저장하지 않는다 |
| **확장(권장)**: 온보딩 프로필 입력, 소셜 로그인(Apple·Naver·Kakao·Google)과 프로필 저장, DB·인증 서비스로 Supabase 무료 플랜 검토 | |
| **확장(권장)**: 수유부·노인 주의. 파일 데이터가 확보되어 있다(수유부주의 CSV, 심평원 노인주의 품목리스트). 사유 문장이 없는 경우가 있어 판정 위주다 | 전문가 전용 기능(처방 점검, 환자 단위 기록), 요양기관 DUR 점검의 대체 |
| 쉬운 요약 + 펼치는 근거 상세 구조의 답변 | 상용 서비스 요소(과금, 약국 검색, 운영 모니터링) |
| | 대규모 문서 전수 수집 (핵심 PDF 소수로 시작) |

> 3주 범위 제어: 핵심 항목을 먼저 끝내고, 확장 항목은 핵심의 주차 완료 기준을 채운 뒤에 한다. 주차 완료 기준에 미달하면 확장 항목부터 줄이며, 줄이는 순서는 Apple·Naver 로그인 → Kakao·Google 로그인 → 프로필 저장(대화 중 입력으로 대체) → FR-07 오탈자 보정 → 열린 질문 retrieval(AG-15) → 수유부·노인 주의 → 중복·용량 순서다. 이 프로젝트가 증명하려는 것은 의약품 지식의 양이나 서비스 기능의 수가 아니라 Agent-RAG의 설계·구현·평가이므로, 어떤 확장이 있어도 Router, 도구 선택, 근거 고정, Validator, 평가 수치는 줄이지 않는다.

> "국가건강검진 대상·주기 안내"와 "보건사업 자격 요건 안내"는 2026-10-31에 포함 범위에서 제거했다. 이 프로젝트는 일반인이 의약품의 병용·연령·임부 금기를 스스로 확인하는 데 집중한다. 보건사업 항목은 초기 작성 때 발표 자료(`MediAgent 포트폴리오 발표.pdf` 3·4쪽)에서 넘어온 잔재이고, 검진 항목은 의약품 병용금기 컨셉에 필요하지 않아 뺐다.

### 5.1 Retrieval 대상 파일의 접근과 검색

> 2026-10-31 작성. 설계 배경은 `P2-doc/PJ2-DUR-RAG-근거설계.md` 3·7·8장이다. 표의 행 수·고유 값 수는 2026-10-31 `data/` 파일을 직접 열어 집계한 값이다. 2026-10-31 사용자가 설계 문서 12장의 결정을 권고대로 확정했다(채택 7건, 후순위 2건). 후순위 결정은 일정 여유가 생길 때 다시 본다.

**원칙**: 금기 판정은 성분코드 정확 일치로 하고(RFP-17 결정 1), retrieval은 판정의 입력을 찾고(A), 열린 질문의 후보를 찾고(B), 근거를 설명한다(C). 런타임은 `data/` 원본을 직접 읽지 않고, 적재 단계가 만든 세 저장소만 읽는다.

#### (2) 접근 경로: 원본 → 적재 → 세 저장소

```
data/ (원본, git 제외, CP949·대용량)
   └─ 적재 스크립트 (①=BE-09, ②=BE-10, ③=BE-05, 1회·재실행 가능)
        ├─ ① 판정 테이블   : 로컬 DB. 금기 종류별 테이블, 키 = 성분코드(쌍), 값 = 등급·연령조건·고시번호·기준일
        ├─ ② 제품·성분 사전 : 제품명·성분명(영문·한글)·별칭 → 성분코드. BM25(문자 n-gram) + 임베딩 색인
        └─ ③ 근거 코퍼스   : 사유·상세정보·고시 조문·e약은요 문장. Vector DB + BM25, 청크마다 메타데이터
런타임 Tool은 ①②③만 읽는다. data/ 원본은 런타임에 열지 않는다.
```

- **스트리밍**: 병용금기 JSON(약 540MB)과 심평원 병용금기 CSV(약 255MB)는 한 번에 읽지 않고 행 단위로 처리한다.
- **중복 축소**: 병용금기 제품 쌍은 판정 테이블(①)에서 성분코드 쌍으로 줄이고, 근거 코퍼스(③)에는 (성분A, 성분B, 금기사유, 고시번호) 고유 조합만 넣는다(RFP-17 결정 6, BE-05).
- **고시번호 정규화**: 연도 4자리 + 번호 4자리(RFP-17 결정 11). 메타데이터 `notice_no`로 쓴다.
- **청크 메타데이터**: `layer`(근거 계층), `issuer`, `doc_type`, `notice_no`, `base_date`, `locator`(조항·별표·연번·파일 행), `ingr_codes`, `license`. 청크 사이를 잇는 `chunk_id`, `parent_id`(조→호→목, 표→행), `refs`(참조 대상), `pair_id`(성분쌍)도 둔다(멀티홉 대응, 설계 문서 6장 (1)).

#### (3) 검색 방식

| retrieval 역할 | 읽는 저장소 | 질의 | 필터 | 결과 | 다음 단계 |
|---|---|---|---|---|---|
| **A. 판정 입력 찾기** | ② 사전 | 사용자가 쓴 약 이름 (오탈자·별칭 포함) | 없음 | 성분코드 후보 top-k와 점수 | 점수가 기준 이상이고 2위와 차이가 크면 확정, 아니면 후보를 보여 주고 질문 1개(FR-07). 확정된 코드로 ① 정확 일치 |
| **B. 열린 질문 후보 찾기** | ③ 근거 코퍼스 | "임신 중 피해야 할 진통제" 같은 성분 없는 질문 | `layer`, 금기 종류 | 후보 성분코드 집합 | 후보마다 ① 정확 일치로 검증하고 통과한 것만 답변. "찾은 항목이며 전체 목록이 아님"을 코드로 붙임 |
| **C. 근거 설명** | ③ 근거 코퍼스 | 판정된 성분 + 질문 의도 | `ingr_codes`(①의 결과로 사전 필터), `notice_no`, `base_date` | 사유·정의·주의 문장 청크 | 답변 문장마다 인용. Validator가 문장 종류별 허용 근거 계층을 검사(FR-05) |
| **D. 검색 보정** | ②·③ | 결과 0개 또는 점수 미달 | 같음 | 재작성한 질의(영문 성분명, 효능군 일반화)로 재검색 | 재검색 상한을 넘으면 "근거 없음"(FR-08) |

- 성분명·조항 번호는 정확한 문자열이라 BM25를, 설명형 질의는 임베딩을 함께 쓴다(하이브리드).
- 판정은 언제나 ①에서 하고, retrieval 결과만으로 금기 여부를 말하지 않는다.
- **멀티홉 대응**: 답이 여러 청크에 나뉘는 질문은 LLM이 연쇄 검색하게 두지 않는다. 주장 유형별로 나눠 계층 필터로 따로 검색하고, 코드가 `parent_id`·`refs`·`pair_id`로 연결 청크를 붙여 증거 묶음으로 LLM에 준다. 홉은 2회까지다(설계 문서 6장 (1)).

#### (7) 판정 소스 우선순위와 API 병기 규칙

2026-10-31 결정(사용자 승인). 연령금기도 병용·임부금기와 같은 방식으로 판정한다.

**이 방향으로 진행하는 이유**: 이 프로젝트의 주 목적은 서비스 완성이 아니라 **Agent-RAG를 활용한 AX 경험, 곧 RAG 실습과 에이전트 하네스 설계**다(1장 프로젝트 성격). 일반인 대상 오남용 예방 서비스는 그 과정을 다루기 위한 도메인이다. 그래서 판정 소스를 고를 때 "실시간으로 가장 최신인가"보다 아래를 먼저 따진다.

| 기준 | 파일 1차 + API 병기가 주는 것 |
|---|---|
| RAG 실습 | 파일을 직접 적재·청킹·색인하므로 사전(②)과 근거 코퍼스(③)를 만들고 retrieval을 평가하는 과정이 생긴다. API만 쓰면 이 과정이 사라진다 |
| 에이전트 하네스 | 스냅샷 판정, API Tool 호출, 두 결과의 비교, 불일치·실패 처리가 에이전트의 도구 선택과 고정 규칙(코드)으로 드러난다 |
| 평가 재현성 | 기준일이 고정된 파일로 같은 평가를 반복해 개선 전후를 수치로 비교할 수 있다(9장) |
| 지식 한계의 명시 | 파일 기준일을 에이전트가 아는 범위로 선언하고, 그 이후는 API 근거로만 말하게 할 수 있다 |

서비스 관점의 최신성은 API 병기로 보완하되, 판단 기준이 충돌하면 Agent-RAG 설계·구현·평가가 드러나는 쪽을 우선한다.

- **1차 판정 소스는 KIDS 파일이다.** 파일 기준일(2026-07-21, 수유부주의는 2025-11-27)이 에이전트의 지식 한계 시점이며, 시스템 프롬프트에 이 날짜를 명시한다(RFP-17 시스템 프롬프트 유의사항 1·2).
- **DUR API(품목정보·성분정보)는 병기한다.** 기준일 이후의 최신 정보를 확인하는 근거로 쓰고, 답변에 조회 시각을 함께 표시한다.
- **평가는 파일 기준으로만 한다.** API 응답은 시간에 따라 바뀌어 같은 평가를 재현할 수 없고 개발계정 트래픽 한도(10,000)도 있다. API는 데모와 실제 질문에서만 호출하고, 파일과 API의 일치율은 별도 관찰값으로 기록한다.

| 경우 | 답변 |
|---|---|
| 파일과 API가 같음 | 결론을 한 번 말하고 두 출처를 함께 표기("기준일 2026-07-21 자료와 실시간 조회(시각) 모두") |
| 파일에 있고 API에 없음 | 둘 다 보이고 한쪽을 확정하지 않는다. 기준일 이후 해제되었을 수 있다고 안내하고 약사·의사 확인을 권한다 |
| 파일에 없고 API에 있음 | 둘 다 보이고 한쪽을 확정하지 않는다. 기준일 이후 새로 지정되었을 수 있다고 안내한다. 어느 경우에도 "안전하다"고 말하지 않는다(FR-06) |
| API 호출 실패 | 파일 기준으로 답하고 "실시간 확인을 하지 못함" 문구를 코드로 붙인다 |

- 확인 결과(2026-11-01, `P2-doc/PJ2-API-응답확인.md`): 응답에 고시일자 필드(`NOTIFICATION_DATE`)가 있고, 연령금기 오퍼레이션은 품목 단위 `getSpcifyAgrdeTabooInfoList03`·성분 단위 `getSpcifyAgrdeTabooInfoList02`다. 다만 API의 성분코드(`D000147` 형식)는 KIDS 파일의 성분코드(`100501ATE` 형식)와 체계가 달라 같은 코드로 일치율을 낼 수 없다. 파일과 API의 비교는 영문 성분명 정규화나 품목(`ITEM_SEQ`) 연결로 한다. 두 고시일자가 같은 기준인지 확인하기 전에는 "API가 파일보다 최신"이라고 단정하지 않는다.

#### (3) 판정과 W1로 넘기는 것

- **판정: 진행 가능.** 핵심 범위(약품 정보, 병용·연령·임부 금기)와 확장의 대부분을 실제 공공 데이터로 처리할 수 있다. 막힌 곳은 없고 조건부 1건과 미정 1건이 있다.
- **사용자 결정**: ① 허가정보 API는 2026-11-01 보류로 결정했으나 같은 날 사용자가 신청해 승인되었다. 보류 때의 우려(본문 필드 없음, 어린이 제품 성분)는 해소되었다([RFP-21 결정 기록](../tickets/doc/RFP-21.md#결정-1-허가정보-api-활용신청-시점-보류-후-신청)). ② 파일과 API의 성분 연결 규칙은 미결정이다(API 안에서는 M-코드로 대부분 이어진다. 구현은 W1의 BE-09·BE-10). 새로 생긴 결정 ③은 허가사항 용법용량 표를 인용해 보일지다(RFP-21 결정 3).
- **W1에 넘기는 사실**: 정규화 규칙(위 (1)), 평가는 파일 기준이고 API Tool은 끔(5.1 (7)), 품목정보 병용금기 호출이 느림, 개발계정 일일 한도 10,000.

#### (4) 엔티티와 목 픽스처

- 네 API의 필드·엔티티·연결 키는 [PJ2-API-엔티티.md](PJ2-API-엔티티.md)에, 실제 응답 12건(서비스마다 3건)은 [tests/fixtures/api/](../tests/fixtures/api/manifest.json)에 저장했다. W1의 클라이언트 단위 테스트가 이 픽스처를 입력으로 쓰고, FastAPI `/mock`으로 API 호출 없이 돌릴 수 있다.
- 연결 키 실측: e약은요 `itemSeq` = 품목정보 `ITEM_SEQ`. KIDS 파일과 API는 같은 성분코드가 아니다.
- 구조화 값(`GRADE`, `AGE_BASE`, `MAX_QTY`, `MAX_DOSAGE_TERM`)은 성분정보 API와 KIDS 파일에만 있다. 품목정보 API는 같은 내용을 `PROHBT_CONTENT` 문장으로만 준다.
- 라벨 본문(2026-11-01 확인): 허가정보 API 허가 상세의 `EE_DOC_DATA`·`UD_DOC_DATA`·`NB_DOC_DATA`가 효능효과·용법용량·사용상의 주의사항을 XML 절 구조(DOC → SECTION → ARTICLE → PARAGRAPH)로 준다. 품목정보 `NB_DOC_ID`의 PDF(`/pbp/cmn/pdfViewer/{품목기준코드}/NB` → `/dsie/pdf/drb/{품목기준코드}/NB`)는 보조 경로다. 이용조건은 확인하지 못했다.
- 품목 ↔ 성분 연결: 허가정보 주성분 상세의 `MTRAL_CODE`가 모든 허가 품목의 제품 → M-코드를 준다. 이를 성분정보 `ORI_INGR`와 대조하면 6개 중 4개가 일치했고, 어린이 타이레놀 2개(`M281939`, `M279100`)는 같은 이름의 다른 M-코드가 있어 이름 보조가 필요하다.

## 6. 기능 요구사항
> **FR** = Functional Requirement, 즉 기능 요구사항. 시스템이 "무엇을 하는가"를 정하며, 표의 한 행이 FR 하나다. ID는 `FR-nn`으로 쓴다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | Router: 질문에서 약품명·연령·임신 여부·질환 등 엔티티 추출 후 도구 분기. 연령·임신 여부는 대화 중 입력하거나 사용자가 동의해 저장한 프로필(FR-09)에서 가져온다. 질문·대화 내용은 저장하지 않는다 | 필수 |
| FR-02 | 공공 API Tool: e약은요·DUR(식약처 OpenAPI) 조회, 조회 시각 기록 | 필수 |
| FR-03 | 문서 RAG: 표를 마크다운으로 보존해 파싱, 메타데이터(문서종류·연도·부처·고시번호·기준일) 필터 검색 | 필수 |
| FR-04 | Citation: 모든 답변에 출처·조회 시각(또는 자료 기준일)·조항 표기. 답변은 쉬운 요약을 먼저 보이고 근거 상세(성분코드·등급·조항)는 펼쳐 볼 수 있게 한다 | 필수 |
| FR-05 | Validator: 답변이 원본 API·문서와 일치하는지 점검 후 출력 | 필수 |
| FR-06 | Guardrail: 진단·처방 금지 문구, 응급 키워드가 있으면 119 안내를 맨 위에 고정하되 금기 조회는 막지 않음, 범위 외 거절. 조회 결과에 금기가 없어도 안전하다고 말하지 않는 고정 문구와 "근처 약국·약사에게 확인" 안내를 모든 답변에 코드로 붙인다 | 필수 |
| FR-07 | 오탈자 보정: 약품명 오입력 시 정규화 후 재검색 | 권장 |
| FR-08 | 근거 없음 처리: 검색 결과가 없으면 지어내지 않고 모른다고 응답. "금기 목록에 없음"과 "근거 없음(약 미식별·데이터 없음)"을 구분해 안내한다 | 필수 |
| FR-09 | 온보딩·계정: 첫 시작 때 프로필(연령대, 임신 여부, 복용 중인 약 등 선택 입력)과 저장 동의를 받고, Apple·Naver·Kakao·Google 소셜 로그인으로 계정을 만들어 프로필을 저장·수정·삭제할 수 있게 한다. 로그인 없이도 핵심 기능은 모두 쓸 수 있다 | 권장(확장) |

## 7. 비기능 요구사항
> **NFR** = Non-Functional Requirement, 즉 비기능 요구사항. 기능 자체가 아니라 "얼마나 잘, 어떤 조건으로 하는가"를 정하며, `FR-nn` 같은 번호는 붙이지 않는다.

- **신뢰성**: 근거 없는 사실 문장 출력 금지
- **재현성**: 같은 평가 세트로 개선 전후를 반복 측정 가능
- **보안**: API 키와 DB·인증 서비스 키(Supabase 등)는 환경변수로 관리하고 저장소에 커밋하지 않는다. 서비스 롤 키는 브라우저에 노출하지 않는다
- **개인정보**: 저장하는 것은 사용자가 동의한 프로필(연령대·임신 여부·복용 중인 약 등)과 로그인에 필요한 최소 정보(목표는 로그인 제공자, 제공자 사용자 ID, 표시 이름이며 인증 서비스가 실제로 저장하는 항목은 BE-11에서 확인해 맞춘다)뿐이다. 질문·대화 내용은 저장하지 않고 로그에도 남기지 않는다. 프로필은 사용자가 수정·삭제할 수 있다. 건강 관련 정보는 민감정보로 볼 수 있어 별도 동의가 필요할 수 있다(법률 검토는 거치지 않았다). 게스트로 쓸 때는 아무것도 저장하지 않는다. 공개 API 응답 캐시는 약품명 같은 공개 데이터만 담고 사용자·세션과 연결하지 않으므로 저장 대상 개인정보가 아니다.
- **고지**: 화면·응답에 "공공데이터 기반 정보 제공이며 진단·처방이 아님", "금기 목록에 없다는 것이 안전하다는 뜻이 아님", "요양기관의 DUR 점검을 대체하지 않음"을 표시하고, 사용한 자료의 출처와 기준일을 함께 표시한다. 한국의약품안전관리원 파일 데이터는 공공저작물 제2유형(출처표시, 상업적 이용금지)이므로 출처를 밝히고 상업적으로 이용하지 않는다.

| PDF 파싱 | pdfplumber, LlamaParse |
| 평가 | Ragas |

> DUR 금기 판정은 파일 적재 데이터와 식약처 OpenAPI를 함께 쓰는 혼합 방식으로 한다. 판정은 성분코드 정확 일치로 하고, RAG는 고시 조문·정의·비고, 금기사유·예외 설명, 인용을 맡는다(`tickets/doc/RFP-17.md`에서 2026-10-30 결정).


### 8.1 서비스 유저플로우

> 2026-11-01 작성. 질문 하나가 들어와 답이 나가기까지의 전체 흐름이다. 페르소나별 통과 기록(실제 값)은 [RFP-21](../tickets/doc/RFP-21.md)의 "서비스 유저플로우" 절에 있다. 아래는 설계이고, 코드는 아직 없다.

**페르소나**: 흐름을 시험하는 가상 인물 3명이다(실제 값은 RFP-21에서 API·파일로 확인). 진단·처방이 아니라 서비스가 만들 응답의 모양을 보는 용도다.

| ID | 인물(가상) | 상황 | 집에 있는 약 | 흐름에서 보는 것 |
|---|---|---|---|---|
| P1 | 지은(34세)과 아들 도윤(만 2세) | 어린이 타이레놀을 먹였고 기침약을 더 줘도 되는지 묻는다. 체중은 말하지 않는다 | 어린이타이레놀현탁액, 타이레놀콜드-에스정 | 제품 연령, 성분 중복, 용량을 정하지 않는 응답. 품목정보에 없는 제품의 성분 풀기(3) |
| P2 | 수아(31세, 임신 14주) | 열이 나서 집의 타이레놀을 먹어도 되는지 묻는다 | 타이레놀정500mg, 타이레놀콜드-에스정 | 모호한 이름 되묻기(2), 임부금기와 "금기 목록에 없음"(4), 라벨 보완(5) |
| P3 | 박순자(78세, 파킨슨병)와 딸 은영(52세) | 어머니가 라사길린(이지렉트정)을 드시는데 감기약 콜드-에스를 같이 먹어도 되는지 묻는다 | 이지렉트정, 타이레놀콜드-에스정 | 병용금기 해당, 파일과 API 불일치 병기(4), 전문의약품 라벨 인용(5) |

**컨셉 한 줄**: 사용자는 쉬운 말로 묻고, 에이전트는 공공 API·적재한 파일·문서에서 근거를 찾아 **쉬운 요약을 먼저, 근거 상세를 펼치게** 답한다. 금기 여부는 코드가 정하고, LLM은 찾은 근거로 설명만 한다. 가부와 용량은 말하지 않는다.

```
[0 사용자 입력]  "임신 14주인데 열이 나요. 타이레놀정500이랑 콜드-에스 먹어도 돼요?"
     │
[1 입력 정리]    Router(AG-05)가 약 이름·나이·임신 여부를 뽑는다 / Guardrail(AG-08, 코드)이 응급 키워드를 감지한다
     │            응급이면 119 안내를 답변 맨 위에 고정하고, 아래 단계는 막지 않고 병행한다
[2 제품 찾기]    사전(BE-10)이 이름을 품목으로 확정하고 e약은요 Tool(BE-02)·허가 상세가 라벨 문장을 가져온다
     │            모호하면 ▶ [되묻기 카드] 질문 1개 ▶ 다시 입력
[3 성분 풀기]    제품을 성분으로 푼다(복합제는 성분별로)        못 풀면 ▶ "약 미식별" = 근거 없음
     │
[4 금기 확인]    판정 테이블(파일, 1차, BE-09) + DUR API 병기(BE-03): 병용·연령·임부, 확장으로 중복·용량·노인·수유부
     │            파일과 API가 다르면 한쪽을 확정하지 않고 둘 다 보인다
[5 근거 찾기]    근거 코퍼스(BE-05, AG-03)에서 주장 유형별로 따로 검색해 증거 묶음을 만든다: 사유(L2), 라벨(L3), 고시(L1)
     │
[6 요약 쓰기]    LLM(AG-06)이 증거 묶음만으로 쉬운 요약 + 근거 상세를 쓴다
     │
[7 검증]         Validator(AG-07): 문장마다 허용 근거 계층인지, 필요한 근거가 빠지지 않았는지, 숫자·원문이 맞는지
     │
[8 마무리]       코드가 붙인다(AG-08): 고정 문구, 자료 기준일·조회 시각, 약국·약사 안내(응급이면 119를 맨 위에)
     ▼
[응답]           BE-06 /chat → FE-01·02 화면: 쉬운 요약 먼저, 펼치면 근거 상세
```

| # | 단계 | 맡는 것 | 읽는 곳 | 결과 | 막혔을 때 |
|---|---|---|---|---|---|
| 1 | 입력 정리 | Router: 프롬프트 + 스키마 검증, Guardrail: **코드** | 사용자 입력 | 약 이름, 나이, 임신 여부, 응급 신호 | 범위 외·진단·처방·용량 요청은 안내 전환 또는 거절 |
| 2 | 제품 찾기 | 사전 검색: **코드**, 라벨 조회: Tool | 사전(②), e약은요 API(일반의약품), 허가정보 API 허가 상세(전문의약품·e약은요에 없는 제품) | 품목기준코드, 라벨 문장, 조회 시각 | 후보가 여럿이면 되묻기, 오탈자는 보정(FR-07) |
| 3 | 성분 풀기 | **코드** | DUR 품목정보 `MATERIAL_NAME`, 허가정보 주성분 상세(`MTRAL_CODE`), 사전, 제품명 괄호 | 성분 목록과 성분코드 | M-코드가 성분정보와 다르면 이름으로 보조, 그래도 못 풀면 "약 미식별"로 분류하고 금기가 없다고 말하지 않음 |
| 4 | 금기 확인 | **코드**(정확 일치) | 판정 테이블(①), DUR 성분정보·품목정보 API | 금기별 해당/목록에 없음, 등급·연령 조건, 고시번호, 기준일 | 파일≠API는 둘 다 표시, API 실패는 파일 기준 + 안내 문구 |
| 5 | 근거 찾기 | 필터·조인: **코드**, 의미 검색: 임베딩 | 근거 코퍼스(③): 사유·상세정보, 라벨(e약은요·허가 상세 본문), 고시 조문 | 주장 유형별 증거 묶음 | 0건이면 재검색 1회 뒤 "근거 없음"(FR-08) |
| 6 | 요약 쓰기 | **LLM** | 증거 묶음만 | 쉬운 요약, 근거 상세 | 근거에 없는 문장은 쓰지 않는다 |
| 7 | 검증 | **코드** + 필요 시 LLM | 요약, 증거 묶음, 원문 | 통과 / 수정 / 재생성 | 해결하지 못하면 안내 전환 |
| 8 | 마무리 | **코드** | 메타데이터 | 고정 문구, 기준일, 조회 시각, 약국·약사 안내 | 모든 답변에 붙는다 |

**구상과 설계의 대응** (사용자 구상: 입력 → e약은요 → DUR API → DUR 문서 → 요약)

| 구상 단계 | 설계에서 | 달라진 점 |
|---|---|---|
| 사용자의 입력이 들어옴 | 1 | 응급 감지와 범위 외 거절이 입구에 붙는다 |
| Agent가 e약은요에서 의약품 정보를 불러옴 | 2·3 | e약은요에는 **성분 필드가 없고 전문의약품도 없다.** 제품은 사전과 e약은요·허가정보로 찾고(전문의약품 라벨은 허가 상세 본문), 성분은 품목정보·허가정보 M-코드·사전으로 푼다 |
| DUR API로 병용금지·임부금지를 찾아옴 | 4 | **1차는 적재한 파일, API는 병기**다. 복합제는 품목 API로는 0건이라 성분으로 풀어서 조회해야 한다 |
| DUR 문서에서 근거와 조항을 불러옴 | 5 | 고시 PDF만이 아니라 사유·상세정보(L2), 라벨(L3, 전문의약품은 허가 상세 본문), 고시(L1)를 함께 쓴다. 고시는 정의 조항 위주이고 별표는 변환 전이다 |
| 요약해서 전달 | 6·7·8 | 요약 앞에 증거 묶음이, 뒤에 검증과 고정 문구가 있다 |

**예외 경로**

| 상황 | 단계 | 응답 |
|---|---|---|
| 응급 키워드 | 1 | 119 안내를 맨 위에 고정하고 금기 조회는 병행 |
| 제품이 여러 개이거나 모호 | 2 | 되묻기 카드(후보 표 + 질문 1개), 가부는 말하지 않음 |

### 8.2 Agent 설계 점검 (Agent 101 기준)

> 강의 「Agent 101」 기준 점검(2026-11-02). 컨셉은 맞지만 8.1의 8단계는 고정 파이프라인이라 ReAct 자리가 없었다. 제안은 "하네스가 감싼 단일 ReAct 에이전트"다. Guardrail·Router·판정·Validator·고정 문구는 코드가 맡고, 2~5단계 도구 호출의 순서만 `create_agent`(ReAct)가 정하며, 종료 직전 코드가 필수 도구 호출을 확인한다. 질문 대화는 저장하지 않는 원칙과 trace가 충돌해 합성 평가 질문에만 trace를 켠다.

점검표 15행, 도구 4개 초안, P2 경로 예시, 평가 보완, 결정 D1~D4는 [RFP-22](../tickets/doc/RFP-22.md)에서 관리한다.

## 9. 평가 기준
| 항목 | 측정 | 목표 | 결과 |
|---|---|---|---|
| 검색 정확도 | Context Precision·Recall (Ragas) | 기준선 대비 개선 | 측정 전 |
| 답변 충실도 | Faithfulness (Ragas) | 기준선 대비 개선 | 측정 전 |
| 오탈자 견고성 | 오탈자 질문 세트 | 정상 대비 하락 최소화 | 측정 전 |
| 안전 응답률 | 범위 외·오정보 질문 세트 | 기준선 대비 개선 | 측정 전 |
| 금기 판정 정답률 | 정상 세트 중 병용·연령·임부 금기 질문 (금기등급 M 성분 포함) | 기준선 대비 개선 | 측정 전 |

- 평가 세트: 정상 / 오탈자 / 범위 외 / 오정보, 세트별 [__]문항 (1주차 확정)
- 평가 세트에는 "금기 목록에 없는 약" 질문과 응급 상황 질문을 넣어 고정 문구와 119 안내가 붙는지 본다. 전문가형 질문은 선택 항목이다.
- 보조 지표: 라우팅 정확도(질문에 맞는 도구를 골랐는지의 비율), retrieval 보조 지표(판정 실행률, 성분코드 Recall, 후보 Recall — 5.1절 (3)의 A·B 역할, 근거 묶음 Recall — 멀티홉 문항에서 정답에 필요한 청크가 모두 들어왔는지). 위 5개 지표에 더하지 않고 개선 분석에 쓴다. 평가는 파일 기준으로 하고 API Tool은 끈다(5.1절 (7)).
- 금기 판정은 성분 단위 규칙 조회라 검색 지표(Context Precision·Recall)로 측정되지 않아 별도 지표를 둔다.
- 보조 비교: `P2-doc/PJ2-가설검증.md`의 시나리오(TC)를 세 조건(LLM 단독 / 규칙·조회만(근거 코퍼스 검색 B·C 끔) / MediAgent 전체)에 똑같이 넣고 채점표 항목별 통과율을 비교한다. 위 5개 지표에 더하지 않는다. 첫째와 셋째의 차이는 Agent-RAG가 LLM 단독보다 나은 점을, 둘째와 셋째의 차이는 근거 코퍼스 검색(역할 B·C)이 실제로 하는 일을 보인다. 둘째 조건에서도 사전(역할 A, 판정 입력)과 Validator는 켜 둔다. 사용자 대상 가설(H1~H4)은 시간이 남을 때만 하는 선택 항목이다.
- 참고: 원스글로벌 Dr.DI 성능검증 기사(약업신문, 2026-07-15)의 평가 항목 구성. 수치는 비교하지 않음

| 금기등급 M은 고시에 없고 심평원 문서에만 정의됨 (처방·조제 사유 코드 M과 다른 것) | 심평원 설명("상병에 따른 1등급 또는 2등급")을 인용하고 등급은 상세정보 원문으로 전달 (RFP-17의 "M 처리 규칙") |
| 범위 확대(중복·용량·수유부·온보딩·소셜 로그인)로 일정 초과 | 핵심(병용·연령·임부 금기)을 먼저 끝내고 4장의 순서대로 확장 항목부터 축소. Agent-RAG 핵심 요소(Router·도구 선택·근거 고정·Validator·평가 수치)는 줄이지 않음. 응급 처리(FR-06)는 필수라 축소 대상이 아님 |

| 건강 관련 프로필 저장의 개인정보 부담 | 최소 항목·동의·수정·삭제, 질문 내용은 저장하지 않음, 게스트는 저장 없음 |
| 소셜 로그인 4종 연동 부담(Apple 계정 조건, Naver 별도 연동) | Google·Kakao를 먼저 하고 Apple·Naver는 확인 후 포함 여부 결정 |
| Supabase 무료 플랜 한계(DB 500MB, 비활동 1주 일시정지) | RFP-15에서 적재 크기를 확인하고, 시연 전에 프로젝트를 깨워 둠. 대안은 로컬 Chroma |
| "금기 없음"을 안전 허락으로 오해 | 결과가 없을 때 붙는 고정 문구를 코드로 강제하고, 평가 세트에 이 경우를 넣음 |
| 응급 대응 문구·연락처에 공식 근거가 없음 | RFP-19에서 공식 출처를 확인하기 전에는 119와 약국·약사 안내 외의 응급 지침을 쓰지 않음 |
| 전문가가 DUR 시스템의 대체로 오인 | 고지에 대체 불가를 명시하고 전문가 전용 기능을 두지 않음 |
| 답이 여러 청크에 나뉘어 일부 근거가 빠짐(멀티홉) | 주장 유형별 분해 검색, 키 조인(`parent_id`·`refs`·`pair_id`), 증거 묶음, Validator 누락 검사. 구현 전에 샘플 질의로 단일 top-K의 누락률을 먼저 잼(AG-03) |
| Retrieval 설계(근거 계층 6개, 저장소 3개, 하이브리드 검색)가 1주차 범위를 초과 | 설계 문서 11장의 순서를 따르고, 용어집(L4)·논문 정리(L5)·약사법 조문은 맨 마지막으로 미룸. 사전(A)과 사유·고시 청크(L2·L1)를 먼저 끝냄 |
