# AG-16 · 고정 파이프라인 대조군(같은 도구·같은 Validator, 호출 순서 고정)

## 1. 이슈
“에이전트가 필요한 이유”를 수치로 보이려면 같은 도구·같은 모델·같은 Validator로 **호출 순서를 코드가 고정**한 대조군(C1)이 있어야 한다(RFP-23 §5). 이 티켓이 그 고정 파이프라인을 만든다. 새 도구를 만들지 않고 AG-02·AG-03의 도구 함수와 AG-08·AG-07의 입구·출구 코드를 그대로 재사용한다. 차이는 "도구를 부르는 순서·횟수를 누가 정하나(코드 대 LLM)" 하나여야 한다.

## 2. 완료 조건
- [ ] LangGraph로 고정 순서 그래프가 만들어진다: `guardrail_in` → `router` → 약마다 `identify_drug` → `check_contraindications` → `search_reason` → `search_label` → LLM 요약 → `validator` → `finalize`. 모델이 도구를 고르지 않는다.
- [ ] 고정 파이프라인은 **두 단계**로 만든다(RFP-23-02 A). 기본 C1은 예외 규칙 두 가지뿐이고, 강화 C1+는 여기에 "오탈자 보정 후 재검색 1회"를 더한다. 설정으로 전환한다.
- [ ] (기본 C1) 예외 규칙은 두 가지뿐이다: 식별 결과 0건이면 "약 미식별" 안내, 후보가 여럿이면 되묻기 카드(RFP-23 §5.2). 오탈자 보정·재검색 규칙은 C1에는 넣지 않는다.
- [ ] 같은 모델, 같은 도구 함수, 같은 Guardrail·Validator·고정 문구를 쓴다(코드 공유로 확인).
- [ ] (RFP-33-03) **기준선 하네스 장치는 C1·C1+·C2 공통**이다: 인자 스키마·도구 출력 계약(성분명 입력이면 `search_label`이 `NO_PRODUCT`를 돌려줌)·상태 키 제한·`finalize` 항목별 문구가 도구 함수와 입구·출구 안에 있어 C1·C1+에서도 같게 동작함을 코드 공유와 테스트(성분명 입력 1건에서 제품 라벨이 새지 않음)로 확인한다. 개선 단계 선택 제한 장치(`known_ids`·단위 보조 차단·반복 경고)는 C1·C1+에 넣지 않는다(C3 전용, AG-13). 조건별 적용 장치 목록을 `harness@v1`로 결과 파일에 기록한다(BE-08).
- [ ] (RFP-33-05) 하네스 차단·경고 건수와 "차단 뒤 상한 종료" 비율을 trace의 `harness_event`로 조건별 보조 기록에 남긴다. PJ2-RFP.md 9장의 지표·평가 세트는 바꾸지 않는다.
- [ ] 평가 설정 식별자로 C1을 선택해 실행할 수 있고(BE-08과 연동), 호출 수·지연·토큰이 C2와 같은 형식으로 기록된다.
- [ ] 샘플 질문 3건(정상, 오탈자, 모호)이 끝까지 실행되고 결과가 저장된다.

## 5. 메모
- 2026-11-02 사용자 요청으로 만듦(RFP-23). 이 티켓의 결과가 에이전트(C2)의 우월성이 아니라 "어디서 이득이고 어디서 아닌지"를 보이는 데 쓰인다.
- 가정: 고정 파이프라인의 예외 규칙 수준은 비교 중에 바꾸지 않는다. 바꾸면 결과 해석에 적는다.
- 가정: 구현 부담은 작다(새 도구 없음, 그래프 간선만 고정). 확인 전이며 구현 시 시간을 기록한다.
- 2026-11-06 결정 반영(RFP-33-03·05 A): 기준선 하네스 장치는 C1·C1+·C2 공통, 개선 단계 장치는 C3에만 한 번에 하나씩(PJ2-Agent-Harness.md 7.2절, PJ2-RFP.md 9.5절). 비교가 하네스 유무가 아니라 도구 선택 주체의 차이를 재게 한다.
- 2026-11-16 **C1 고정 파이프라인 W2로 당김(AG-13-01 A)**: RFP 10장은 3주차 항목이지만 AG-12 비교 실험(C0·C1·C1+·C2)이 W2 11-21에 시작하므로 C1 구현을 W2 11-20(금)으로 당긴다(BE-08 조건 전환과 함께). 이 티켓은 원래 SCH-02이라 소속 변경은 없다. 측정 기간(AG-11 ~ AG-14)에는 C1 규칙을 바꾸지 않는다(RFP 9.6절). 평가 규칙은 그대로다.
