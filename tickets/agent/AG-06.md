## 1. 이슈
검색·조회된 근거만 사용해 답변을 만들고, 모든 답변에 출처·조회 시각(또는 자료 기준일)·조항을 붙인다. LLM은 설명과 종합만 맡는다(RFP 1장). 주 사용자가 일반인이므로 답변은 일반인 눈높이의 쉬운 요약을 먼저 쓰고, 성분코드·등급·조항 같은 근거 상세는 요약과 분리해 따로 만든다(RFP FR-04). 두 부분은 BE-06의 `summary`, `detail` 필드에 들어간다.

규칙 구현 방식은 항목마다 (코드) / (프롬프트)로 표기한다.

## 2. 완료 조건
- [ ] (프롬프트) 생성 프롬프트가 제공된 근거만 사용하도록 제한되어 있다.
- [ ] (코드) 모든 사실 문장에 연결된 출처 ID가 있고, 출처 ID가 없는 문장은 출력 전에 걸러진다. 확인: 출처 ID 없는 문장을 넣은 가짜 모델 응답이 걸러지는 pytest 테스트.
- [ ] (코드) API 출처에는 조회 시각이, 파일 데이터와 문서 출처에는 자료 기준일과 문서명·조항/쪽이 포함된다.
- [ ] (프롬프트) 쉬운 요약은 일반인 눈높이의 평이한 말이며 결론(주의가 필요한 조합인지, 확인할 점)을 먼저 말한다. 복용 여부와 용량은 정해 주지 않는다.
- [ ] (코드) 근거 상세(성분코드·금기등급·고시 조항·기준일)는 요약과 분리된 별도 필드로 만들어진다. 요약에 성분코드 같은 전문 용어가 그대로 나열되지 않음을 샘플로 확인했다. 확인: 응답 JSON의 `summary`·`detail` 필드가 분리되어 있고(BE-06), `summary`에 성분코드 형식(`D######`)이 없음을 정규식 테스트로 본다.
- [ ] 샘플 10건에서 출처 누락이 0건이다.
- [ ] 제품 사용 연령·상호작용 같은 라벨 문장은 요약하지 않고 인용으로만 쓰며, Validator(AG-07)가 원문과 대조한다(`P2-doc/PJ2-가설검증.md` TC-01).
- [ ] (개선) (코드 + 프롬프트) 답변은 AG-03이 돌려준 증거 묶음에 들어 있는 청크만으로 쓴다. 묶음 밖의 청크나 모델 지식으로 쓴 사실 문장은 출처 ID가 없어 걸러지는 테스트가 통과한다(위 출처 ID 조건과 같은 검사로 확인).
- [ ] (개선) (코드 + 프롬프트) 약이 N개라 쌍이 여럿인 질문(TC-18, 22)은 map-reduce로 쓴다. 쌍마다 그 쌍의 사유 청크만으로 따로 요약한 뒤 합친다. 3쌍 샘플에서 쌍별 요약 3개가 따로 만들어지고, 합친 답변에서 쌍마다 사유가 해당 쌍의 청크 출처와 연결되며, 다른 쌍의 사유가 섞이지 않음을 확인했다. 금기 목록에 없는 쌍은 사유를 만들지 않고 "금기 목록에 없음"으로 구분한다(AG-09).
- [ ] (PRD-10-04) 허가사항 원문 인용은 `{약 이름} 허가사항 원문({항목}): "…"` 형식으로 약 이름·항목·인용부호를 붙이고 대괄호 자리표시를 만들지 않는다. 원문이 비면 인용 줄을 만들지 않고 `missing_reason`에 대응하는 코드 상수(PRD-11-03, H26)로 쓴다. 단일 문구 "원문을 가져오지 못했어요"는 폐기한다(RFP-21-03 고정 문구는 그대로).
- [ ] (코드, PRD-11-05·H29) 근거 상세 항목마다 `source_kind`·청크 ID·조회 시각을 도구 결과 값 그대로 붙이고 LLM이 쓰지 않는다. 라벨은 자료 이름대로다: e약은요에서 왔으면 "쉬운 설명(e약은요)", 허가정보 상세에서 왔으면 "허가사항 원문"(PRD-11 §7.1 정정). e약은요 `intrcQesitm` 문장에 "허가사항 원문"이 붙지 않음을 테스트로 확인한다.
- [ ] (코드, PRD-11 H28) 인용부호 안 문자열은 청크·API 원문과 글자 일치하고(의역 금지, 생략은 `…`로만) 근거 상세에 `LLM_SUMMARY`가 들어가지 않는다.
- [ ] (AG-06-01 A, 코드) `detail`·`citations[]`(출처 표)·`badges[]`는 도구 결과 `items[]`를 읽는 **코드 렌더러**(`finalize` 쪽, AG-08)가 만들고 LLM은 만들지 않는다. AG-06의 LLM은 쉬운 `summary` 문장과 문장별 근거 ID·인용 지정만 낸다. 확인: 가짜 `items[]`를 넣으면 LLM 호출 없이 `detail`·`citations[]`가 만들어지는 pytest.
- [ ] (AG-06-02 A, 코드) LLM 출력은 구조화 출력(Pydantic 스키마: `sentences[{text, evidence_ids[], claim_type}]`, 인용 `{evidence_id, start, end}`)이고 코드가 검사·조립한다(자유 텍스트 표지 파싱 없음). 확인: 스키마에 맞지 않는 출력과 근거 ID가 없거나 모르는 ID인 문장이 걸러지는 pytest, 걸러진 문장 수와 글자 불일치 인용 수가 `harness_event`로 남는다(제안, AG-13 개선 전후 비교의 원천).
- [ ] (AG-06-03 A, 코드) **코드 부분**(문장 필터, 렌더러, `D######`·KIDS(`######AAA`) 정규식, 인용 글자 일치 함수)은 AG-01·AG-02·AG-03 선행 없이 W1 안에서 가짜 `items[]`로 먼저 만든다. 프롬프트 부분은 기준선(AG-01) 뒤에 한다. 입력 계약은 BE-09 `ToolResult.to_dict()` + BE-02·03·09 계약 보강(각 티켓 완료 조건)이다. 코드 위치(제안): `backend/app/agent/` 안의 렌더러 모듈 또는 별도 `backend/app/render/`는 CLAUDE.md 7장에 없는 폴더라 새로 만들기 전에 결정 번호를 올린다.

- [ ] (PRD-16-01·03) `summary` 프롬프트(`answer_summary@v1.md` 후보, `P-AG06-summary`)는 AG-01 기준선 뒤에 PRD-16-01 형식(정적 프런트매터, 평가 결과는 카드)으로 쓰고 **검토 카드를 사용자가 승인한 뒤에만** 기준선에 넣는다. L0·L1·L2(개발 골든) 결과를 카드에 적고, 이 프롬프트를 바꿀 때는 L3(개발셋 전체)도 돌린다. 이 항목은 프롬프트 부분이며 코드 부분(렌더러·필터·정규식·글자 일치 함수)은 위 AG-06-01~03 항목이다.

### 6.1 AG-06-01 결정 이유 기록(사용자 확인 질문에 대한 답)
사용자가 "코드 렌더러가 등장하는 이유는 의약품 같은 안전 정보에서 할루시네이션을 제어하기 위한 조치로 이해하면 되느냐"고 물었고 그렇다고 정리했다. 구체적으로 세 가지다. ① 등급·성분·날짜·고시번호·인용 같은 **사실은 LLM이 쓰지 못하게** 해서 할루시네이션이 생길 수 있는 곳을 요약 문장 한 곳으로 줄인다. ② 고정 문구·약사 권고처럼 안전을 위한 요소를 코드가 항상 넣어 LLM이 빠뜨릴 수 없게 한다. ③ 근거 ID와 글자 일치를 코드로 검사한다(H1·H28·H29). **단, LLM이 쓰는 요약 문장은 남으므로 이것은 할루시네이션을 완전히 없애는 것이 아니라 줄이고 검사 가능하게 만드는 조치다**(과장하지 않는다). 요약 문장의 사실 일치는 AG-07 Validator와 평가(AG-11)가 계속 본다.
