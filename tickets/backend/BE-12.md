## 1. 이슈
RFP 5장은 e약은요의 문장형 필드(사용법·주의사항·상호작용 등)를 "전체 품목을 1회 수집해 스냅샷으로 적재하고 문장 단위 retrieval, 런타임에는 Tool로 최신 확인"한다고 적었고, 5.1절 (4)는 e약은요를 "전체 품목 1회 수집 → ②·③"으로 둔다. 설계 문서 12장 결정 9(채택)가 신규 티켓으로 수집 스크립트를 두기로 했다. 이 티켓이 e약은요 API를 한 번 전부 내려받아 스냅샷으로 저장한다. 스냅샷은 제품·성분 사전(BE-10, ②)의 보강 재료이자 근거 코퍼스(BE-05, ③)의 e약은요 문장 청크 원천이다. 런타임의 개별 조회·캐시·조회 시각은 BE-02가 맡는다.

가설 문서 8.2는 TC-14·15의 약(메토트렉세이트정·알렌드로네이트)이 전문의약품이라 e약은요에 없을 수 있다고 본다. 이 티켓이 전체 수집으로 그 포함 여부를 한 번에 확인해 기록한다.

## 2. 완료 조건
- [ ] 수집 전에 API로 `totalCount`를 확인해 기록했고, 수집한 품목 수가 `totalCount`와 같다(다르면 차이와 이유를 기록).
- [ ] 전체 품목을 1회 수집해 스냅샷 파일로 저장한다. 스크립트를 재실행해도 중복이 생기지 않고 중단 지점부터 이어서 할 수 있다.
- [ ] 스냅샷에 수집일이 기록되어 있다(청크 기준일과 답변 표기에 쓰인다).
- [ ] 효능·사용법·경고·주의사항·상호작용·부작용 문장형 필드가 원문 그대로 저장된다.
- [ ] 전문의약품 포함 여부가 기록되어 있다. 메토트렉세이트정·알렌드로네이트 같은 제품이 스냅샷에 있는지를 제품명 검색으로 확인해 있음/없음을 적었다.
- [ ] (PRD-08-07) 허가정보 **전체** 상품명 목록(전문·일반)을 수집해 사전용 스냅샷으로 둔다(BE-10 사전이 비전 후보 제시·오탈자·되묻기에 공용으로 씀). 상세 수집 대상은 아래 선별 범위 그대로다.
- [ ] 호출 제한 오류가 나면 중단하고 오류를 기록한다. 인증키와 호출 주소는 환경변수(`DRDEASYDRUG_API_KEY`, `DRDEASYDRUG_END_POINT`)로만 읽고 로그와 스냅샷에 남기지 않는다.
- [ ] 스냅샷은 `data/` 아래에 두고 커밋하지 않는다.
- [ ] 허가정보 API 활용 범위가 기록되어 있다. 허가정보 API는 2026-11-01 승인되었고(RFP-21 결정 1), 전문의약품·e약은요에 없는 제품의 허가 상세(`getDrugPrdtPrmsnDtlInq08`)와 주성분 상세(`getDrugPrdtMcpnDtlInq08`)는 평가·페르소나에 쓰는 제품 목록(AG-04 평가 세트, RFP-21 페르소나 약 포함)만 **이 티켓이 수집해 스냅샷으로 저장**한다. 청킹·적재는 BE-05, 제품→성분 연결은 BE-10이 한다.
- [ ] (PRD-11 §6.1, H26) 이지렉트정(S2 페르소나 제품)이 허가정보 상세 수집 대상에 들어가는지 확인해 기록한다. 들어가면 `EASY_TEXT_MISSING` + 허가사항 원문 경로, 들어가지 않으면 `OUT_OF_SCOPE`(수집 범위 밖) 판정 근거가 된다. 수집 범위 목록을 파일로 남겨 AG-02가 대조할 수 있게 한다.

## 3. 하위 작업

- [ ] 페이지 단위 수집 스크립트(재개 가능, 호출 제한 처리)
- [ ] 스냅샷 저장과 수집일 기록
- [ ] 전문의약품 포함 여부 확인(메토트렉세이트정·알렌드로네이트)

## 5. 메모
- 가정: 전체 수집의 호출 수와 일일 트래픽 한도는 BE-02의 응답 샘플 확인 전에는 알 수 없다. 한도를 넘으면 며칠에 나눠 수집하도록 재개 기능을 두었다. 개발계정 한도(10,000)는 DUR API 쪽 값이며 e약은요 한도는 확인하지 않았다.
- 가정: `totalCount`는 수집 시점에 확인하는 값이라 이 티켓 작성 때는 숫자를 적지 않았다.
- 가정: 이 티켓은 SCH-01의 필수로 둔다. 사전(BE-10)과 근거 코퍼스(BE-05)가 이 스냅샷을 받으므로 BE-02 직후에 착수해야 SCH-01 완료 기준(문서 검색 동작)에 맞는다. SCH-01이 밀리면 RFP 4장 순서가 아니라 BE-05·BE-10의 e약은요 보강 범위를 줄인다(핵심은 파일 기반 사전).
- 허가정보 API 활용신청은 설계 문서 12장 결정 4에 따라 1주차에 미리 신청하지 않는다. 신청은 사용자 승인이 있어야 하며 이 티켓은 신청 필요 여부를 판단·보고만 한다. 2026-11-01 결정으로 보류이며 신청 기준은 RFP-21 결정 1의 (a)(b)다.
- 2026-10-31 BE-02 메모의 "전문의약품이 e약은요에서 조회되는지 응답 샘플로 확인" 항목은 개별 샘플 확인이고, 전체 포함 여부는 이 티켓이 기록한다.
- 2026-11-01 응답 확인: e약은요 전체 4,746건이고 전문의약품이 없다는 것이 확인되었다(`P2-doc/PJ2-API-응답확인.md`). 이 티켓의 "전문의약품 포함 여부 기록"은 이미 답이 있으므로 수집 때 재확인만 한다. 라벨 문장이 필요한 전문의약품은 허가정보 API(사용자 결정)로 잇는다.
- 2026-11-01 후속: 위 "활용신청은 1주차에 미리 신청하지 않는다" 메모는 보류 결정 시점의 기록이다. 같은 날 사용자가 허가정보 API를 신청해 승인되어 게이트는 사라졌다(RFP-21 결정 1).
- 2026-11-02 전체 점검: 허가정보 수집을 맡는 티켓이 없었다(BE-02는 e약은요 클라이언트만, BE-05·BE-10은 입력만 받음). 이 티켓이 선별 수집을 맡는 것으로 정하고 제목을 바꿨다. 허가정보는 필터 이름이 `item_name`·`item_seq`·`Prduct`로 서비스마다 다르다(`P2-doc/PJ2-API-엔티티.md` 9장). 선별 수집 대상 제품 수와 호출 한도는 수집 전에 정한다.
- 2026-11-02 RFP-21-03(B): 허가 상세 수집 때 `UD_DOC_DATA`(용법용량)를 빠뜨리지 않는다. 근거: RFP-21 §6.3.
