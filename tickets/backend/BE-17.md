## 1. 이슈
2026-11-19 사용자 관찰: 서버를 띄운 뒤 첫 응답이 27.84초 걸렸고 "약 찾는 중" 진행 표시가 멈춰 보였다. 원인 조사(chat-rca)에서 **되묻기 경로는 LLM 호출이 0회이고 그래프 계산은 0.02초**이며, 27.8초는 서버 시작 뒤 첫 요청이 코퍼스·사전을 DB에서 읽어 메모리 색인을 만드는 시간(합계 29.21초: 코퍼스 SELECT 16.07초·사전 SELECT 7.94초·BM25 구성 2.56초)이었다(확실, `P2-doc/PJ2-코퍼스-적재와-준비.md` §2.2·§4.3).
진행 표시가 멈춰 보인 이유는 둘이 겹친다: 첫 `progress` 이벤트 전에는 `stage=null`이라 움직이는 것이 없고, `drug_lookup` 단계는 모델이 `identify_drug`를 부를 때만 나오는데 개발셋 C2 실행에서 그런 문항은 1/150이다(같은 문서 §4.3).
BE-06-27 A는 "첫 요청에서 만든다. 실제 시간을 한 번 재고 시작 뒤 백그라운드 준비로 옮길지 판단한다"였다. 이번 측정이 그 조건을 채웠으므로 같은 결정을 이 티켓 BE-17-01에서 다시 정한다.
근거 문장: BE-06-27 A("첫 요청 시간 측정 뒤 BE-13 배포 구성", [BE-06 §6](BE-06.md#6-결정-현황)), 설계 문서 §4.3 원인, Recap 사례(첫 응답 27.84초, 2026-11-19).

## 5. 메모
- 2026-11-19 신설(사용자 "FE-10-05~09 권장대로, 지연 티켓 신설", 지시서 `2026-11-19-m19-sched.md`). 우선순위는 `권장`으로 뒀다(가정: RFP FR에 직접 대응하는 필수 항목이 아니라 사용성 개선이며, 사용자가 신설을 지시했다. 필수로 올릴지는 사용자 판단).
- 숫자는 모두 로컬 → 원격 Supabase 1회 측정이다(설계 문서 §2.2, ±수 초 흔들림). 효과(27.8초 → 0.02초 등)는 추정이며 실서버 확인 ⑥으로 확인한다.
- 이 티켓 작업은 서비스 경로 전용이라 평가 영향이 없다. 단 코퍼스 로더(`CorpusIndex.from_db`)는 서비스와 평가가 공유하므로 로더 변경(후보 C6)은 이 티켓 범위가 아니다(측정 기간 보류, 설계 문서 §7).
- **BE-17-09 배경(사용자 질문 2026-11-19)**: 사용자는 코퍼스 3층 가운데 L3가 API(e약은요·허가정보)에서 온다는 점을 짚고, BM25 색인을 사용자 질의 때가 아니라 빌드 때로 당기면 문제가 있는지 확인하라고 요청했다. 정리(메인 답, 설계 문서 보강 대상):
  - 색인은 **질의와 무관하게 코퍼스 청크로 만드는 것**이다(L1·L2·L3 청크는 이미 DB `corpus_chunks`에 있고 L3도 요청 때 API를 부르지 않는다). 질의는 완성된 색인 위에서 점수만 계산한다. 그래서 빌드 때 만드는 것은 기술적으로 가능하다.
  - 다만 ① 29초의 대부분(약 24초)은 색인 구성(2.56초)이 아니라 DB에서 코퍼스·사전을 읽는 **전송 시간**이라 색인만 당겨서는 효과가 작다 ② 빌드 때 DB에서 읽으려면 빌드 환경에 DB 비밀값이 필요하고(이미지 층에 남을 위험) 비밀값을 피하려고 데이터 파일을 이미지에 넣으면 BE-06-24 B(런타임 데이터는 DB 원칙)를 어긴다 ③ 공공저작물 제2유형(출처표시, 상업적 이용금지) 데이터가 이미지에 실려 재배포 범위가 넓어진다 ④ DB 재적재와 이미지 판이 어긋날 수 있고 평가는 `from_db`로 읽으므로 서비스와 평가의 근거 판이 갈라질 수 있다 ⑤ EC2 1대 상시 구동(`BE-13.md:27`)이면 BE-17-01이 같은 효과를 낸다.
  - 재시작이 잦아 부담이면 **C8**(인스턴스 디스크에 판 키로 만든 스냅샷 캐시)로 간다. 이는 새 후보라 필요해질 때 결정으로 올린다.
- 가정: 하위 작업 ⑤의 "§5.5 보강"은 설계 문서에 BE-17-09 정리를 옮겨 적는 일이다. 문서 쓰기는 이 티켓 작성자(schedule-writer)의 범위 밖이라 Docs 담당(메인 위임)이 한다.
