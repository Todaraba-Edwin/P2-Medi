## 1. 이슈
2026-11-06 사용자 제안: 사용자에게 가장 편한 입력은 **약봉투를 찍어 올리는 사진**과 **말로 하는 마이크 입력**이다. 둘 다 지원하고 싶다. 사진 흐름을 살피다 보니 약봉투 속 약은 **전문의약품(조제약)**이 많은데, e약은요에는 전문의약품이 없어 같이 다뤄야 한다는 이슈가 나왔다.

- **지금 문서에는 없다**: `P2-doc/PJ2-RFP.md`와 `P2-doc/PJ2-PRD.md`에는 사진·음성 입력이 없다(FR-01은 텍스트 질문). 새 요구라 요구사항과 결정이 먼저 필요하다.
- **판정은 영향이 없다**: 병용·연령·임부 금기 판정은 DUR 품목정보·성분 코드와 파일 기준이라 전문의약품도 처리된다. 빠지는 것은 e약은요의 **쉬운 설명 문장**뿐이다.
- **원칙**: 사진·음성은 **입력을 글자로 바꾸는 단계**일 뿐이고, 바뀐 글자(약 이름 목록·질문)는 기존 에이전트 흐름(`identify_drug` 이후)을 그대로 탄다. 도구와 판정 코드는 늘리지 않는다.
- **범위 원칙**: Agent-RAG 핵심(병용·연령·임부, 에이전트·평가)이 먼저이고 이 입력 기능은 확장이다. 미달하면 확장부터 줄인다(CLAUDE.md 1장, RFP 4장).

## 3. 전문의약품 접근 (PRD-08-05)
확인된 사실(근거: `tickets/backend/BE-02.md` 메모, `tickets/doc/RFP-32.md`, `P2-doc/PJ2-API-응답확인.md`).

| 출처 | 전문의약품 | 쓰임 |
|---|---|---|
| e약은요 API | **0건**(전체 4,746건, 이지렉트·에소메졸·미프론·심바로드·로바스크 모두 0건) | 일반의약품의 쉬운 설명 |
| 허가정보 API | 전문·일반 모두(`ETC_OTC_CODE`, 약 42,707건, 제품명 `item_name`으로 검색) | 품목기준코드 얻기, 허가 상세 XML의 효능·용법·주의사항 원문 |
| DUR 품목정보 API | 전문·일반 모두, 품목기준코드 아래 성분과 금기·주의 8종 | 성분 풀기, 금기 판정 근거 |

- 전문의약품은 **허가정보로 찾고, DUR·파일로 판정하고, 라벨은 허가 상세에서** 얻는다. 이미 `identify_drug`·`search_label`·`get_label_section`의 설계 안이다(RFP-22 §6, AG-02).
- **결정됨(PRD-08-05 A, 2026-11-06)**: 쉬운 설명 문장이 없으므로 라벨은 **허가 상세 원문을 그대로 인용**하고 "쉬운 설명 없음(허가사항 원문)"으로 표시한다. 원문은 어렵다는 점이 한계이고, 요약은 LLM이 하되 용량 숫자를 쓰지 않는 규칙(RFP-21-03)은 그대로다.
- 약국 조제약도 허가된 제품이라 상품명으로 추적된다(§3.1 검토).
- 확인하지 못한 것: 허가정보 상세에 모든 전문의약품의 효능·주의사항 본문이 같은 모양으로 있는지는 시나리오 5개 외에 확인하지 않았다(BE-05에서 전수 확인).

### 3.1 약국 조제약 추적 가능성 검토
2026-11-06 사용자 질문: 약국에서 받은 처방약은 보통 제약회사의 상품이므로 추적할 수 있지 않은가, 약봉투에 상품명과 이부프로펜 같은 성분명도 있으니 DUR API를 쓸 수 있는가. 웹 조사와 우리 API 확인 결과로 검토했다.

**결론**: 가능하다. 약국 조제약은 허가된 제품이라 **상품명으로 추적할 수 있고**, 우리 데이터 경로(허가정보 → DUR 품목정보)가 이미 전문의약품을 처리한다. 다만 **약봉투에 성분명이 항상 있는 것은 아니라서** 기본은 상품명, 성분명은 보조로 쓴다.

| 질문 | 확인 결과 | 근거 |
|---|---|---|
| 약봉투에 무엇이 적히나 | **원문 확인(2026-11-06)**: 시행규칙 제18조①이 용기·포장에 적게 한 것은 환자 이름·용법 및 용량, 조제 연월일, 조제자 이름, 조제한 약국 또는 의료기관의 명칭과 소재지다. **약 이름은 필수 기재사항이 아니다.** 실제 봉투의 약품명은 약국 프로그램 관행이라 보도됐다 | [약국·약봉투 조사 4장](../../P2-doc/PJ2-약국-약봉투-조사.md#4-약사법-시행규칙-원문-확인), [데일리팜 43510](https://www.dailypharm.com/user/news/43510) |
| 상품명인가 성분명인가 | 2023-01-31·02-08 서울시약사회가 약학정보원에 낸 건의 내용에 따르면 현재 약봉투에는 **상품명이 표기**된다. 성분명 우선 표기, 상품명 부연으로 바꿔 달라는 건의라서 **성분명은 기본 표기가 아니다** | [데일리팜 31243](https://dailypharm.com/user/news/31243) |
| 복약안내문 | 약 사진·효능·주의사항을 담은 안내문을 약봉투·처방전과 함께 주는 서울시 시범 사업이 있다(시립병원 대상). 모든 약국이 하는 것은 아니다 | [데일리팜 151288](https://m.dailypharm.com/user/news/151288) |
| 우리 API로 상품명을 추적할 수 있나 | 허가정보 `getDrugPrdtPrmsnInq08`의 `item_name`(포함 일치)으로 품목기준코드(`ITEM_SEQ`)와 전문·일반(`ETC_OTC_CODE`)을 얻고, DUR 품목정보 `itemName`·`itemSeq`로 성분(`INGR_CODE`)과 금기·주의를 얻는다. 전문의약품 5개(이지렉트·에소메졸·미프론·심바로드·로바스크)가 이 경로로 확인됐다 | `P2-doc/PJ2-API-응답확인.md` 3장, `tickets/doc/RFP-32.md` |
| 성분명만 있으면 | DUR 성분정보 API는 **`ingrCode`만 필터로 동작하고 `ingrName`은 무시**된다. 그래서 "이부프로펜"이라는 글자를 성분코드로 바꾸는 **사전이 필요**하다(BE-10, DUR 품목정보의 `MATERIAL_NAME`·`INGR_CODE`와 KIDS 파일). 성분 단위 병용금기는 한쪽 성분 쪽으로만 조회되므로 양쪽을 모두 조회한다(BE-03 메모) | `P2-doc/PJ2-API-응답확인.md` 73줄, `tickets/doc/RFP-32.md` |

**설계** (PRD-08-02 A로 결정됨, 2026-11-06)
- **상품명 우선**: 사진에서 읽은 상품명으로 허가정보를 찾아 품목기준코드를 정한다. 이 코드로 성분·연령 문장·라벨까지 이어지므로 성분명만 쓸 때보다 얻는 정보가 많다(제품 단위 연령금기, 허가사항 원문).
- **성분명은 교차검증과 대안**: 봉투에 성분명도 있으면 상품명으로 찾은 성분과 맞춰 본다. 서로 다르면 가부를 말하지 않고 **되묻기 카드**(FR-10)로 후보를 보인다. 상품명을 못 찾았을 때만 성분명으로 사전에서 성분코드를 찾고, 이때는 제품 단위 정보(연령 문장·라벨)가 없다고 표시한다.
- **한계**: 약국마다 프로그램·서식이 달라 표기가 다르고(상품명이 줄거나 규격이 다르게 적힐 수 있음), 약 이름 목록이 봉투가 아닌 복약안내문에 따로 있을 수 있으며, 약국이 **변경조제**를 하면 처방전과 봉투의 약이 다를 수 있다. 사용자가 확인 카드에서 고치도록 한다.
- **확인하지 못한 것**: 실제 약국 약봉투 표본(여러 약국, 상품명·성분명·규격 표기와 한 봉투의 약 수)을 보지 못했다. 사용자가 개인정보를 가린 약봉투 사진 몇 장을 주면 §9의 이미지 입력 시험에 쓴다.

**한국의 약봉투 인식 사례**(검색 결과 기준, 앱 기능은 각 스토어 설명 수준이며 정확도는 확인하지 못했다)
- 처방전·약봉투를 촬영해 약 이름과 복용법을 인식하는 복약 관리 앱이 여럿 있다고 한다(PILLGOOD, 아이약, 약속 등). 약국용 굿팜은 처방전 촬영을 약국 PC로 보내 OCR 처리한다.
- 연구에서는 Google Cloud Vision API로 의약품명을 인식하는 구현이 있었다([koreascience 연구](https://koreascience.kr/article/JAKO202330557777125.page?lang=en), [아이약 앱스토어](https://apps.apple.com/us/app/id6467175742)).
- 의미: 사진으로 약 이름을 얻어 제품 정보와 잇는 방식은 국내에도 흔한 접근이다. 우리의 차이는 인식 뒤 **금기 판정을 코드가 하고 근거를 다는 것**이다.

## 4. 범위와 시점 (PRD-08-01)
- **A (결정됨, 2026-11-06)**: Agent-RAG 핵심 뒤 확장으로 두고, **설계(FR·화면 상태·고지·결정)는 지금 끝낸다.** 구현은 SCH-02 핵심 뒤 또는 SCH-03 확장 구간. 이유: 핵심을 먼저 끝내고 확장부터 줄인다는 원칙을 지키면서, 사용자가 원한 편의성을 문서로 확정해 두면 추후 확장하기 쉽다(PRD-07-01과 같은 방식).
- **B**: 3주 필수. 비전·음성·고지·UI·평가까지 늘어나 핵심이 위험해진다.
- **C**: 3주 뒤. 3주 안에는 설계도 안 한다.
- 참고: 3주 안에 구현하더라도 이 입력 단계는 에이전트 그래프를 바꾸지 않고 **그래프 앞의 변환 함수**로 둘 수 있어 핵심 일정과 분리하기 쉽다(설계 의견, 구현 전 확인 필요).

## 5. 약봉투 사진 입력 (PRD-08-02)
- **A (결정됨, 2026-11-06) 비전 모델이 약 이름 목록을 추출하고 사용자가 확인한다**: 사진 → 비전 가능한 LLM이 "약 이름(과 있으면 용량·제형)"만 JSON으로 → **확인·수정 카드**(이름 목록, 잘못된 것 수정, 빠진 것 추가) → 기존 `identify_drug`부터. 이유: 약봉투 서식이 제각각이고 줄임 표기가 많아 규칙 기반보다 유연하고, 확인 카드가 오인식이 금기 판정으로 번지는 것을 막는다.
- **B 별도 OCR + 사전 매칭**(채택 안 함, 새 OCR 서비스·키는 쓰지 않음): OCR 글자를 제품·성분 사전(BE-10)과 맞춘다. 외부 LLM 전송은 줄지만 OCR 도구 선택·한글 정확도 시험이 필요하다.
- 확인 카드는 되묻기 카드(FR-10)와 같은 틀을 쓴다. 추출 결과가 맞다고 **자동으로 확정하지 않는다**(안전 필수).
- 약봉투의 환자 이름·병원·약국·연락처는 **읽거나 저장하지 않는다**(§7). 추출 지시에 "약 이름·용량·제형만"을 두고, 코드가 출력 필드를 스키마로 제한한다.
- 읽은 상품명은 허가정보로 찾고, 봉투에 성분명도 있으면 교차검증, 불일치·미식별이면 되묻기(§3.1).
- 비전 모델은 **`gpt-6-luna` 하나**다(PRD-08-06 A, 2026-11-06). 이미지 입력 지원을 확인했고, 실제 약봉투 사진 4장에서 긴 변 1400px 확대 전처리를 했을 때 상품명 34/51(3회 합산)이었다. 흐린·작은 사진은 읽지 못하고, 실존하는 다른 제품명을 높은 확신도로 낼 수 있어 확인 카드에는 **추출 원문 + 허가정보 사전 후보 + 기본 선택 없음**을 둔다(§9).

### 5.1 연구 사례와 MediAgent의 방향
2026-11-06 사용자 요청: Google Cloud Vision으로 의약품명을 인식한 연구를 참고해 MediAgent의 방향도 함께 다룬다.

**연구 사례**(출처: [OCR API 성능 비교를 통한 의약품 정보 조회 시스템 구현, koreascience](https://koreascience.kr/article/JAKO202330557777125.page?lang=en), 확인한 것은 **초록 수준**이다)
- 목적: OCR로 복약 정보 검색 시스템을 만들어 고령층의 만성질환 약물 관리를 돕고, 직접 입력의 불편을 없앤다.
- 방식: Google Cloud Vision API로 의약품명을 인식하고, 인식한 이름을 DB에서 찾아 **복약 정보와 복약 일정 관리**를 제공한다.
- 확인하지 못한 것: 입력 사진의 종류(약봉투·처방전·포장), 다른 OCR API와의 비교 결과와 인식 정확도 수치, 조회에 쓴 데이터·공공 API 이름, 한계. 원문 전체를 읽지 못했다.

**같은 점과 다른 점**
| 구분 | 연구 사례 | MediAgent 방향 |
|---|---|---|
| 입력 | 사진에서 약 이름을 인식(OCR) | 같다. 사진·음성에서 약 이름 목록을 얻는다 |
| 인식 뒤 | 이름을 DB에서 조회해 정보·복약 일정 관리 | 조회 뒤 **금기 확인**(병용·연령·임부)과 근거 제시. 복약 일정·알림은 만들지 않는다(복용 여부·용량을 정하지 않는 원칙) |
| 인식 결과 | 인식 결과를 그대로 조회 | **자동 확정하지 않는다.** 확인·수정 카드를 거치고 불일치·미식별은 되묻는다(FR-10) |
| 판정 | 확인하지 못함 | 판정·근거는 **코드가 공공 API·파일에서**, LLM은 쉬운 설명과 도구 선택만 맡는다 |
| 안전 | 확인하지 못함 | 인식 오류가 판정으로 번지지 않게 **확인 전에는 판정 도구를 부르지 못하도록** 코드로 막는다(하네스, `P2-doc/PJ2-Agent-Harness.md` 참조 예정) |
| 초점 | 인식 정확도·편의 | 포트폴리오 목표에 맞춰 **인식 이후의 에이전트 제어·근거·평가**에 둔다 |

**방향 정리**
- 이름 인식 자체(OCR·비전)는 이미 흔한 접근이라 **차별점이 아니다.** MediAgent의 가치는 인식된 이름을 받아 **도구 선택·근거 고정·Validator·하네스로 안전하게 금기를 확인**하는 데 있다. 포트폴리오에서도 이 부분에 시간을 쓴다.
- PRD-08-02의 B(별도 OCR + 사전 매칭)는 이 연구가 택한 방식과 가깝다. 결정은 A(비전 모델, 2026-11-06)이고 **B는 채택하지 않는다.**
- **방향(사용자 2026-11-06)**: Google Cloud Vision은 **참고한 사례일 뿐**이다. 이미지 처리는 **이미 가진 LLM 키**로 한다: `OPENAI_API_KEY`(에이전트 모델 `gpt-6-luna`의 이미지 입력) 또는 `ANTHROPIC_API_KEY`(Claude Haiku 4.5 이미지 입력). 새 OCR 서비스·계정·키는 만들지 않는다. 두 모델 중 무엇으로 할지는 아래 작은 시험(§9)으로 정했다: **`gpt-6-luna` 하나**(PRD-08-06 A, 2026-11-06). Haiku 4.5는 같은 시험에서 확대 조건 12/51로 약해 쓰지 않는다.
- 복약 일정·알림 같은 기능은 연구 사례에서 보이는 편의지만 **범위 밖**이다(진단·처방·복용량 결정을 하지 않는 서비스). 필요해지면 별도 결정으로 올린다.

## 6. 음성(마이크) 입력 (PRD-08-03)
### 6.1 음성 인식 방식
- **A (결정됨, 2026-11-06) 브라우저 음성 인식**(Web Speech API 등): 무료이고 구현이 단순하며 결과가 **글자**로 와서 기존 텍스트 입력과 같게 처리된다. 인식된 글자를 입력창에 채워 **사용자가 보고 보낸다.**
- **B 서버 음성 인식 API**: 정확도 선택지가 넓지만 비용과 외부 전송이 늘고 크레딧 한도(OpenAI $8, 다른 시험과 공유)를 쓴다.
- 확인하지 못한 것: 브라우저별 한국어 인식 정확도와 지원 범위, 음성이 브라우저 제공자 서버로 가는지(제공자별 다를 수 있음)는 확인이 필요하다. 지원하지 않는 브라우저에서는 마이크 버튼을 숨기고 텍스트 입력으로 안내한다.
- 약 이름(제품명)은 음성으로 오인식이 잦을 수 있어 **확인 단계가 안전 장치**다. 응급 표현이 인식되면 확인 전에도 119 안내를 먼저 보일지는 FR-06·PRD-07 규칙과 맞춰 정한다(§11 열린 질문).

## 7. 개인정보와 외부 전송 (PRD-08-04)
- **A (결정됨, 2026-11-06) 저장하지 않는다**: 사진·음성은 브라우저 메모리와 요청 처리 중에만 쓰고 서버·DB·로그에 저장하지 않는다. 대화 상태를 브라우저 메모리에만 두는 PRD-07-01과 같은 원칙이다. 결과의 이름 목록도 사용자가 동의한 프로필 외에는 저장하지 않는다.
- **B 저장**: 재시도·디버깅은 쉽지만 약봉투 속 개인정보를 저장하게 되어 3주 범위에서 부담이 크다.
- **고지**: 외부 AI 서비스 제공자 쪽 보관 고지(PRD-07-02, 동의 관문이 아니라 고지)에 **사진·음성이 외부 AI(비전·음성 인식)로 전송될 수 있음**을 더한다. 학습에 쓰인다고 단정하지 않는다.
- **환자 정보**: 약봉투에는 이름·병원·약국 정보가 있을 수 있다. 읽은 결과에서 약 이름 외 필드를 버린다. 사용자가 사진을 올리기 전에 가려도 된다는 안내를 화면에 둔다(문구는 FE).
- 법률 검토는 추후로 보류한 상태다(사용자 2026-11 결정).
