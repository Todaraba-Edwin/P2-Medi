## 이슈
RFP-01의 'DUR 데이터 확보 점검' 섹션(`tickets/doc/RFP-01.md`)에서 이어지는 티켓이다. 병용·연령·임부 금기 규정이 이 프로젝트의 핵심 데이터인데 확보 경로가 아직 확정되지 않았다.
사용자 관찰: 컨셉이 RAG인데 DUR을 모두 API로 해결하면 에이전트를 만드는 의미가 축소된다. 그래서 확보 경로와 RAG 적용 방식을 함께 정한다.
자세한 비교는 아래 섹션에서 다룬다.

## 왜 이 질문이 중요한가
이 프로젝트가 DUR(Drug Utilization Review, 의약품 처방·조제 점검)을 어떻게 푸느냐에 따라 RAG와 에이전트가 DUR에서 하는 일이 달라진다. 근거는 RFP의 세 곳이다.

| 근거 | RFP 문구 |
|---|---|
| 1장 개요 | 한 줄 정의: "사실은 공공 API·문서에서 가져오고, LLM은 설명과 종합만 맡는 근거 기반 질의응답 에이전트" |
| 3장 목표 2 | "정형(API)·비정형(PDF) 하이브리드 검색" |
| 9장 평가 기준 | 검색 정확도를 Context Precision·Recall(Ragas)로 측정 |

사용자 우려: DUR을 API 호출 한 번으로 끝내면 병용금기 판정이 규칙 조회로 끝난다. 그러면 RAG(검색 → 근거 → 생성)와 에이전트의 역할이 DUR에서 줄어든다.

가정: Context Precision·Recall은 검색 결과의 품질을 재는 지표이므로, 검색을 거치지 않는 API 조회는 이 지표의 측정 대상이 아니다.

## 지금 정해진 것과 아닌 것
**정해진 것** (RFP 문구)
- RFP 12장: 병용금기 판정은 DUR 기준으로 한다(e약은요 상호작용은 문장형이기 때문).
- RFP 5장: 정형 소스인 심평원 DUR은 Tool 호출로 쓰고, 비정형 소스에 "DUR 가이드" PDF가 있다. 다만 포털에서 확인한 DUR API의 제공기관은 식약처다([RFP-01](RFP-01.md)의 'DUR 데이터 확보 점검' 섹션).

**정해지지 않은 것**
- DUR 금기 판정을 런타임 API로 풀지, 문서 RAG로 풀지, 섞을지.

`data/`는 `.gitignore` 대상이라 저장소에 올리지 않는다. 같은 폴더에 임부금기 항목정의서 `CustomExcelView.xlsx`도 있다.

### 실제로 확인한 구조
확인한 값이다(2026-10-30 파일을 직접 열어 집계).

**임부금기 CSV**
- 18,804행이며 한 행이 제품 하나다.
- 항목은 10개다: 성분명, 성분코드, 제품코드, 제품명, 업체명, 급여구분, 고시일자, 고시번호, 금기등급, 상세정보.
- 성분명은 고유 1,686개다.
- 금기등급 값은 1(3,182건), 2(15,563건), M(59건)이다. 뜻은 파일과 항목정의서에 없어 미확인이다. 항목정의서에는 컬럼 정의만 있고 코드표가 없다.
- 상세정보는 고유 1,073개이고 빈값이 688건이다.
- 고시일자는 2016-12-30부터 2026-07-21까지이고, 고시번호는 18종이다.

**병용금기 JSON**
- 배열이며 레코드가 512,464건이다. 한 레코드가 제품 A와 제품 B의 쌍이다.
- 레코드마다 `id`, `text`(자연어 문장, 평균 106자), `metadata`가 있다. `metadata`에는 성분명, 성분코드, 제품코드, 제품명, 업소명(구분 A·B 각각), 고시번호, 고시적용일, 금기사유, 비고가 들어 있다.
- 성분코드 쌍 기준으로 고유 23,619개이고, 쌍마다 고시번호가 하나다.
- 금기사유 문구는 고유 370개, 고시번호는 39종이다.
- 고시적용일은 2004-01-16부터 2026-07-21까지다.

두 파일의 가장 최근 고시일이 모두 2026-07-21이다.

**샘플 (증거)**

| 파일 | 내용 |
|---|---|
| 병용금기 `contra_1` | 5-fluorouracil(중외5-에프유주)와 gimeracil+oteracil potassium+tegafur(티에스원캡슐20). 사유는 gimeracil에 의해 fluoropyrimidine 계열 약물의 대사가 감소해 항암제 독성이 증가한다는 것. 고시번호 20200130, 고시적용일 2020-12-28 |
| 임부금기 첫 행 | 씨앤유캡슐(Chenodeoxycholic acid + Ursodeoxycholic acid). 금기등급 1, 상세정보 '임부 투여금기, 동물실험에서 간독성의 증거 나타남'. 고시일자 2020-12-28, 고시번호 20200130 |

이 샘플은 완료 조건 2번(실제 증거)에 쓸 수 있는 근거다. 단 어느 경로로 갈지 결정되기 전이라 완료 처리는 하지 않는다.

### 설계에 주는 의미
- 가정: 제품 쌍 512,464건은 성분 쌍 23,619개가 제품 수만큼 반복된 것이다(약 22배). 전부 임베딩하면 중복이 많으므로 RAG 청크는 성분 쌍(고시번호 포함) 단위로 줄이는 안이 유력하다. 제품 단위 정보는 제품명을 성분코드로 바꾸는 사전(FR-01 엔티티 정규화, FR-07 오탈자 보정)에 쓴다.
- 가정: 금기사유 문구가 370개뿐이라 병용금기 판정 자체는 성분코드 정확 일치 조회에 가깝고, 의미 검색으로 얻는 이득은 작다. RAG의 가치는 사용자가 쓴 제품명·일반명을 성분으로 연결하고 금기사유와 고시 근거를 붙여 설명하는 데 있다. 이는 선택지 C(정확 매칭으로 판정, RAG는 근거·설명)와 맞는다.
- 가정: 연령 금기는 두 파일에 없다. 식약처 DUR API(특정연령대금기)가 유력하다.
- 가정: 답변과 문서에 출처(한국의약품안전관리원)와 기준일 2026-07-21을 표시한다. 두 파일은 갱신되지 않는 스냅샷이라 이후 고시는 반영되지 않는다.
- 가정: 제품 코드를 쓰지 않는 한 JSON은 한 번에 읽지 말고 스트리밍으로 처리한다.

## 선택지 비교
| 방식 | 사실의 출처 | RAG의 역할 | 장점 | 위험 |
|---|---|---|---|---|
| A API만 | 런타임에 식약처 DUR API 조회 | DUR에서는 없음(e약은요 설명과 검진·사업 PDF에만 쓴다) | 정확하고 최신이며 구현이 단순하다 | DUR 쪽 RAG·평가 대상이 빠져 컨셉이 약해진다. 키·호출 제한에 의존한다 |
| B 문서 RAG만 | DUR 가이드 등 PDF | DUR 판정 전체 | 컨셉에 부합하고 API가 필요 없다 | 성분 쌍을 임베딩 검색에 맡기면 놓치거나 틀릴 수 있어 의료 금기에는 위험하다. PDF 확보와 표 파싱 실패(RFP 12장), 최신성 문제가 있다 |
| C 혼합 | 판정은 API, 금기 사유·고시 근거·예외는 문서 RAG | 근거와 설명. Validator가 API 결과와 문서 근거를 교차 점검 | 정확성과 RAG·에이전트 역할을 함께 확보한다 | 구현량이 늘고, 두 출처가 어긋날 때의 처리 규칙이 필요하다 |
| D API 수집 후 적재 | API를 호출 도구가 아니라 수집 경로로 쓴다. 금기 레코드를 문서화해 Vector DB에 넣고 메타데이터(성분 코드·연도) 필터와 검색으로 사용 | DUR 판정 근거 검색 | 런타임 API 의존이 줄고 RAG 평가가 가능하며, 성분 코드 필터로 정확 매칭을 보완한다 | 갱신 주기에 따라 최신성이 떨어진다(RFP 2장 최신성 문제). 적재 파이프라인이 필요하다. FR-02의 '조회 시각 기록' 해석을 조정해야 한다 |

## API가 있어도 에이전트에 남는 일
가정: API로 판정을 가져오더라도 아래 일은 에이전트가 맡는다.

| 일 | 설명 |
|---|---|
| 엔티티 추출 | 질문에서 약품명·연령·임신 여부를 뽑는다(FR-01) |
| 제품명 → 성분 연결 | 포털의 DUR API가 품목정보와 성분정보로 나뉘어 있어 필요하다 |
| 쌍 조합 조회 | 약이 N개면 쌍 조합마다 조회한다 |
| 도구 선택과 근거 없음 처리 | API와 문서 중 무엇을 쓸지 고르고, 근거가 없으면 모른다고 답한다(FR-08) |
| 종합과 출처 표기 | 결과와 e약은요 서술문·PDF 근거를 종합하고 출처를 붙인다(FR-04) |
| 출력 전 점검 | 답변이 원본과 일치하는지 점검한다(FR-05) |

정리하면 에이전트의 역할은 남지만, '검색해서 근거를 찾는' RAG의 비중은 DUR에서 작아진다. 가정: 이 점에서 사용자 우려는 타당하다.

## 평가에 미치는 영향
RFP 9장의 Context Precision·Recall은 검색(RAG) 지표다. 가정: A를 고르면 DUR 판정은 이 지표로 측정되지 않아 별도 지표(예: 병용금기 판정 정답률)가 필요하다. 가정: C·D는 문서 검색 평가에 DUR 근거가 포함된다.

## 권장안
가정: C를 기본으로 하고 D는 보강 후보로 검토하기를 권장한다. 이유는 다음과 같다.
- 금기 판정의 정확성은 정확 매칭(API 또는 성분 코드)으로 보장한다.
- 문서 RAG는 금기 사유·고시 근거·가이드 설명을 찾아 설명과 출처를 붙인다.
- Validator가 두 출처를 교차 점검하면 DUR에서도 RAG와 에이전트의 역할이 실질이 된다.

단 이 권장은 데이터 확보에 달려 있다. API 활용신청이 막히면 PDF 확보 가능성이 결정을 좌우하고, C의 문서 쪽도 DUR 관련 PDF가 확보되어야 한다. 최종 결정은 사용자가 한다.

가정: 확보한 파일 2종과 식약처 API를 합친 C+D 결합이 유력해졌다. 근거는 "확보한 파일 데이터" 섹션이다.

## 결정할 것
1. DUR 판정은 API로 보장하고 RAG는 근거·설명에 둘지(C), RAG를 판정 자체에 쓸지(B·D).
2. 수집할 DUR PDF의 범위.
3. API 결과와 문서 근거가 어긋날 때 어느 쪽을 따를지.
4. FR-02 문구('API 조회')를 바꿀지.
5. 병용금기 판정 정답률 같은 평가 지표를 더할지.
6. RAG 청크 단위(성분 쌍 / 제품 쌍).
7. 금기등급 1·2·M의 뜻을 어떻게 확인할지.
8. 기준일 2026-07-21을 답변에 어떻게 표시할지.

## 환경변수
식약처 [DUR 품목정보 OpenAPI](https://www.data.go.kr/data/15059486/openapi.do)와 [DUR 성분정보 OpenAPI](https://www.data.go.kr/data/15056780/openapi.do)(성분 단위 버전)용 환경변수가 `.env`에 있다. 이름만 기록하고 값은 쓰지 않는다. `.env`는 직접 읽지 않았고, 변수의 존재는 사용자가 알려준 내용에 근거한다.

| 변수 이름 | 용도 |
|---|---|
| `DURPrdlstInfoService03_END_POINT` | 품목정보 서비스 호출 주소 |
| `DURPrdlstInfoService03_API_KEY` | 품목정보 서비스 인증키 |
| `DURIrdntInfoService03_END_POINT` | 성분정보 서비스 호출 주소 |
| `DURIrdntInfoService03_API_KEY` | 성분정보 서비스 인증키 |

가정: 용도는 변수 이름에서 읽은 것이다.

가정: 변수 이름의 Service 부분이 각 OpenAPI의 서비스 이름과 같다(품목정보는 포털 메타데이터의 기본 URL `.../1471000/DURPrdlstInfoService03`과 일치한다). 성분정보 기본 URL은 확인하지 않았다.
