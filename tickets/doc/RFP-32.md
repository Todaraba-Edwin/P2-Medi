## 1. 이슈
사용자 설명(2026-11-05): mock에서 원했던 일은 **e약은요와 DUR API로 실제 사례에 쓰일 의약품의 데이터를 미리 확보하고, 지금까지 정리한 유저플로우에 필요한 데이터를 미리 가져다 두는 것**이다. 그래야 개발 단계에서 LLM 호출을 아낄 수 있다.

**정정**: RFP-31이 만든 mock은 이 뜻과 달랐다. RFP-31은 LLM이 쓴 문장·judge 출력·질문 틀 같은 **생성 결과 fixture**를 만들었고, 그 안의 값(등급·성분코드·기준일)은 `data/` 파일과 RFP-21(2026-11-01 확인값)에서 가져왔다. **공공 API를 새로 호출해 응답 원문을 확보하지는 않았다.** 이 티켓이 그 빈칸을 채운다. RFP-31 결과는 버리지 않고, 확보한 API 응답 위에서 다시 만들 수 있다(§3).

## 3. 왜 이것이 LLM 호출을 줄이는가
| 층 | 하는 일 | 스냅샷으로 줄어드는 것 |
|---|---|---|
| ① 도구·판정 층(코드) | `identify_drug`·`check_contraindications`·`get_label_section`(AG-02), API 클라이언트(BE-02·03), 판정 테이블 | **LLM이 필요 없는 층**이라 원래 호출이 없지만, 실제 API를 반복 호출하면 한도·시간이 든다. 스냅샷을 모의 서버처럼 쓰면 오프라인으로 테스트한다 |
| ② 에이전트 실행(AG-01) | 모델이 도구를 고르고 도구 결과로 답을 만든다 | 도구 결과를 스냅샷에서 주면 **모델 호출만** 남는다. 입력(질문·도구 결과)이 고정되므로 ③ 캐시가 잘 맞는다 |
| ③ LLM 호출 | 에이전트·Validator·요약 | **record/replay 캐시**(RFP-32-02): 모델·프롬프트·인자 해시를 키로 응답을 저장해 같은 입력의 반복 호출을 막는다. 개발용이고 평가 측정(AG-11·12·14)에서는 끈다 |
| ④ 이미 만든 mock(RFP-31) | `/chat` 응답 fixture 등 | 값을 스냅샷에서 가져오도록 다시 만들어 **API 응답 → 응답 fixture**가 하나로 이어지게 한다 |

## 5. 규칙
- 키는 환경변수로만 읽는다(`.env`는 사람이 만든 값이라 에이전트가 열지 않는다, CLAUDE.md 3장). 스냅샷·로그에 **인증키가 들어가지 않게** 요청 URL에서 `serviceKey`를 지운 뒤 저장한다.
- **로컬 전용**: `mock/api_snapshots/`는 `.gitignore`의 `mock/` 아래라 커밋하지 않는다. 공공 API 응답 원문의 재배포·이용 조건을 확인하지 않았다(법률 검토 보류). 커밋 대상은 스크립트뿐이다.
- 호출 간격을 두고(속도 제한), 같은 요청은 다시 호출하지 않는다(요청 해시 → 파일). 실패(HTTP 오류·한도)는 그대로 기록하고 재시도 횟수를 제한한다.
- 응답 원문(JSON/XML)을 그대로 보존하고, 정규화한 색인은 별도 파일로 둔다(원문 수정 금지).
- 평가 시험셋 후보(`data/credit_use/pool_test.jsonl`)는 열지 않는다. 시나리오·페르소나 약은 평가 세트와 별개다.
- 스냅샷 기준일(조회 시각)을 화면·응답의 기준일 표시와 구분한다. 스냅샷은 **개발용이며 서비스 근거 데이터가 아니다**(서비스는 파일 1차 + API 병기, RFP-17).
