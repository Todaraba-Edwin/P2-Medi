## 1. 이슈
강의 「Agent 101」(교안 `04_Agent_101.pdf`, 강의 정리 `PJ2-PreWeek-Agent101.md`)을 기준으로 MediAgent의 컨셉과 8.1절 유저플로우를 점검한다. 구상은 ReAct 패턴 + LangChain 1.x(`create_agent`) + OpenAI `gpt-6-luna`다. 긴 내용이라 RFP에는 요약만 두고([8.2절](../../P2-doc/PJ2-RFP.md#82-agent-설계-점검-agent-101-기준)) 점검표·도구·평가·결정은 이 티켓에서 관리한다. Pre-Week 논의 자료이고 코드는 없다.

**한 줄 판정**: 컨셉(근거 기반 Agent-RAG, 판정은 코드·설명은 LLM)은 강의 내용과 맞는다. 다만 지금 문서에는 **ReAct가 들어갈 자리가 없다.** 8.1의 8단계는 코드가 순서를 정하는 고정 파이프라인(Workflow)이다. ReAct를 쓰려면 "어디까지 LLM이 고르고 어디부터 코드가 강제하는가"를 정해야 하고, 그 답이 아래 §5다.

> 점검 근거: 강의 정리는 Part II (2)절(create_agent)까지만 있어서 LangGraph·Agentic RAG·Middleware·평가·Harness는 교안 PDF 51~91쪽을 직접 읽었다. 쪽 번호는 교안 기준이다.

## 5. 제안 컨셉: 하네스가 감싼 단일 ReAct 에이전트


```
[입력] → [Guardrail·응급 감지: 코드] → [Router: structured output, fallback]
            범위 외·진단·처방 요청 ▶ 안내 전환(ReAct 안 탐)
                                  │
         ┌────────── ReAct 에이전트 (LangGraph 그래프, gpt-6-luna, 도구 6개) ──────────┐
         │  Thought → Action(도구 호출) → Observation → … → 최종 답(structured output) │
         │  step 상한·같은 호출 반복 감지·도구별 호출 상한(middleware)                │
         └──────────────────────────────┬─────────────────────────────────────────┘
                        종료 직전 sensor(코드): 필수 도구 호출 여부, 증거 ID 존재
                           미충족 ▶ 에이전트로 되돌림(최대 1~2회) → 그래도 안 되면 안내 전환
                                  │
[Validator: 문장↔증거 계층 검사] → [마무리: 고정 문구·119·기준일·약국·약사 안내: 코드] → [응답]
```

- **LLM이 고르는 것**: 어떤 도구를 어떤 순서로 부를지, 검색어를 어떻게 고칠지, 결과가 모자라면 다시 찾을지, 어떻게 쉽게 설명할지.
- **코드가 정하는 것**: 금기 판정 자체(성분코드 정확 일치), 응급 119, 고정 문구, 기준일, 호출 상한, 필수 도구 호출 확인. 이 판정을 LLM에 맡기면 같은 질문에 결과가 달라질 수 있어(4번) 도구 안으로 넣는다.
- **8.1 단계와의 대응**: 1(입력 정리)은 Router, 2~5(제품·성분·금기·근거)는 ReAct의 도구 호출, 6(요약)은 ReAct의 최종 답, 7(검증)과 8(마무리)은 바깥 노드다. 8.1의 단계 번호와 예외 경로 표는 그대로 쓴다. 바뀌는 것은 2~5의 **순서를 코드가 아니라 에이전트가 정한다**는 점과, 순서가 어긋나도 필수 단계가 빠지지 않게 종료 직전 sensor가 막는다는 점이다.
- **ReAct가 고정 파이프라인보다 나은 곳**(이 분기들이 포트폴리오에서 "Agent를 쓴 이유"가 된다):

| 질문 유형 | Observation이 알려 주는 것 | 에이전트가 하는 일 |
|---|---|---|
| 오탈자 "타이레놀 콜드에쓰" | 식별 결과 0건 | 이름을 고쳐 다시 찾음(교안 20쪽 HotpotQA의 검색어 수정과 같은 구조) |
| 모호 "타이레놀 먹어도 돼요?" | 후보 7개 | 가부를 말하지 않고 되묻기 카드(최종 답의 한 형태)로 종료 |
| 오정보 "타이레놀이랑 와파린은 같이 먹으면 안 되죠?" | 병용금기 쌍 없음 | 라벨 근거를 추가로 찾아 "금기 목록에 없음 + 라벨 문장"으로 답함 |
| 근거 없음 | 증거 청크 0건 | 검색어를 바꿔 1회 재검색, 그래도 없으면 "근거 없음" |
| 정상(두 약, 임신) | 모두 한 번에 풀림 | 도구를 순서대로 부르고 종료. **이 유형은 Workflow와 차이가 없다** |

## 6. 도구 6개 (RFP-22-01 A로 코퍼스별 분리)


| 도구 | 입력 | 돌려주는 것 (필드 제한, 청크는 ID 포함) | 내부 |
|---|---|---|---|
| `identify_drug` | 사용자가 쓴 약 이름 | 후보 최대 5개: 품목기준코드, 제품명, 제형, 연령 문장, 성분 목록(성분코드, 연결 근거: M-코드/이름), 일반·전문 구분. 못 찾으면 "없음 + 다시 쓸 이름" | 사전, e약은요, 허가정보 주성분(코드) |

- 되묻기(`ClarifyCard`)는 도구가 아니라 최종 답의 한 형태다(후보가 여럿이면 가부를 말하지 않고 질문 1개로 종료).
- 병용·연령·임부를 `check_contraindications` 한 번에 묶는 이유: step이 늘면 오류가 곱으로 쌓인다(1번). 두 약을 한 번에 식별하는 호출을 병렬로 내면 정상 질문은 모델 호출 약 4회(식별 → 판정 → 근거 → 최종 답)로 끝난다. 교안의 단순 계산(step당 95%)으로 0.95⁴ ≈ 81%다. 이 95%는 설명용 가정이지 측정값이 아니다. 병렬 도구 호출이 `gpt-6-luna`에서 되는지는 확인하지 못했다.
- 도구가 돌려주는 값은 **ID가 붙은 근거**다. 최종 답은 문장마다 증거 ID를 달고, Validator가 문장 유형에 허용된 계층인지 검사한다(8.1 7단계, 설계 문서의 허용 계층 표).

## 10. 구현 순서 제안

1. 1주차: 도구 6개와 판정 테이블·사전·코퍼스(근거 계층은 설계 문서 11장 순서대로 사전·L2·L1 먼저). 에이전트 없이 도구 단위 테스트.
2. 2주차 앞: 최소 ReAct 그래프(또는 `create_agent`, RFP-22-03) + 도구 + 시스템 프롬프트 + 모델 호출 상한 + Guardrail·마무리 코드만으로 **기준선을 먼저 잰다**. 안전 필수 장치(고정 문구, 119 병행, 안전 단정 금지 코드 검사)는 기준선에도 넣는다. 성능 개선용 장치(종료 sensor, grade, 분해 검색, loop 감지)는 기준선의 실패를 본 뒤 더한다(RFP-22-08).
3. 2주차 뒤: 기준선의 실패를 경로 기록으로 분류하고, 실패 1개당 장치 하나(종료 sensor, loop 감지, Validator 규칙 등)를 더한다.
4. 3주차: 재측정, (가) 대 (나) 비교, 장치가 실제로 막은 사례를 리포트에 기록.
5. 3주 이후(범위 밖, RFP-22-10): Reflexion 확장 — Actor(ReAct 그래프) / Evaluator(코드 검사 + Claude Sonnet judge) / Self-reflection(실패 회고문을 메모리에 저장해 다음 시도에 사용)을 더하고, ReAct와 같은 평가 세트로 비교한다. 시간이 남을 때만 하며 3주 완료 기준에는 넣지 않는다.

### 12.3 11-02 논의 항목
**RFP-22-01. 근거 검색 도구: 코퍼스별 도구 vs 주장 유형 인자**
- 강의 방식(코퍼스별 도구): `search_notice`(고시 L1), `search_reason`(사유 L2), `search_label`(라벨 L3) 식으로 나눈다. docstring이 경계를 말하고, 어느 도구를 불렀는지가 경로 평가에 그대로 남는다. 도구가 늘어 4개가 6개 안팎이 된다.
- 현재 안(도구 하나 + `주장 유형` 인자): 도구 수가 적고 "분해 검색"을 인자로 강제한다. 대신 인자를 틀리게 고르는 경우를 따로 검증해야 한다.
- 제안: **코퍼스별 도구**로 시작한다. 강의 실습과 같은 구조라 동작이 검증되어 있고 경로 평가가 쉽다. 도구가 늘면 step이 늘 수 있으므로 병렬 호출이 되는지 먼저 본다.

**RFP-22-02. "근거 없음"의 기준: 0건이 아니라 grade**
- 정확 일치·필터 경로(성분코드로 판정 테이블, 약 ID로 청크를 거는 경우)는 0건이 곧 "없음"이다. 코드가 판정한다.
- 의미 검색 경로(라벨 문장 찾기)는 항상 k개가 나오므로 **관련성 판정**이 필요하다. 후보는 (가) LLM grade 노드(강의 방식), (나) 코드 검사(청크의 약·성분 ID가 질문 대상과 일치하는지) 먼저, 애매하면 LLM grade.
- 제안: (나) 먼저, (가)는 보조. LLM이 판정하면 같은 질문에도 판정이 달라질 수 있어서(교안 36쪽의 라우팅과 같은 이유) 코드로 걸러낼 수 있는 것은 코드로 한다. 이 결정은 FR-08, 8.1 5단계, AG-09(근거 없음 처리)에 영향을 준다.

**RFP-22-03. 오케스트레이션 다시 보기** (2026-11-02 사용자 방향: 프로젝트는 LangGraph로 구성. 아래는 그 전에 쓴 비교이고, 남은 선택은 기준선 형태 A) 최소 ReAct 그래프 / B) `create_agent`다)
- 노트북 1-2 구조(`create_agent` + 도구 + system prompt)가 가장 단순한 기준선이다. 교안 91쪽의 "단순하게 시작 → 실패 관찰 → 부품 추가"와 맞고, **기준선 대 개선 전후 비교**(RFP 9장)의 "전"으로 쓰기 좋다.
- 개선 단계에서 Guardrail·Router·종료 sensor·grade·Validator를 넣으려면 루프를 바꿔야 한다. 이때 노트북 1-3에서 연습한 대로 `StateGraph`로 ReAct를 직접 조립하고, 종료 sensor는 `tools_condition` 같은 **routing 함수**(도구 호출이 없을 때 필수 도구를 불렀는지 확인하고 아니면 `model`로 되돌림)로 구현한다. 이 구성은 강의에서 연습한 부품만으로 만들어진다.
- 당시 권장: "LangGraph 바깥 틀 + `create_agent` 노드"(강의 미연습)보다 **기준선 `create_agent` → 개선 LangGraph 직접 조립** 순서였다. 사용자 방향이 LangGraph이므로 A(처음부터 최소 ReAct 그래프)가 같은 부품(`StateGraph`, `ToolNode`, `tools_condition`)으로 바로 시작할 수 있어 더 단순할 수 있다. 이 경우 `create_agent`가 주던 편의(system_prompt, 호출 상한, structured output)를 State 필드와 노드로 직접 채워야 하는 비용이 있다. 이 비용은 아직 재 보지 않았다.
- 포트폴리오 관점: "단순 Agent 대 하네스 추가 Agent의 측정 차이"가 Agent-RAG 설계·구현·평가 경험이 된다.

**RFP-22-04. 범위: 3주·1인에서 어디까지 LangGraph로 짤까**

### 14.1 RFP-22-02 grade(관련성 판정)란 무엇인가
**한 줄 뜻**: 검색이 가져온 조각이 "정말 이 질문에 답할 근거인가"를 답을 쓰기 **전에** 따지는 단계다. 강의의 Corrective RAG에서는 "충분(RELEVANT) / 부족(NOT_RELEVANT)"으로 나누고, 부족이면 답을 지어내지 않고 "근거를 찾을 수 없습니다"로 안내(fallback)한다.

**왜 필요한가**: 의미 검색(벡터 검색)은 항상 "가장 비슷한 k개"를 돌려준다. 규정에 없는 질문에도 비슷해 보이는 조각이 나오므로, 그대로 답을 만들면 그럴듯한 틀린 답(환각)이 된다. 강의 표현으로 "검색 결과가 있다 ≠ 답할 근거가 있다"이다. 반면 성분코드로 판정 테이블을 조회하는 경로는 0건이 곧 "없음"이라 grade가 필요 없다(코드가 판정). grade는 **라벨 문장 같은 의미 검색 경로**에만 해당한다.

**예시**: 질문 "타이레놀정500 임신 중 먹어도 돼요?"에 검색이 조각 3개를 돌려줬다고 하자.
| 조각 | 코드 검사(A) | 결과 |
|---|---|---|
| 타이레놀정500 주의사항 "임부 또는 수유부 … 상의하십시오" | 약 ID 일치, 청크 종류(주의사항) 일치 | 통과 |
| 콜드-에스정 주의사항 | 약 ID 불일치 | 탈락 |
| 타이레놀정500 용법 문장(임신 언급 없음) | 약 ID는 일치하지만 질문이 묻는 내용이 있는지 코드로 알 수 없음 | 애매 → A에서는 이때만 LLM에게 "이 문장이 임신 관련 주의를 담고 있는가?"를 묻는다 |

**두 선택지**
| | A (★ 권장) 코드 검사 먼저, 애매하면 LLM grade | B 처음부터 LLM grade만 |
|---|---|---|
| 방식 | 청크의 약·성분 ID, 청크 종류(layer), 점수 같은 규칙을 코드로 검사. 코드가 판단하지 못하는 경우만 LLM | 모든 조각을 LLM이 충분/부족으로 판정(강의 숙제와 같은 구조) |
| 장점 | 같은 질문이면 같은 결과, 비용·지연이 적다(교안 36쪽: LLM 판단은 기준대로 안 따를 수 있음) | 코드 규칙을 만들 필요가 없어 구현이 단순 |
| 단점 | 검사 규칙을 직접 만들어야 한다 | 같은 질문에도 판정이 달라질 수 있고, 호출이 늘어 step 오류가 쌓인다(교안 9쪽) |

**답이 바꾸는 것**: "근거 없음"이 나오는 기준(PJ2-RFP.md 6장 FR-08, 8.1 5단계), AG-03(검색 도구)·AG-09(근거 없음 처리)의 구현 방식. 어느 쪽이든 판정이 틀려 근거 없는 문장이 나가는 것은 Validator(AG-07)가 한 번 더 막는다.

### 14.2 RFP-22-06 trace(도구 호출 기록)와 합성 평가 질문에만 켠다는 뜻
**trace란**: 에이전트가 한 질문을 처리하는 동안의 **전체 기록**이다. 어떤 도구를 어떤 입력(검색어)으로 불렀고, 무엇을 돌려받았고, 모델이 어떤 순서로 판단했는지, 걸린 시간과 토큰이 남는다(교안 63쪽 Tracing). 쓰임: 오답의 원인 찾기, 경로 평가(필수 도구를 불렀는가, RFP-22 §9), 기준선의 실패 분석 → 개선. 이 프로젝트의 평가·개선은 trace가 있어야 한다.

**어디가 원칙과 충돌하나**: PJ2-RFP.md 7장 개인정보는 "질문·대화 내용은 저장하지 않고 로그에도 남기지 않는다"고 한다. 그런데 trace에는 사용자가 쓴 질문 문장(예: "임신 14주인데 열이 나요…")과 약 이름이 **그대로** 들어간다. 실제 사용자 질문에 trace를 켜면 이 원칙을 어기게 되고, LangSmith·Langfuse 같은 외부 trace 서비스를 쓰면 질문이 외부로 전송될 수도 있다(해당 서비스의 데이터 정책은 확인하지 못했다).

**"합성 평가 질문에만 켬"의 뜻**: 우리가 직접 만든 **가상의 질문**(평가 세트 20문항, RFP-21 §4.2 페르소나 질문)을 평가 스크립트(BE-08)로 돌릴 때만 trace를 켠다. 실제 사용자가 입력하는 질문에는 trace 코드가 아예 돌지 않도록 설정(평가 모드 / 서비스 모드)으로 끈다. 그러면 경로 분석과 개선은 가능하고, 실제 사용자 질문은 남지 않아 원칙과 충돌하지 않는다.

**두 선택지**
| | A (★ 권장) 합성 평가 질문에만 켠다 | B 마스킹 후 전체 |
|---|---|---|
| 방식 | 평가 모드에서만 trace 기록 | 실제 입력도 이름·날짜 등을 가리고 기록 |
| 장점 | 원칙과 충돌 없음, 구현 단순 | 실제 사용 중 실패도 분석 가능 |
| 단점 | 실제 사용 중 생긴 실패는 trace로 볼 수 없음 | 마스킹이 완벽하지 않으면 건강 정보가 남아 원칙 위반 위험, 포트폴리오 데모에는 불필요 |

**구현 때 정할 것**: trace를 로컬 파일에 둘지 LangSmith·Langfuse를 쓸지, 서비스 모드에서도 질문 내용이 없는 오류 건수·응답 시간 같은 지표를 남길지. 합성 질문만 다루므로 어느 쪽이든 원칙 위반은 아니다.
