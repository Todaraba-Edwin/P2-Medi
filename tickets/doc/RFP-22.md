## 이슈
강의 「Agent 101」(교안 `04_Agent_101.pdf`, 강의 정리 `PJ2-PreWeek-Agent101.md`)을 기준으로 MediAgent의 컨셉과 8.1절 유저플로우를 점검한다. 구상은 ReAct 패턴 + LangChain 1.x(`create_agent`) + OpenAI `gpt-6-luna`다. 긴 내용이라 RFP에는 요약만 두고([8.2절](../../P2-doc/PJ2-RFP.md#82-agent-설계-점검-agent-101-기준)) 점검표·도구·평가·결정은 이 티켓에서 관리한다. Pre-Week 논의 자료이고 코드는 없다.

**한 줄 판정**: 컨셉(근거 기반 Agent-RAG, 판정은 코드·설명은 LLM)은 강의 내용과 맞는다. 다만 지금 문서에는 **ReAct가 들어갈 자리가 없다.** 8.1의 8단계는 코드가 순서를 정하는 고정 파이프라인(Workflow)이다. ReAct를 쓰려면 "어디까지 LLM이 고르고 어디부터 코드가 강제하는가"를 정해야 하고, 그 답이 아래 (2)다.

> 점검 근거: 강의 정리는 Part II (2)절(create_agent)까지만 있어서 LangGraph·Agentic RAG·Middleware·평가·Harness는 교안 PDF 51~91쪽을 직접 읽었다. 쪽 번호는 교안 기준이다.

## (2) 제안 컨셉: 하네스가 감싼 단일 ReAct 에이전트


```
[입력] → [Guardrail·응급 감지: 코드] → [Router: structured output, fallback]
            범위 외·진단·처방 요청 ▶ 안내 전환(ReAct 안 탐)
                                  │
         ┌────────── ReAct 에이전트 (create_agent, gpt-6-luna, 도구 4개) ──────────┐
         │  Thought → Action(도구 호출) → Observation → … → 최종 답(structured output) │
         │  step 상한·같은 호출 반복 감지·도구별 호출 상한(middleware)                │
         └──────────────────────────────┬─────────────────────────────────────────┘
                        종료 직전 sensor(코드): 필수 도구 호출 여부, 증거 ID 존재
                           미충족 ▶ 에이전트로 되돌림(최대 1~2회) → 그래도 안 되면 안내 전환
                                  │
[Validator: 문장↔증거 계층 검사] → [마무리: 고정 문구·119·기준일·약국·약사 안내: 코드] → [응답]
```

- **LLM이 고르는 것**: 어떤 도구를 어떤 순서로 부를지, 검색어를 어떻게 고칠지, 결과가 모자라면 다시 찾을지, 어떻게 쉽게 설명할지.
- **코드가 정하는 것**: 금기 판정 자체(성분코드 정확 일치), 응급 119, 고정 문구, 기준일, 호출 상한, 필수 도구 호출 확인. 이 판정을 LLM에 맡기면 같은 질문에 결과가 달라질 수 있어(4번) 도구 안으로 넣는다.
- **8.1 단계와의 대응**: 1(입력 정리)은 Router, 2~5(제품·성분·금기·근거)는 ReAct의 도구 호출, 6(요약)은 ReAct의 최종 답, 7(검증)과 8(마무리)은 바깥 노드다. 8.1의 단계 번호와 예외 경로 표는 그대로 쓴다. 바뀌는 것은 2~5의 **순서를 코드가 아니라 에이전트가 정한다**는 점과, 순서가 어긋나도 필수 단계가 빠지지 않게 종료 직전 sensor가 막는다는 점이다.
- **ReAct가 고정 파이프라인보다 나은 곳**(이 분기들이 포트폴리오에서 "Agent를 쓴 이유"가 된다):

| 질문 유형 | Observation이 알려 주는 것 | 에이전트가 하는 일 |
|---|---|---|
| 오탈자 "타이레놀 콜드에쓰" | 식별 결과 0건 | 이름을 고쳐 다시 찾음(교안 20쪽 HotpotQA의 검색어 수정과 같은 구조) |
| 모호 "타이레놀 먹어도 돼요?" | 후보 7개 | 가부를 말하지 않고 되묻기 카드(최종 답의 한 형태)로 종료 |
| 오정보 "타이레놀이랑 와파린은 같이 먹으면 안 되죠?" | 병용금기 쌍 없음 | 라벨 근거를 추가로 찾아 "금기 목록에 없음 + 라벨 문장"으로 답함 |
| 근거 없음 | 증거 청크 0건 | 검색어를 바꿔 1회 재검색, 그래도 없으면 "근거 없음" |
| 정상(두 약, 임신) | 모두 한 번에 풀림 | 도구를 순서대로 부르고 종료. **이 유형은 Workflow와 차이가 없다** |

## (3) 도구 4개(초안)


| 도구 | 입력 | 돌려주는 것 (필드 제한, 청크는 ID 포함) | 내부 |
|---|---|---|---|
| `identify_drug` | 사용자가 쓴 약 이름 | 후보 최대 5개: 품목기준코드, 제품명, 제형, 연령 문장, 성분 목록(성분코드, 연결 근거: M-코드/이름), 일반·전문 구분. 못 찾으면 "없음 + 다시 쓸 이름" | 사전, e약은요, 허가정보 주성분(코드) |
| `check_contraindications` | 성분코드 목록, 프로필(연령, 임신 여부) | 병용·연령·임부 판정과 성분 중복: 해당/목록에 없음, 등급, 고시번호·일자, 파일·API 일치 여부, 기준일 | 판정 테이블(파일 1차) + 성분정보 API 병기 |
| `search_evidence` | 주장 유형(등급 정의/사유/제품 주의), 약·성분 ID | 증거 청크 최대 3개: 청크 ID, 계층(L1/L2/L3), 원문, 출처, 기준일 | 근거 코퍼스. 주장 유형을 인자로 받아 분해 검색을 강제 |
| `get_label_section` | 품목기준코드, 절 이름 | 해당 절의 본문(길이 제한) | 허가정보 허가 상세, e약은요 |

- 되묻기(`ClarifyCard`)는 도구가 아니라 최종 답의 한 형태다(후보가 여럿이면 가부를 말하지 않고 질문 1개로 종료).
- 병용·연령·임부를 `check_contraindications` 한 번에 묶는 이유: step이 늘면 오류가 곱으로 쌓인다(1번). 두 약을 한 번에 식별하는 호출을 병렬로 내면 정상 질문은 모델 호출 약 4회(식별 → 판정 → 근거 → 최종 답)로 끝난다. 교안의 단순 계산(step당 95%)으로 0.95⁴ ≈ 81%다. 이 95%는 설명용 가정이지 측정값이 아니다. 병렬 도구 호출이 `gpt-6-luna`에서 되는지는 확인하지 못했다.
- 도구가 돌려주는 값은 **ID가 붙은 근거**다. 최종 답은 문장마다 증거 ID를 달고, Validator가 문장 유형에 허용된 계층인지 검사한다(8.1 7단계, 설계 문서의 허용 계층 표).

## (5) 문서 충돌과 장치


| 문제 | 장치 |
|---|---|
| 에이전트가 판정 도구를 건너뜀(교안 65쪽의 "규정 확인 생략") | 종료 직전 sensor가 필수 도구 호출을 확인하고 어긋나면 에이전트로 되돌린다(교안 78쪽: `after_model`에서 model로 되돌림). 경로 평가에도 같은 기준을 쓴다 |
| 무한 루프·같은 검색 반복(교안 81쪽) | 모델 호출 상한, 도구별 호출 상한, 같은 호출 반복 감지. 상한 숫자는 초안 값(모델 호출 8회 안팎)이며 기준선 측정 뒤 정한다. 상한에 닿으면 "근거 없음/안내 전환" |
| MAST 1단계(명세 위반·종료 조건 모름) | 시스템 프롬프트와 도구 설명에 금지 사항을 적는 것은 guide일 뿐이라, 같은 내용을 sensor로도 둔다(6번) |
| MAST 2단계(정보 누락) | 단일 에이전트라 해당 없음. 이것이 멀티에이전트를 쓰지 않는 이유 중 하나다 |
| MAST 3단계(조기 종료, 검증 누락) | 종료 직전 sensor + Validator |
| 되묻기 멀티턴 vs "대화 비저장" | 메모리 안 checkpointer(`thread_id` = 세션), 세션이 끝나면 폐기. 프로필(확장)은 별도 저장이고 대화는 저장하지 않는다 |
| trace vs "로그에도 남기지 않음" | trace(LangSmith·Langfuse 등)는 합성 평가 질문 실행에만 쓴다. 실제 입력에는 끄거나, 마스킹 middleware를 쓴다(교안 52쪽 `PIIMiddleware`가 이 용도인지는 확인하지 못했다) |

## (6) 평가 보완


| 보조 지표 | 측정 | 비고 |
|---|---|---|
| 경로 평가 | 질문마다 기대 경로(필수 도구, 금지 도구, 호출 수 상한)와 실제 경로 비교: Pass / Warn(중복) / Fail(필수 도구 생략) | 최종 답이 맞아도 판정 도구를 안 불렀으면 Fail. 라우팅 정확도를 이것으로 확장 |
| `pass^3` | 같은 질문 3번 모두 성공한 비율. 안전 핵심 문항(응급·금기 해당·금기 목록에 없음)에만 | 확률적 생성이라 1번 성공은 성공이 아님. 비용이 3배라 핵심 문항만 |
| 비교 실험 | 같은 평가 세트를 **(가) 고정 파이프라인 / (나) ReAct 에이전트**로 돌려 (2)의 분기 유형(오탈자·모호·오정보·근거 없음)별로 비교 | "더 좋은 모델보다 더 좋은 workflow"(교안 28쪽)를 우리 데이터로 확인하는 실험. 9장의 LLM 단독 / 규칙·조회만 / 전체 비교와 같은 틀에 조건 하나를 더하는 것 |

평가셋은 교안 기준 20문항으로 시작할 수 있다. 문항 수는 RFP-15에서 정한다.

## (7) 구현 순서 제안

1. 1주차: 도구 4개와 판정 테이블·사전·코퍼스(근거 계층은 설계 문서 11장 순서대로 사전·L2·L1 먼저). 에이전트 없이 도구 단위 테스트.
2. 2주차 앞: `create_agent` + 도구 + 시스템 프롬프트 + 모델 호출 상한 + Guardrail·마무리 코드만으로 **기준선을 먼저 잰다**.
3. 2주차 뒤: 기준선의 실패를 경로 기록으로 분류하고, 실패 1개당 장치 하나(종료 sensor, loop 감지, Validator 규칙 등)를 더한다.
4. 3주차: 재측정, (가) 대 (나) 비교, 장치가 실제로 막은 사례를 리포트에 기록.
