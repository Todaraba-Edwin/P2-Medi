## 1. 이슈
2026-11-03 사용자 요청: Pre-Week에서 더 다뤄야 할 부분으로 **에이전트 디자인 패턴**을 올린다. 지금 요구서는 Router로 구분하는 설계처럼 읽히는데, Supervisor를 두고 서브에이전트에게 위임하는 설계도 있다. **현재까지의 제품요구서(요구서 `PJ2-RFP.md`)에 비추어 어느 쪽이 프로젝트에 적합한지** 분석하고 결정한다.

미리 말하면 분석 결과는 "**지금 설계(단일 ReAct 에이전트 + 코드가 강제하는 입구·출구)를 유지하고, Supervisor는 기준선 실패를 본 뒤 필요할 때 도입**"이다. 다만 분석 중에 **요구서와 티켓이 Router에 대해 두 가지 설계를 섞어 쓰고 있다**는 것을 찾았다(§5). 이것을 먼저 정리해야 AG-05·AG-01을 구현할 때 흔들리지 않는다.

## 4. 패턴 정리와 현재 요구


### 4.1 용어와 공식 문서 확인
> LangChain·LangGraph 공식 문서를 조회해 확인했다(조회 도구의 요약을 읽은 것이라 세부 수치는 원문으로 다시 확인할 것).

| 패턴 | 뜻 | 호출 수(공식 문서 비교표, 단일 요청) |
|---|---|---|
| **Router** | 라우팅 단계가 입력을 분류해 **전문화된 에이전트로 보낸다** | 3회 |
| **단일 에이전트(+Skills)** | 한 에이전트가 도구를 고르고, 필요한 맥락은 그때그때 불러온다 | 3회(Skills) |
| **Subagents(= Supervisor)** | 메인(감독) 에이전트가 **서브에이전트를 도구처럼 호출**하고 모든 라우팅이 메인을 거친다. LangGraph에서는 `langgraph-supervisor`의 `create_supervisor`와 `create_handoff_tool`(handoff 도구로 제어를 넘김), 또는 서브에이전트를 `@tool`로 감싸는 방식으로 만든다 | 4회 |
| **Handoffs** | 도구 호출이 상태를 바꿔 다음 에이전트로 제어를 넘긴다 | 3회 |

- 공식 문서는 멀티에이전트가 가치 있는 경우를 **컨텍스트 관리(전문 지식이 컨텍스트에 안 들어갈 때), 개발 분업, 병렬화**로 꼽고, 특히 "**단일 에이전트가 도구가 너무 많아 잘못된 결정을 할 때**"를 든다.
- `create_supervisor`에는 서브에이전트 출력을 어떻게 이어 줄지 정하는 `output_mode`가 있다(`full_history`: 전체 대화 / `last_message`: 마지막 메시지만).
- 이 티켓에서 "Supervisor"는 위 Subagents(감독형) 패턴을 가리킨다.

### 4.2 현재 요구서가 요구하는 것
| 요건(요구서 위치) | 설계에 주는 의미 |
|---|---|
| 도메인은 하나(약 금기 확인)이고 도구는 6개(RFP-22 §6) | 도구가 적어 "도구가 너무 많아 오선택" 조건에 해당하지 않는다 |
| **판정·고정 문구·119·Validator는 코드**, LLM은 도구 선택·근거 탐색·쉬운 설명(1장, 8.2절) | LLM 에이전트의 자율 영역이 좁다. 서브에이전트에 판정을 맡기면 "판정은 코드" 원칙과 충돌한다 |
| 모든 답에 근거, 근거 고정, Validator가 원문 대조(FR-04·05) | 근거 청크 ID·원문이 끝까지 전달되어야 한다. 서브에이전트가 요약해서 넘기면 근거가 흐려진다 |
| 모델 호출 상한 8회, 경로 평가·`pass^3`(RFP-22-05, 9장) | 호출이 늘수록 단계 오류가 곱셈으로 쌓이고(교안 0.95^n) 상한에 닿기 쉽다 |
| 평가: 에이전트가 필요한 이유를 C0/C1/C1+/C2로 증명(RFP-23-02), 약 150문항 | 비교 대상 구조가 늘면 문항·반복·비용이 곱해진다(9.7절 예산 미측정) |
| 3주·1인, 기준선 먼저 측정하고 실패를 본 뒤 개선(RFP-22-03, 22-08) | 처음부터 복잡한 구조는 기준선 측정 자체를 늦춘다 |
| 확장(중복·용량·수유부·노인 주의, 프로필)은 핵심 뒤에만(4장) | 도구·역할이 늘어날 때가 서브에이전트 분리의 후보 시점이다 |

## 5. 현재 요구서·티켓의 Router 설계 불일치
**두 문서군이 서로 다른 설계를 말하고 있다.**

| 문서 | 말하는 설계 | 근거 문구 |
|---|---|---|
| PJ2-RFP.md 6장 FR-01, 8장 구조도, AG-05, RFP-02 | **Router 분기형**: Router가 질문을 분류해 경로(공공 API / 금기 조회 / 문서 검색 / 안내 전환)로 **분기**한다 | AG-05 "질문 유형별 분기 테스트가 통과한다", "엔티티 추출 후 4경로 분기" |
| PJ2-RFP.md 8.2절, RFP-22, RFP-23-01, AG-01 | **단일 ReAct 에이전트**: `router` 노드는 입력 정리(엔티티 추출)이고, **도구는 `model`이 고른다** | 8.1절 "2~5단계는 에이전트(ReAct)가 도구를 골라 수행하는 기본 경로", RFP-23 §4.2 `router`·`model` 노드 표 |

- 8장 구조도 아래 설명("분기는 코드가 나누는 경로가 아니라 에이전트가 고르는 도구 호출의 기본 경로")이 이 충돌을 부분적으로 풀었지만 **AG-05 완료 조건은 아직 분기형 그대로**다.
- 이 충돌을 두면 AG-05를 구현할 때 "router가 경로를 정한다"로 만들게 되고, 그러면 에이전트(ReAct)의 도구 선택과 겹치거나, 사실상 고정 파이프라인(RFP-23의 C1)이 되어 "에이전트가 필요한 이유" 비교가 흐려진다.
- 결정 RFP-25-02에서 router의 역할을 하나로 정한다.

## 6. 패턴별 비교 분석


### 6.1 비교표
평가 척도는 ◎ 잘 맞음 / ○ 무난 / △ 부담 / ✕ 충돌이다. 판단 근거는 §4.2의 요건이다.

| 기준 | **Router 분기형**(코드가 경로 선택) | **단일 ReAct + router는 입력 정리**(현재 RFP-23-01) | **Supervisor + 서브에이전트** |
|---|---|---|---|
| 도구 수가 적은 단일 도메인(6개) | ◎ | ◎ | △ 도구가 적어 분리 이득이 작다 |
| 판정은 코드, LLM은 설명 | ◎ | ◎ | △ 서브에이전트가 판정에 끼면 충돌 |
| 근거 고정·Validator 원문 대조 | ◎ 경로가 정해져 근거가 명확 | ◎ 증거 목록을 상태에 누적 | △ `last_message`면 근거가 줄고 `full_history`면 토큰 증가 |
| 모델 호출 수·지연(상한 8회) | ◎ 가장 적음 | ○ 도구 호출 수 + 1 | △ 감독 + 서브에이전트마다 루프 + 최종 종합 |
| 오탈자·모호·예외 질문 대응 | △ 분기 규칙에 없는 질문에 약함(C1이 이 조건) | ◎ 도구를 다시 고르고 재시도 가능 | ◎ 이론상 가능하나 호출·실패 지점이 늘어남 |
| 평가 용이성(경로 평가·`pass^3`) | ◎ | ◎ 경로가 한 에이전트 기록에 모인다 | △ 감독·서브 경로를 모두 평가해야 함 |
| 3주·1인 구현 부담 | ◎ | ○ | △~✕ 에이전트 여러 개의 프롬프트·상태·평가 |
| 포트폴리오 스토리("에이전트가 필요한 이유") | ✕ 에이전트가 아니라 파이프라인 | ◎ C1 대 C2 비교가 성립 | ○ 단계적 도입 이야기가 되면 좋음, 처음부터면 과설계 |

호출 수 예시(제 추정, 가정: 도구 3번 호출): 단일 ReAct는 `model` 4회(도구 호출 3회 + 최종 답). 감독형은 감독 1회 + 서브에이전트 둘(각각 도구 1~2회 + 답) + 감독 최종 1회로 **6회 안팎**이 되어 상한 8회에 가까워진다. 서브에이전트 수나 재시도가 늘면 상한을 넘는다.

### 6.2 서브에이전트가 이득이 되는 경우와 아닌 경우
**이득이 되는 경우(공식 문서의 기준과 이 프로젝트)**
1. **컨텍스트 격리**: 허가사항 라벨처럼 긴 텍스트를 읽는 일을 "근거 탐색 서브에이전트"로 떼어 메인 컨텍스트를 아끼는 경우. 기준선에서 긴 텍스트 때문에 정확도가 떨어지는 것이 **관찰되면** 후보다. 이때도 근거 청크 ID와 원문 발췌는 그대로 넘겨야 한다.
2. **도구·역할 증가**: 확장(중복·용량·수유부·노인 주의, 프로필)으로 도구가 크게 늘어 한 에이전트가 도구를 잘못 고르는 경우. 지금은 도구 6개라 해당하지 않는다.
3. **병렬화**: 3개 이상 약의 쌍별 확인처럼 독립 작업을 동시에 돌릴 때. 다만 이것은 **코드가 쌍을 나눠 반복(map-reduce, `Send`)하는 일**이라 LLM 서브에이전트가 필요 없다. RFP-22-04에서 실패를 보기 전에는 쓰지 않기로 했다.

**이득이 아닌 경우**
- 금기 판정·고정 문구·119·Validator: 이미 코드라서 서브에이전트가 필요 없다.
- 쉬운 설명 쓰기: 한 번의 LLM 호출이면 된다(AG-06). 별도 에이전트로 만들면 호출만 늘어난다.
- "역할을 나누면 있어 보인다"는 이유의 분리: 평가 수치로 정당화되지 않으면 포트폴리오에서 약점이 된다.

## 7. 권장과 도입 조건


### 7.1 권장
1. **기준선은 단일 ReAct 에이전트**로 간다(RFP-23-01의 6노드 그대로). `router` 노드는 입력 정리만 한다(RFP-25-02 A).
2. **Router 분기형은 이미 대조군(C1·C1+)으로 있다.** 별도로 기준선으로 삼으면 "에이전트가 필요한 이유" 비교의 한쪽이 사라진다.
3. **Supervisor는 지금 도입하지 않는다.** 이유는 도구 6개, 판정 코드, 근거 고정, 호출 상한, 평가 규모, 3주 일정이다. 다만 **기준선 실패가 특정 모양일 때** 도입하는 조건을 미리 정해 둔다(§7.2).

### 7.2 Supervisor 도입 조건(AG-13이 쓰는 기준)
기준선(AG-11·AG-12) 측정 뒤 아래 중 하나가 **경로 평가·실패 사례 분석에서 관찰될 때만** 서브에이전트(우선 "근거 탐색"을 서브에이전트-as-tool로)를 검토한다. 임계값은 기준선 수치를 본 뒤 정한다(지금 숫자를 정하지 않는다).
1. 라벨처럼 긴 근거 텍스트가 컨텍스트를 채워 **Faithfulness·근거 묶음 Recall이 떨어지는** 실패가 반복된다.
2. 확장으로 도구가 늘어 **필수 도구 누락·오선택**이 경로 평가(RFP-23 §5.5)에서 두드러진다.
3. 한 에이전트의 시스템 프롬프트가 역할별 규칙 충돌로 길어져 **프롬프트 수정이 서로 영향**을 주는 실패가 반복된다.
도입하면 같은 평가 세트로 재측정하고 호출 수·지연·정확도를 기준선과 비교한다(RFP-23 결과 표 틀 사용).

### 7.3 비교 실험 시점
- **권장(A)**: Supervisor는 3주 이후 확장 비교(Reflexion과 같은 취급, RFP-22-10). 3주 안에는 기록만 한다. 이유: 평가 세트·예산·일정이 C0~C2 비교만으로도 빠듯하다(RFP-23 §10.3의 평가 비용 미측정).
- B(3주차에 C3 추가)를 택하면 평가 실행량이 조건 하나만큼 늘고 AG-12·AG-14·BE-08에 조건이 더해진다. 비용·시간 측정(RFP-15) 뒤에 판단하는 편이 안전하다.
