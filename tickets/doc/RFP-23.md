## 1. 이슈
2026-11-02 사용자 지적 두 가지를 Pre-Week 안에서 다룬다.
1. **노드 구성**: 지금까지 "최소 ReAct 그래프 = `model` ⇄ `tools` 두 노드"라고 적었는데, 이것은 강의 실습(계산기 도구 2개)의 모양이다. MediAgent는 `tools`에 도구 6개가 들어가고 입구·출구 안전 장치와 상태가 있어서 실제로는 두 노드로 끝나지 않는다. 노드 몇 개로 어떻게 나눌지는 아직 판단이 서지 않았다.
2. **“에이전트가 필요한 이유”의 수치 증명**: 금기 판정은 코드가 하므로 정상 질문은 고정 파이프라인과 차이가 없을 수 있다. 에이전트가 낫다는 것(또는 어디서만 낫다는 것)을 수치로 보이지 못하면 취업 포트폴리오의 스토리라인이 약하다.

사전 기간(Pre-Week)은 **2026-11-06(금)까지** 늘었고 1주차(W1)는 **2026-11-09(월)**에 시작한다. Pre-Week는 코드를 만들지 않는 설계·논의 단계라서, 이 티켓은 **그래프 설계서와 실험 설계서**를 만든다. 실험을 실제로 돌리는 일은 W2~W3 티켓(AG-04·AG-16·BE-08·AG-12·AG-14·PRD-03)이 맡는다.

## 4. 그래프 노드 구성 설계 (RFP-23-01)
> 코드는 만들지 않는다. 아래는 설계안이고 확정은 사용자가 한다. 노드 이름은 임시다.

### 4.1 강의 실습과 MediAgent의 차이
| | 강의 실습 1-3 | MediAgent |
|---|---|---|
| 도구 | 계산 도구 2개(`add`, `multiply`) | 6개: `identify_drug`, `check_contraindications`, `search_notice`, `search_reason`, `search_label`, `get_label_section`(RFP-22 §6) |
| 입구 | 없음 | 응급 감지, 범위 외·진단·처방 요청 거절(Guardrail, 코드) |
| 출구 | 마지막 AI 메시지가 곧 답 | 검증(Validator), 고정 문구·119 최상단·기준일(코드) |
| 상태 | `messages` 하나 | 응급 여부, 프로필(연령·임신), 약 후보, 증거 목록(청크 ID·계층), 호출 횟수, 검증 결과 |
| 분기 | 도구 호출 있으면 `tools`, 없으면 끝 | 거절이면 바로 마무리, 호출 상한이면 안내 전환, 검증 실패면 안내 전환 |

그래서 `model` ⇄ `tools`는 **ReAct 루프의 핵심 부품**이고, 실제 그래프는 그 앞뒤에 노드가 붙는다. 강의에서 연습한 부품(`StateGraph`, `ToolNode`, `tools_condition`, 조건부 엣지)은 그대로 쓴다.

### 4.2 노드 표 (A안 기준)
| 노드 | 하는 일 | 코드/LLM | 읽는 상태 → 쓰는 상태 | 기준선 포함 |
|---|---|---|---|---|
| `guardrail_in` | 응급 키워드 감지(`emergency` 표시), 범위 외·진단·처방·용량 결정 요청 판별 | 코드 | 질문 → `emergency`, `route` | 포함(안전 필수, RFP-22-08) |
| `router` | 약 이름·나이·임신 여부·의도 추출(구조화 출력 + 스키마 검증), 실패하면 fallback | LLM(구조화 출력) | 질문 → `profile`, `drug_mentions`, `intent` | 포함(FR-01) |
| `model` | 다음 도구 호출 또는 최종 답을 결정(ReAct의 Thought/Action) | LLM | `messages` → `messages` | 포함 |
| `tools` | 호출된 도구를 실행(단일 `ToolNode`에 6개 등록) | 코드 | `messages`(tool_calls) → `messages`(ToolMessage), `evidence` | 포함 |
| `validator` | 안전 단정·복용 지시 표현, 등급값(1·2·M), 근거 없는 문장·수치, 출처 ID 누락, M 원문 검사 | 코드 | 답 → `verdict` | 최소형만 포함(RFP-22-08). 근거 계층·누락 검사는 (개선) |
| `finalize` | 고정 문구, 119 최상단, 자료 기준일·조회 시각, 약국·약사 안내 부착, 거절·안내 전환 응답 구성 | 코드 | 모든 상태 → `answer` | 포함 |

### 4.3 tools 노드와 도구 6개
- **단일 `ToolNode`**: 6개 도구를 한 노드에 등록하면 모델이 부른 도구가 그대로 실행된다. 노드가 늘지 않고 강의에서 연습한 방식이다. 기준선에는 충분하다고 본다.
- **도구별 노드**가 필요해지는 때: 특정 도구의 결과에 **도구 전용 후처리**가 붙을 때다. 예: `search_*` 결과의 관련성 판정(`grade`, RFP-22-02 A의 애매한 경우), `check_contraindications` 결과의 코드 재검증. 이런 후처리는 기준선 실패를 본 뒤 (개선)에서 노드로 추가한다(RFP-22-08, 교안 91쪽).
- **미확인**: `ToolNode`가 한 번에 여러 도구 호출을 병렬로 실행하는지, `gpt-6-luna`가 병렬 도구 호출을 내는지는 확인하지 못했다(RFP-15에서 소량 호출로 확인).

### 4.4 상태(State) 필드 초안
| 필드 | 내용 | 갱신 방식 |
|---|---|---|
| `messages` | 대화·도구 호출·도구 결과 메시지 | `add_messages` 누적 |
| `emergency` | 응급 키워드 감지 여부 | `guardrail_in`이 쓰고 `finalize`가 읽음 |
| `route` | 정상 / 거절 / 안내 전환 | `guardrail_in`·`validator` |
| `profile` | 연령, 임신 여부(대화 입력, 저장하지 않음) | `router` |
| `drug_mentions` | 질문에서 뽑은 약 이름 목록 | `router` |
| `evidence` | 도구가 돌려준 근거(청크 ID, 계층, 출처, 기준일) | 누적(reducer로 이어 붙임) |
| `steps` | 모델 호출 횟수(상한 8회, RFP-22-05) | `model`이 증가 |
| `verdict` | 검증 결과(통과/수정/실패) | `validator` |
| `answer` | 최종 응답(요약, 근거 상세, 고정 문구) | `finalize` |

### 4.5 간선(엣지) 초안
```
START → guardrail_in ─(거절·범위 외)→ finalize → END
              │(정상, emergency 표시는 상태에 남음)
              ▼
            router ─(실패)→ finalize(약 미식별 안내)
              ▼
            model ⇄ tools      ← tools_condition: 도구 호출 있으면 tools, 없으면 validator
              │ (steps ≥ 8이면 finalize로 안내 전환)
              ▼
          validator ─(실패)→ finalize(안내 전환)
              ▼
           finalize → END
```
- 응급은 별도 병렬 경로를 만들지 않는다. `emergency` 표시가 상태에 남은 채 같은 경로를 끝까지 가고, `finalize`가 119 안내를 맨 위에 붙인다. 그래서 "금기 조회는 막지 않는다"(FR-06)가 자연히 지켜진다.
- (개선) 검증 실패 시 `model`로 되돌림(최대 2회, RFP-22-05)과 `grade` 노드는 기준선 실패를 본 뒤 더한다.

### 4.6 구성 후보 비교와 권장 (RFP-23-01)
**답할 질문**: 그래프 노드 구성을 어떻게 할까?

| | A (★ 권장) 6노드 | B 핵심 2노드만 | C 도구별·후처리 노드까지 |
|---|---|---|---|
| 구성 | `guardrail_in`, `router`, `model`, `tools`, `validator`, `finalize` | `model`, `tools`만 그래프. 입구·출구는 그래프 밖 함수(AG-01 현재 서술) | A + 도구별 노드 + `grade` 등 후처리 노드 |
| 장점 | 안전 장치가 그래프에 보여서 trace·경로 평가·포트폴리오 설명에 그대로 드러난다. 노드 6개라 구현 부담이 작다 | 가장 단순 | 이후 개선이 쉬움 |
| 단점 | 노드가 2개보다 많다 | 입구·출구가 그래프 밖이라 경로 평가·trace에 잡히지 않는다 | 기준선 과설계(교안 91쪽: 실패를 보기 전에 부품을 쌓지 않는다) |
| 권장 이유 | 위 장점 + 고정 문구·119 강제를 한 곳에서 보여 줄 수 있다 | - | - |

## 5. “에이전트가 필요한 이유” 수치 증명 설계 (RFP-23-02)
> 취업 포트폴리오라 수치 증명이 있어야 스토리라인을 쓸 수 있다. 이 절은 **무엇을 어떤 조건으로 재서 어떻게 읽을지**를 미리 정한다. 결과가 기대와 반대여도 그대로 기록한다.

### 5.1 증명하려는 주장 (사전에 고정)
| 가설 | 내용 | 지지되는 모양 | 반대되는 모양 |
|---|---|---|---|
| H-E1 | 분기 질문(오탈자·모호·오정보·근거 없음)에서 ReAct 에이전트가 고정 파이프라인보다 정답·안전 응답이 높다 | 분기 유형 몇 가지에서 C2의 k/n이 C1보다 높다 | 차이가 없거나 C1이 높다 |
| H-E2 | 정상 질문에서는 둘이 비슷하고, 에이전트는 호출 수·지연·토큰이 더 크다 | 정답은 비슷, C2 비용이 큼 | C2가 정상에서도 크게 나음/못함 |
| H-E3 | LLM 단독은 근거·고정 문구 지표가 낮다(RFP 9장 기존 비교와 같은 방향) | C0의 근거 표기·고정 문구 비율이 낮음 | 차이 없음 |

가설은 실험 전에 고정하고, 결과를 본 뒤 바꾸지 않는다.

### 5.2 비교 조건과 통제
| 조건 | 이름 | 도구를 부르는 순서·횟수를 정하는 쪽 | 구현 |
|---|---|---|---|
| C0 | LLM 단독 | 없음(도구 없이 답) | 같은 모델에 질문만 |
| C1 | 고정 파이프라인 기본 | **코드**(정해진 순서, 예외 규칙 2개) | AG-16 |
| C1+ | 고정 파이프라인 강화 | **코드**(C1 + 오탈자 보정 후 1회 재검색 규칙) | AG-16 |
| C2 | ReAct 에이전트(MediAgent) | **LLM**(ReAct) | AG-01 |

- **같게 둘 것**: 모델 `gpt-6-luna`, 도구 함수와 데이터(파일 기준, API 끔), Guardrail·Validator·고정 문구, 평가 세트, 평가 judge(Claude Sonnet 계열).
- **C1의 순서**: `guardrail_in` → `router` → 약마다 `identify_drug` → `check_contraindications` → `search_reason` → `search_label` → LLM 요약 → `validator` → `finalize`. 식별 결과가 0건이면 "약 미식별", 후보가 여럿이면 되묻기 카드로 끝낸다(**규칙은 이 두 가지만**).
- **공정성 주의**: C1에 예외 규칙을 많이 넣을수록 에이전트의 이점은 줄어든다. 그래서 **기본 C1(규칙 2개)과 강화 C1+(오탈자 보정·재검색 1회 추가)** 두 단계를 모두 두고, 규칙 내용을 **미리 고정하고 문서화**한다. 에이전트가 C1에는 이기고 C1+에는 비슷하다면 그것도 결과로 그대로 쓴다. 이 수준을 바꾸면 결과 해석에 반드시 적는다.

### 5.3 질문 세트와 분기 유형
- AG-04의 평가 문항마다 **분기 유형 라벨**을 단다: 정상 / 오탈자 / 모호(후보 여럿) / 오정보(잘못된 전제) / 근거 없음 / 범위 외 / 응급. 그리고 문항마다 **기대 도구 경로**(필수 도구)를 적는다.
- 예시 문항(RFP-21 §4.8): "타이레놀 먹어도 돼요?"(모호), "타이레놀이랑 와파린은 같이 먹으면 안 되죠?"(오정보), 위 P1~P3의 정상 질문. 오탈자·근거 없음 문항은 AG-04에서 추가한다.
- **표본 수의 한계**: 옛 권장인 총 20문항이면 유형당 3~4개라서 유형 간 우열을 말하기 어렵다. 그래서 분기 4유형을 유형당 20문항 안팎(총 약 150, PJ2-RFP.md 9.2절)으로 키웠다(§5.4). 못 채우면 유형별 k/n과 사례 중심으로 서술하고 일반화하지 않는다. 최종 문항 수는 AG-04에서 RFP-15-02와 함께 정한다.

### 5.4 "소표본"이 뜻하는 것과 문항 생성으로 해소되는 범위
소표본의 문제는 **비교하는 칸 하나(예: 오탈자 유형의 C1)에 들어가는 문항 수 n이 작아서 비율의 불확실성이 크다**는 것이다. 전체 문항 수가 아니라 **유형 × 조건 칸당 n**이 기준이다. 계산 예(Wilson 95% 구간, 정확 검정 p):

| 칸당 n | 50% vs 100% (큰 차이) | 70% vs 90% (중간 차이) |
|---|---|---|
| 4 | 15~85% vs 51~100%, p=0.43 (구분 불가) | p=1.0 (구분 불가) |
| 8 | 22~78% vs 68~100%, p=0.08 (경계) | p=1.0 (구분 불가) |
| 20 | 30~70% vs 84~100%, p<0.001 (구분됨) | 48~85% vs 70~97%, p=0.24 (구분 불가) |
| 50 | - | p=0.02 (구분됨) |

즉 큰 차이(예: 오탈자에서 절반 vs 전부)는 칸당 **20문항 안팎**이면 구분되고, 중간 차이(70% vs 90%)는 칸당 **50문항**이 필요하다. 이 표는 §5.6 규칙이 "유의성 주장 없음"에서 "큰 차이는 근거와 함께 주장, 작은 차이는 보류"로 바뀌는 기준이다.

소표본의 원인은 세 가지이고 해소 방법이 다르다.

| 원인 | 설명 | 해소 방법 |
|---|---|---|
| 문항 샘플링 | 문항이 적어 우연히 쉬운·어려운 문항이 몰림 | **문항 수 늘리기**(LLM 생성으로 해소 가능) |
| 실행 변동 | 같은 문항도 LLM이 매번 다른 경로·답을 냄 | **같은 문항 반복**(`pass^3`). 문항을 늘려도 해소되지 않음 |
| 채점 변동 | judge가 같은 답에 다른 점수를 줌 | 판정은 코드(파일 기준)로, judge는 설명 품질만 맡기고 일부는 사람이 확인 |

**LLM으로 문항을 생성할 때의 조건** (이 조건이 없으면 문항 수가 늘어도 표본이 늘지 않는다):
1. **정답은 LLM이 아니라 코드가 정한다.** 병용·연령·임부 금기는 파일(KIDS)에서 약 쌍·성분을 뽑아 정답을 자동 산출하고, 생성 LLM은 질문 문장(말투·오탈자·모호함·오정보 전제)만 만든다. 그러면 정답 라벨 노동이 줄고 오류가 없다.
2. **서로 독립적이어야 한다.** 같은 약 쌍에서 말투만 바꾼 문항은 사실상 한 문항이다. 약·성분 쌍을 다양하게 뽑고 쌍 하나당 유형별 1~2문항으로 제한한다.
3. **중복·템플릿 점검**: 문장이 비슷한 문항은 제거한다(유사도 점검).
4. **사람 검수 표본**: 문항의 약 15~20%를 직접 읽어 비현실적이거나 정답이 틀린 문항을 점검하고, 비율을 보고한다.
5. **한계로 남는 것**: 합성 질문은 실제 사용자 질문의 분포를 대표하지 않는다. 생성 모델은 Claude Haiku 4.5(사용자 결정)로 judge(Sonnet)·평가 대상(`gpt-6-luna`)과 다른 모델이지만 judge와 같은 Claude 계열이라 문체 편향이 약하게 남을 수 있다(PJ2-RFP.md 9.2절). 사람 검수와 기록으로 완화하고 한계로 적는다. 합성 질문의 대표성 한계는 리포트에 적는다. 문항 확대로 해소되는 것은 위 "문항 샘플링" 원인뿐이다.

### 5.6 해석 규칙
1. 결과는 **k/n으로 보고**하고 퍼센트만 쓰지 않는다.
2. 칸당 n이 20 안팎이면 큰 차이(§5.4 표)만 근거(p값·구간)와 함께 "관찰된 차이"로 쓰고, 작은 차이는 판단 보류로 쓴다. 칸당 n이 8 이하이면 유의성을 주장하지 않는다.
3. 차이가 있으면 trace로 **원인 사례 2건 이상**을 붙인다.
4. 반복 3회로 같은 결과가 나오는지 확인한다(`pass^3`).
5. 가설 H-E1~E3 각각에 **지지 / 불지지 / 판단 보류**를 적는다. 결과가 반대여도 그대로 쓴다.
6. 평가 세트와 C1 규칙 수준은 비교 중에 바꾸지 않는다(재현성).

## 6. 포트폴리오 스토리라인 초안 (RFP-23-03)

- **발견**: (1) 유형 7개 × 조건 4개를 여러 번 비교하는데 다중 비교 언급이 없음 (2) 정상 하위 유형(병용 15·연령 10·임부 10)은 칸당 n이 20 미만인데 단독 주장 금지가 없음 (3) `pass^3` 대상 문항이 정해지지 않음 (4) 오탈자 20문항의 짝 출처가 불명확 (5) 모호·오정보·근거 없음 문항은 정답을 파일에서 자동 산출하기 어려움 (6) judge 지표(Faithfulness, 정정 여부)의 채점 변동 (7) 시간이 부족할 때 줄이는 순서가 없음.
- **조치**: 9.1(다중 비교 보정 안 함·p값은 탐색적, 하위 유형 단독 주장 금지, judge 온도 0과 20문항 사람 교차 확인), 9.2(오탈자 짝은 금기 판정 35개 중 20개 변형, 생성 때 기대 응답 유형 지정, 근거 없음은 약·성분이 파일에 없음을 코드가 확인, 칸당 15까지 축소하는 순서), 9.4(`pass^3` 대상 40문항)에 반영.
- **남은 위험**: (a) 합격선 수치(95%, 90%, 10%p)는 근거 자료가 없는 잠정값이다 (b) 합성 질문은 실제 사용자 분포를 대표하지 못한다 (c) 문항 생성(Haiku 4.5)과 judge(Sonnet)가 같은 Claude 계열이라 문체 편향이 약하게 남을 수 있다. 사람 검수와 기록으로 완화하고 한국어 품질이 부족하면 Upstage를 고려한다 (d) 조건 간 결과가 비슷하면 짝 비교에서 불일치 문항이 적어 차이를 검출하지 못한다. 이때는 "차이 없음"이 아니라 "이 세트에서 검출되지 않음"으로 쓴다 (e) 고정 파이프라인의 규칙 수준(C1, C1+) 선택에 따라 에이전트의 이점이 달라진다.

### 10.3 3회차: 개발 정합·일정
- **점검**: 개발자가 9장만 보고 구현해도 되는지, 티켓과 문서가 서로를 참조하는지, 일정에 들어가는지 확인.
- **발견**: (1) 코드 채점 함수(금기 판정·고정 문구·119·경로)를 만드는 티켓 항목이 없음(BE-08에 평가 실행만 있었음) (2) AG-14에 보고 형식(구간·p값)이 없음 (3) PJ2-RFP.md의 FR·그래프·일정 부분에서 9장으로 가는 링크가 없음 (4) `CLAUDE.md`에 평가 기준을 갱신하는 규칙이 없음 (5) AG-04는 1주차에 문항 150개 생성·검수·10문항 시험 생성이 들어가 부하가 큼.
- **조치**: BE-08에 코드 채점 함수 완료 조건, AG-12·AG-14에 구간·p값·`pass^3` 대상 반영, PJ2-RFP.md 상단과 6장·8장·10장에 평가 참조 링크, `CLAUDE.md` 5장에 "평가 기준 유지 규칙" 추가. 부하는 9.2의 축소 순서(칸당 15까지)로 완충.
- **남은 위험**: (a) AG-04가 1주차 분량을 넘길 수 있다(정답 청크 목록 작성까지 포함). 이번 점검에서는 분량을 시간으로 추정하지 못했다 (b) 평가 실행 비용·시간(4조건 × 150문항 + 반복)은 `gpt-6-luna` 호출 비용을 모르는 상태라 미추정이다. RFP-15에서 소량 호출로 확인한다 (c) Upstage 생성 API 이용 가능 여부는 미확인이다.
