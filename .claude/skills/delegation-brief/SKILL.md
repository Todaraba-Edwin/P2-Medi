# delegation-brief

> 출처: `CLAUDE.md` 2장 "herdr 환경에서의 실행 규칙"과 "메인 pane의 역할과 위임"을 절차로 요약했다. **위임 기준·에이전트/모델 표·시작 옵션은 `CLAUDE.md` 2장이 원본이므로 여기에 복제하지 않는다**(표는 그쪽을 읽는다). 등록 결정: RFP-30-03(2026-11-09).

## 1. 지시서 양식
지시서는 로컬 전용 `data/mock/briefs/{날짜}-{주제}.md`에 쓴다(`.gitignore` 대상, 커밋 안 함). pane에는 "지시서 경로를 읽고 수행하라"만 보낸다.

```
# 지시서: {제목} ({날짜})
(맥락 한두 줄. 비밀값 금지, .env 열지 않음, 커밋·push 하지 않음)

## 1. 목표
## 2. 먼저 읽을 파일
## 3. 고치지 않을 파일   (동시에 다른 pane이나 메인이 고치는 것)
## 4. 산출물 경로
## 5. 검증 방법          (check_schedule.py가 일시적으로 실패하면 그 이유)
## 6. 보고 형식          (아래)
```

보고 형식: `## <에이전트> 보고` 아래 작업, 변경 파일(신규·수정 개수와 경로), 확인한 것·확인하지 못한 것, 결정 현황(번호·질문·★), 가정·확인 필요, `check_schedule` 결과. 비용이 큰 호출은 지시서에 상한을 적는다.

## 2. herdr 절차 (요약)
1. `test "${HERDR_ENV:-}" = 1` 확인. 아니면 중단.
2. `herdr pane list`로 workspace와 `cwd`가 P2-Medi인지 보고, 메인 pane ID를 **명시**해 `herdr pane split <메인 pane ID> --direction right --cwd "$PWD" --no-focus`. `--current`와 `$HERDR_PANE_ID` 직접 사용은 피한다.
3. `herdr pane rename <pane> <에이전트 이름>`.
4. `herdr agent start <이름> --kind claude --pane <pane> -- --agent <이름> --permission-mode acceptEdits --disallowedTools 'Read(./.env)' 'Read(./.env.*)'` (`--model`은 CLAUDE.md 2장 표에 따른다).
5. `herdr agent prompt <이름> "<지시서 경로를 읽고 수행하라>"`. 완료 대기는 전경 `sleep` 대신 백그라운드 감시 루프(`herdr agent get <이름>`의 `agent_status`가 `working`이 아닐 때까지)를 쓴다.
6. `herdr agent read <이름> --source recent-unwrapped --lines 120`로 보고를 읽는다.
7. 검수는 가볍게: `git status`, `wc -l`, `grep -n '^## '`, `check_schedule.py`처럼 작은 사실 확인만 한다(CLAUDE.md 2장 4번).
8. **검수가 끝나면 사용자에게 묻지 않고 바로 닫는다**(§3의 예외가 아니면). 닫기 전에 `herdr agent get <이름>`이 `working`·`blocked`가 아닌지와 `herdr agent read <이름> --source recent-unwrapped --lines 6`의 마지막 `❯` 줄이 비어 있는지 확인한다. `herdr pane close <pane>` 후 `herdr pane list`로 사라졌는지 확인하고, 보고에 "닫은 pane"을 적는다. 열린 채 남기는 것은 §3의 경우뿐이며 그 이유와 pane ID를 보고에 적는다(2026-11-09 사용자 지적: 완료한 pane을 묻고 닫지 않음).

## 2.1 pane 수명주기·재사용 규칙 (2026-11-09 사용자 지적 후 추가)
목적: 같은 역할 pane이 중복으로 열려 컨텍스트가 갈라지거나 같은 파일을 두 pane이 만지는 일, 끝난 pane이 방치되는 일을 막는다.
1. **열기 전에 `herdr pane list`와 `herdr agent list`로 같은 역할 pane이 있는지 본다.** 같은 역할은 **한 번에 하나**만 둔다. `-2` 같은 중복 이름 pane을 만들지 않는다.
2. **있고 `idle`이며 입력창이 비어 있고 컨텍스트 사용률(pane 하단 `컨텍스트 N%`)이 50% 미만이면 재사용한다**(`herdr agent prompt`만 보낸다). 같은 티켓 계열의 후속 지시는 재사용이 기본이다(앞 작업의 맥락과 파일 상태를 이미 알고 있어 읽기 비용이 적다). 컨텍스트가 50% 이상이거나 전혀 다른 일이면 보고를 받고 닫은 뒤 **같은 이름으로** 새로 연다.
3. **작업 pane 입력창의 사용자 글은 메인에게 하려던 말이다**(2026-11-09 사용자 확인: `PRD-11-01~06 권장대로`는 schedule-writer가 아니라 메인 pane에 요청할 내용이었다). 메인은 마지막 `❯` 줄을 읽어 **메인에 준 답·지시로 접수**하고(이미 준 답과 겹치면 최신 문장과 합쳐 해석을 사용자에게 한 줄로 밝힌다), 그 pane에는 보내지 않는다. 사용자가 "그 pane 종료"라고 하면 닫는다. 아래는 그 글을 접수하지 못하거나 사용자 뜻이 불명확할 때의 절차다.
   **입력창에 사용자가 쓴 글이 있으면**(마지막 `❯` 줄) 그 pane에 지시를 보내지 않고, 새 pane도 열지 않는다. 사용자에게 한 줄로 알린다: "pane ID의 입력창에 글이 있어요. 보낼지(Enter) 지울지 알려 주세요." 사용자가 지우거나 보내면 재사용하거나 닫는다. 글이 이미 새 지시로 덮였으면(사용자가 그렇게 말했을 때) 사용자 확인 뒤에 닫는다. **사용자 글을 임의로 지우거나 대신 보내지 않는다.**
4. **작업 중인 pane이 있는 같은 역할에 두 번째 일을 맡기지 않는다.** 같은 파일(`schedule.md`, 티켓)을 두 pane이 동시에 고치면 충돌한다. 끝나기를 기다렸다가 같은 pane에 이어서 시킨다. 대기는 `herdr agent wait <이름> --state idle`(또는 백그라운드 감시 루프)로 한다.
5. **끝나면 닫는다**(2번 절차 8단계). 사용자가 입력창에 쓴 글이 남은 pane만 예외이고, 그 pane ID를 보고에 적어 사용자에게 처리를 요청한다.
6. **승인 창(`blocked`)**: 어떤 명령인지 `herdr agent read <이름> --source visible`로 읽어 사용자에게 pane ID와 명령(읽기 전용 여부)을 알린다. 입력은 보내지 않는다. 승인 대기가 반복되면 읽기 전용 명령의 허용 규칙(settings)을 제안한다.
7. **메인 컨텍스트 위생**: 사용자가 `@파일`로 큰 문서를 첨부해도 메인은 `wc -l`·`grep -n '^## '`·필요한 줄 `sed -n`으로 필요한 부분만 본다. 300줄 넘는 문서의 처음부터 끝까지 읽기·긴 문서 작성은 위임한다(CLAUDE.md 2장 1번). 지시서는 짧게 쓰고(목표·읽을 곳·산출·보고), 사용자 문장은 그대로 인용하되 해석은 한 곳에만 적는다.

## 2.2 보고는 파일로 받는다 (2026-11-10 사용자 지적: 보고가 메인 pane에 안 전달됨)
pane이 여러 개 나란히 열리면 폭이 좁아 `herdr agent read` 결과가 한두 단어씩 줄바꿈되어 읽을 수 없다. 그래서 **모든 지시서의 보고 형식에 "최종 보고를 `data/mock/briefs/reports/{pane 이름}.md`에 Write 도구로 저장한다"를 넣고**, 메인은 pane 화면이 아니라 그 파일(`sed -n`·`head`)을 읽어 검수한다. 보고 파일에는 변경 파일, 시험 결과, 확인하지 못한 것, 완료 조건 체크 제안, **닫은 pane**을 담게 한다. 파일이 없으면 pane에 "방금 낸 보고를 그대로 파일로 저장하라"고 한 번 시킨다.

## 2.3 완료 pane 정리 점검 (매 턴)
여러 pane을 병행하면 끝난 pane이 조용히 쌓인다. 메인은 **새 작업을 보내기 전에, 그리고 사용자 메시지에 답하기 전에** `herdr pane list`와 각 에이전트의 `agent_status`를 한 번 훑어 `idle`·`done`인 pane을 보고 파일을 확인한 뒤 바로 닫는다. 병행 pane이 둘 이상이면 **끝남 감시**를 한 개 두고(`until`루프가 어떤 pane이든 `working`이 아니게 되면 끝나는 백그라운드 명령), 알림이 오면 같은 턴에서 검수·종료한다. 알림이 와도 다른 지시를 먼저 하다가 닫기를 미루지 않는다.

## 2.4 완료 프로토콜: 보고 파일 + NEXT 블록 (2026-11-10 사용자 분석 요청 후)
**원인 분석(사실):** ① 작업 pane은 대화형 Claude 세션이라 일을 끝내도 **스스로 종료하지 않고 idle로 입력을 기다린다**(정의 파일도 "pane을 열거나 닫지 않는다"). 닫는 주체는 메인뿐인데 메인은 끝남을 **끌어와서(poll)** 알 수밖에 없고, 감시를 일부 pane에만 걸었다. ② 보고가 pane 화면에만 있어 메인이 읽기 어렵고(좁은 폭), 메인이 먼저 읽을 이유가 약했다. ③ `schedule-writer`는 git을 못 하게 정의돼 있어 사용자가 입력창에 "커밋해줘"를 써도 **"제안 상태"(메인이 git-actor를 시키라는 말)로 멈추고**, 이를 메인에게 알리는 통로가 없었다.
**프로토콜:** 모든 지시서의 보고 형식에 아래를 넣는다. (a) 최종 보고를 **`data/mock/briefs/reports/{pane 이름}.md`**(파일 이름 = pane 이름)에 Write로 저장하고 pane에는 "저장했다" 한 줄만 쓴다. (b) 그 파일 끝에 **`## NEXT` 블록**을 둔다: `STATUS: DONE|BLOCKED|NEEDS_USER`, `CHANGED:` 변경 경로 목록, `COMMIT:` git-actor에게 맡길 묶음과 제안 메시지(작업자는 git을 하지 않고 제안만 쓴다), `NEEDS_USER:` 사용자 승인·답이 필요한 것(없으면 없음), `NEXT_JOB:` 이어서 시킬 작업(있으면). (c) 작업자는 사용자가 입력창에 쓴 "커밋해줘" 같은 글을 **거절 대화로 끝내지 말고 NEXT 블록의 COMMIT에 반영**하고 종료한다. 메인은 NEXT 블록을 읽고 곧바로 git-actor·다음 작업을 지시하며, 끝난 pane은 `scripts/herdr_sweep.py`(idle·입력창 비어 있음·보고 파일 있음이면 `--close`로 닫음)나 수동으로 닫는다.

## 3. 닫지 않는 경우(이 경우에만)
에이전트가 `working`·`blocked`이거나 timeout으로 끝났을 때, 사용자 답·승인이 필요할 때, pane 입력창에 사용자가 적은 내용이 있을 때. 승인 창에는 입력을 임의로 보내지 않고 사용자에게 알린다.

## 4. 주의
- 같은 파일을 두 pane이 동시에 고치지 않게 파일 소유를 나눈다.
- 같은 일에 여러 관점이 필요하면 회차마다 관점을 나누고 앞 회차 결론을 알려 주지 않는다(앵커링 방지).
- 새 에이전트 정의 파일은 만들지 않는다. 맞는 것이 없으면 전역·일반 에이전트를 쓴다.
